# Amendments to the API design, section 4.6 (`paddock-limits`, packages 1.4 and B1)

Next to `docs/plans/debrief-1-2-api.md` (revision 5, on `docs/debrief-1-2-api`), so the packages that use `paddock-limits`
read the contract as built on branch `debrief/1.2-limits`. Each row is a point the design left open or that the code
had to settle. Review 1 (of 479dcff3f) settled L6 and L8; see the last section.

| Q | Design said | Built | Why |
|---|---|---|---|
| L1 | `SettingPath`, `Unit` named, not defined | `SettingPath(&'static str)`: dotted parts `[a-z][a-zA-Z0-9_]*`, at most 64 bytes, `const fn new`. `Unit` = `Bytes, Count, Ratio, Millis, Percent`, one per `Quantity` variant | Needed to compile; `Registry::check` requires default, min and max in the row's unit |
| L2 | `FieldPath(Box<str>)`, grammar in ADR 0065 | `FieldPath(Cow<'static, str>)`, same grammar (at most 64 bytes, `[a-z][a-zA-Z0-9]*` parts with one optional `[u32]`, never starting with `result`), plus `FieldPath::lit` as a `const fn` and `root()` | A literal in a `const` fails the build instead of a test; constructors take a `FieldPath`, not a `&str` |
| L3 | `Bounded::first(iter, row, of)` | Same, using the row default as the limit; plus `first_with(iter, row, limit: RowLimit, of)` where a `RowLimit` comes only from `CutRow::limit_of(value)`, which checks the row's min and max | A Setting's current value is not in the registry row, and a bare number could be outside the bounds |
| L4 | `CutRow<S>` "generated by the registry" | `CutRow::<S>::of(&ROW)` is a `const fn`; used in a `const` it fails the build for a stop row, a row that does not declare `S`, or a row that does not count items | Same guarantee without a generator; B3 may still generate the consts |
| L5 | `LimitId(&'static str)`, `Cut` deserializes | `LimitId::parse` validates the syntax. Ids of a registered registry (`LimitId::register`, plus the built-in `bounded.cuts`) resolve to their static text and can never be refused; any other key is interned (leaked once per distinct key), **at most 4096 unknown keys**, then `BadKey::Full` for those only | `&'static str` cannot come from the wire otherwise; the bound keeps hostile input from growing memory |
| L6 | More than 32 cuts: "keep the first 31 by the position of their list in `result` (outer first, then index)" | The 31 smallest in the **structural order of `FieldPath`** (a path before the paths inside it, siblings by name, entries of one list by numeric index), kept sorted, so `.and` does not depend on the order cuts are added in (proptest-style test with a reversed order) | A constructor cannot know where a list sits in `result`; the path order is the same order for the usual reply shapes. Review item addressed |
| L7 | `.and(cut)` on a second cut of the same list | A cut with the same `(of, limit)` replaces the earlier one in place (and is not counted again) | `TryFrom<BoundedWire>` refuses duplicates, so `.and` must not make them |
| L8 | Message "Raise it in Settings -> Performance -> Plugin memory" (ADR 0019) | `message(&Registry)` writes the dotted path; `message_with(&Registry, &dyn SettingLabels)` writes the schema's words (`SettingLabels::label(path) -> Option<(section, field)>`, implemented by the app over its schema); `setting_path(&Registry)` gives the structured log field. `SettingPath` has the grammar of `paddock_settings::valid_id` (a test in `paddock-settings` keeps them equal). Measured values (`reached`) are rounded (`1.2 GiB`), limits stay exact | The crate stays a leaf, and the words belong to the Settings schema |
| L9 | `LimitExceeded { id, limit, reached, scope }` | As specified; the Setting path and remedy come from the row via `message(&Registry)` | The design's struct has no path field |
| L10 | Constructors return values only | **No constructor panics on a number.** There is one constructor per selection (`counted_first`, `page`, `counted_top`, `counted_last`, `counted_sample`, `at_least`, `maybe`), each taking the handle of its own selection, so a wrong kind of row does not compile. Numbers that disagree (a stale offset after a filter, rows that arrived between the count and the read) give a cut with `Total::Unknown`; a window that does not start at 0 is always a cut | Request and I/O data reach `page` (review P1-1); the first design assumed they could not |
| L11 | `Cut::maybe(row, of, shown, selection)` | `CutRow<Maybe>` handle (selection kind `Maybe` in the row) | Instance 12 needs an unknown total with a real selection |
| L12 | Generated `core/generated/limits.ts` | Only `--features ts` declarations, checked against the golden file `tests/golden/limits.ts` (`CutWire` is exported as `Cut`, `BoundedWire<T>` as `Bounded<T>`; counts are `number`); `Bounded<T>` and `Cut` implement `TS` by delegating, so a struct holding them can derive it. No file is written under `ui/` | The UI entry point is B2/2.3 |

## Package split (coordinator decision, 2026-11-07)

Package 1.4 + B1 is the crate and the testkit (this branch, `debrief/1.2-limits`). Its adoption pieces are their own
package, **1.4b**, after IP1, on its own branch:

- variants that keep `LimitExceeded` in `paddock-archive`, `paddock-ipc`, `paddock-plugin-host`, `paddock-jobs` and
  `paddock-health` (`Cause` from it);
- shared rows 51 to 62, each with a `limit_case!` (each crate owns its registry rows);
- the conformance completeness check (`conformance/src/limits.mjs`, warning mode);
- the `JobState` / job wire change with the regenerated TypeScript. Before v1 the wire changes directly: no shims, no
  migration. `paddock-jobs` and the job wire are shared code that every app ships, so 1.4b updates every consumer in
  the same change (rules 39 and 43) and runs every app's affected tests. It merges only after the Dyno tag.

## IP1 deviations (branch `debrief/1.2-ip1`)

| Q | Design said | Built | Why |
|---|---|---|---|
| I1 | "An oversized reply from a plugin is the plugin's fault (`Failure::Garbled`)" | New `IpcError::ReplyTooLarge { len, max }` (not process failure); `Peer::on_skipped` posts it for Reply, Item and Fail frames; the supervisor maps it to `FaultKind::Garbled` | `IpcError::TooLarge` is also the error of our own request being too large; one variant could not tell them apart |
| I2 | `PeerOptions { write_queue, write_queue_bytes }` | Both, plus **`write_stall`** (default 30 s on the peer's clock). Defaults 256 frames, 32 MiB. A sender blocks while the queue is full, for at most the stall or its call's own timeout (`min`). **Stall: the connection closes** ("<label> stopped reading for 30 s"), the queue shuts first, every pending call fails with that reason, the sender gets `IpcError::Timeout`; a stall drops the frame, and a lost reply, credit or cancel would leave the sides disagreeing. **A call's own timeout running out** fails only that call (nothing is closed). **The reader thread never waits**: it sends with `try_push`, and a full queue there closes the connection at once (two full sides would otherwise wait for each other). One frame over the byte bound is accepted into an empty queue | "blocks, then fails at the bound" needs a deadline, and a dropped frame cannot be survived; it is an option, not a constant, so tests drive it with a fake clock (IP1 review P1) |
| I3 | `ProtocolError { RepeatedCallId { id }, ItemWithoutCredit, .. }` | `ProtocolError { RepeatedCallId, ItemWithoutCredit { received, granted }, ItemForNonStreamingCall }`, `#[non_exhaustive]`; the connection closes with `IpcError::Protocol(text)`. A repeated id is detected while the first call is running or waiting only | Ids are allocated before the send, so they can arrive out of order; a strictly increasing rule would refuse legitimate calls, and remembering finished ids is unbounded |
| I4 | `Contract::role` and `introduced_in` | Only `introduced_in` (default 0); `Remote::call_within` refuses with `HostError::Unavailable` before sending. `role` stays with 2.6b | Scope of IP1 item 4 |
| I5 | `PeerCredentials` compared with the host's own uid on Unix | `PeerCredentials` (re-exported), `Authenticator::authenticate_as`, `Host::same_account_only()` (on in `launch()`; **off by default**). Another uid, or an unreadable uid, is refused before the hello is read | A system service accepts other accounts; a default-on rule would break Dyno's service |
| I6 | "fuzz target for plugin request bodies" | `paddock-ipc/fuzz` target `plugin_request` (depends on `paddock-plugin-api`), and the nightly job `shared-fuzz` | `nightly.yml` is a shared integration point, so the job is in its own commit |
| I7 | Re-export `codes` and `cancelled_error` | `paddock_plugin_api::codes`, `ExtCtx::cancelled_error()`. "An example plugin builds with `paddock-plugin-api` as its only platform dependency" is not proven by a separate example crate | Not built in this package |
| I8 | README: "no app links `paddock-ipc` on `main` yet" | Dyno links it on `main` (by path); the row says so | The plan statement is wrong for Dyno |
| I9 | (not in the design) | `IpcError` gained a variant, so Dyno's exhaustive match in `apps/dyno/crates/dyno-plugin-host/src/host.rs` changed in the same change (rule 39): `ReplyTooLarge` maps like `TooLarge` to a protocol failure of the plugin. Dyno's agent, cli, plugin-host and plugin-api tests: 458 passed | A shared enum change updates every consumer in the commit that makes it |

## Review 1 of `479dcff3f`: what changed

| Item | Change |
|---|---|
| P1-1 | No constructor panics; one constructor per selection; stale windows have an unknown total; a window not starting at 0 is a cut (L10) |
| P1-2 | `Bounded<T>` and `Cut` implement `ts_rs::TS` by delegating to their wire types |
| P1-3 | Registered ids resolve first and are never refused; the flood test uses a local table, not the process-wide one (L5) |
| P1-4 | `limit_cases!` generates one `#[test]` per case plus a both-ways check against the registry; the process-wide record of exercised ids is gone |
| L6 / L8 / L3 | See the rows above |
| Wire | `AtLeast` only for the first items from 0 (so a ranking or a middle page has an exact or an unknown total); the aggregate must be the last of exactly 32 cuts, `of` empty, `First{0}`, `Exact` with more than 31, shown 31, `Next::None` (the count cannot be unknown, so `.and` needs no rule for it); `LimitExceeded`'s units must agree (`reaching` returns a `Result`); a `Percent` over 100 is refused |
| Serialize | `Bounded` serializes by borrowing; no `Clone` bound |
| Format | The crate doc and a test say JSON/self-describing formats only (postcard fails) |
| Text | `describe()` reads "rows: showing 501 to 503 of 1,204 (test.first)" |
| Mutations | Both-rows-in-bytes and `AtLeast` outside `First{0}` are now killed (see the commit message) |

## Review 2 of `d5f684c21`: what changed

| Item | Change |
|---|---|
| P1 | `Cut::describe()` cannot overflow: the sums saturate; a window's start is clamped so `from + shown` fits u64; `check` refuses `from + shown` past u64 even with an unknown total (red first: debug overflow panic in `describe`) |
| P2 | An index with a leading zero is not a field path (`groups[03]`) |

| P2 | `limit_cases!` documents one module per registry |
| P2 | `message_with` shows the limit's value, not the id (the id stays in the log form) |

## Review 3 of `03f9a652e`: what changed

| Item | Change |
|---|---|
| Quantity wire | The tag is read through a derived `Kind` (a name from JSON, an index from a compact format) and the number at the kind's own width (u32 ratio, u8 percentage, u64 otherwise); the `human` flag is gone. Round trips are tested for JSON, postcard, MessagePack (default and named) and bincode (red first: MessagePack failed for every kind, bincode for ratio and percentage) |
| Repeated keys | `{"kind":"bytes","kind":"count"}` is `duplicate_field`, not the last one |
| JSON arrays | `["bytes", 5]` is still accepted (compact formats write a struct as a sequence); documented on `Deserialize for Quantity` |
| Aggregate words | The count can include lists counted before and added again, so `describe()` says "up to N" (`the value: the first 31 cuts of up to 40 are listed (bounded.cuts)`) |
| Row helper | `LimitRow::stop` builds the usual stop row; 1.4b uses it for the other shared crates |

## Package 1.4b: what it covers and what it leaves (coordinator decisions, 2026-11-08)

Built (branch `debrief/1.2-limits-adopt`): `LimitExceeded` kept in `ArchiveError::Limit`, `JobError::Limit`, `JobState::Failed`
and `WireState::Failed` (with the UI's `SuJobState.limit` and parser); `IpcError::limit()` and `HostError::Limit`;
`Cause::from_limit`; rows with `limit_cases!` for ipc (51), plugin host (52, 53), guard (54), archive (55), net (56), download
(57), updater (58), view (59), diag (60) and storage (61); `LimitId::register` from the shell builder; conformance check C62 in
warning mode (a row without a case, and limit-shaped constants no registry file mentions: today it lists the older constants of
diag, download, guard, ipc, net, shell, storage and updater, to be turned into rows or waived by name).

Follow-ups, deliberately not in 1.4b:
- Debrief's, Pitwall's and Spotter's job models (their own `JobState`) keep their failure text; they adopt the limit with their
  own registries (Debrief 3.6, B3).
- Row 62 (the UI's IPC call timeout) is TypeScript and goes with the UI package (2.3, `LimitNotice`).
- `Cause::from_limit` is not yet called by an app; the first caller is the plugin host's memory kill (2.6a).
- C62 becomes an error when Debrief's list is reasoned (ADR 0019 phases it).

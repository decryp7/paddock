# Audit of long operations, progress and parallelism (2026-10-23)

Read-only audit of origin/main of Debrief, Pitcrew, Pitwall, Spotter and Dyno against the rule of 2026-10-23: live phase-labelled progress from the first moment, one scale per phase, Cancel in every phase, bounded multi-threaded and pipelined processing. P1 = users see "stuck" or very slow on realistic data; P2 = noticeable; P3 = minor. Effort: S/M/L.

Already known and being fixed in Debrief (not repeated): AI model/runtime download then checksum restarting the bar (fix/ai-setup-once); large-folder import stuck at 0 during discovery (fix/import-large-folder).

Cross-app finding: Pitcrew, Spotter and Dyno have no progress or cancel channel at all, so a shared job/progress port (throttled, phase-labelled events plus a cancel token) should be built once in the Paddock shared crates and adopted per app.

## Structural gaps behind many rows

- **No phase in the progress types.** `ProgressSnapshot` (crates/debrief-core/src/workspace/mod.rs:75) has done/total/bytes/current only; `JobProgress` (app/src-tauri/src/jobs/model.rs:201) has no phase/label either. A phase can only be a free-text `ctx.message(..)`, so "name each phase on its own scale" is not expressible. Add `phase: Option<Phase>` (enum + own done/total/indeterminate) to both, and let the Jobs pane (app/src/app/jobs/jobs-panel.ts:82-95, already renders `<progress>` indeterminate when `fraction` is null) show "Phase - count".

- Good reference to copy: the folder survey (crates/debrief-core/src/survey/mod.rs:93-160, app/src-tauri/src/ai/folder_setup.rs:67-100) has stages, own total per stage, cancel and a time budget.

## Anti-pattern checklist

- **Work before the first progress event:** `files_to_read` + loading all known source paths (lib.rs:376-390, known); `changed_files` stat of every source and `compile_parsers` in `set_profile` (profiles.rs:109-130); `refresh` SQL per path and `fts.delete_source` (lib.rs:781-815); `exact_selection` pass in analyses (analysis.rs:733).
- **Totals computed in a separate pass:** analyses with non-exact filters (row 13).
- **Re-reading files for hashes after writing:** `chromium_driver::install::sha256_file` (row 5; AI one is the known item). Counter-example done right: `bundle::extract` hashes while writing (core/src/bundle.rs:290-300), `fetch.rs` verifies PDB identity by header only.
- **Sequential per-file loops over trees:** redacted copy (row 4), zip export/extract (rows 3, 20), compaction groups (rows 1, 7), watched folder (row 10), `walk` in package.rs:213.
- **Per-item IPC events without throttling:** none found. The Jobs service ticks (jobs/service.rs `with_tick`) and the import follower polls every 100 ms (engine/import.rs:21), so UI event rate is bounded.
- **UI thread blocking:** none found in the Angular layer (all calls go through backend services). Shell commands that block an IPC worker for the full duration: rows 3, 4, 5, 8, 14, 21 (they run under `spawn_blocking`, so only that command waits, but there is no feedback).
- **Parallelism already good:** import parse pool (`ingest::import_files_parallel`, ingest/parallel.rs:201-206), symbol downloads (servers.rs:169), anomalies in DuckDB SQL.

# Pitcrew: long-operation progress / cancel / threading audit (main @ f1f7e56, read-only)

Paths: E = /Volumes/d8sst7/dev.decryptology.net/pitcrew/crates/pitcrew-service/src, T = .../app/src-tauri/src, U = .../app/src/app.

## Cross-cutting findings (verified)
- **There is no progress channel at all.** `ServiceEvent` has only `Status` and `Notification` (crates/pitcrew-core/src/protocol.rs:~469-480). Requests are one-shot request/response, one connection each (T/service_client.rs:127-136). No operation reports a count or bytes. The only "progress" is the `UpdatePhase` enum (downloading/verifying/...), shown by a step bar with no numbers (U/shared/ui/update-progress.ts:10-40). Every other long operation is a spinner or button text.
- **No cancel token exists anywhere.** Workers are detached `std::thread` closures (E/supervisor.rs:1041-1050, E/supervisor/ops.rs:24,32,48,61,105). The only "Cancel" is the update state machine (U/features/updates/updates-page.html:81-83 -> machine.rs:352). It changes state and discards the file, but the HTTP download or hash worker keeps running (no flag is checked in net.rs:87-101 or net.rs:150-153).
- **UI timeouts are shorter than the real work.** U/core/call-timeout.ts:9 gives `clean_disk`, `engine_prune`, `cache_clean`, `register_runner`, `install_app_update`, `export_diagnostics` 120 s. `runner_disk`, `engine_report`, `cache_*` get 60 s (line 10). The backend allows 10-16 min (T/service_client.rs:117-123, E/ipc.rs:72-79). On a big tree the UI shows a timeout error while the service keeps working and then finishes silently. Users read this as "stuck".
- **All IPC replies are single, final and buffered.** Nothing is streamed. This is fine for small replies but means a progress event type has to be added before any other fix is visible.
- Threads: workers are unbounded (1 thread per request or runner), but none of them parallelises inside a job. Nothing uses rayon or walkdir. Every tree walk is a single-threaded `read_dir` + `metadata` stack loop.

## Detail on the specific anti-patterns asked about

1. **Download then re-read to hash (restarts a bar): CONFIRMED.** `Http::download` (E/net.rs:87-101) already computes `Sha256Digest` while writing. `work::download` (E/work.rs:73) drops it. `work::verify_download` (E/work.rs:90) calls `net::file_digest` (E/net.rs:150) which re-reads the whole `.download` file. This is a separate phase on a separate worker (E/supervisor.rs:1099-1106), so the user sees "Downloading" then "Verifying" again over the same bytes. Also fetches the checksum files only after the hash (work.rs:93-110) rather than during the download.
2. **Work before first progress event:** nothing emits progress events at all; `Disk`, `CleanDisk`, `CacheReport` etc. run their full walk before any reply (E/supervisor.rs:1499-1517, ops.rs:56-117).
3. **Totals in a separate pass:** not used (no totals exist), but `cleanup::scan` does measure the whole runner dir again after measuring its entries (cleanup.rs:142), and `cache_clean` flows re-walk after preview (hygiene.rs:380).
4. **Sequential per-file loops over trees:** all of `cleanup::measure`, `clear_read_only`, `hygiene::tree`, `remove_dir_all` per entry.
5. **Unthrottled per-item IPC events:** none today (no events); keep throttling in mind when adding.
6. **UI-thread blocking:** none. All Tauri commands go through `blocking()` (T/commands.rs:71) or async tasks. Only `diagnostics()` blocks the service's control loop (supervisor.rs:1731).
7. **Budgets silently truncate instead of continue:** cleanup 500k files/30 s (cleanup.rs:20-22), hygiene 300k/20 s (hygiene.rs:24-26). With a parallel walker the time cut-off can become much more generous, and "truncated" should be displayed as a count ("500,000+ files").

## Suggested implementation order (shared building blocks)
1. `Progress` plumbing (S): `ServiceEvent::Progress { op: OpId, phase, done, total: Option<u64>, bytes }`, throttled 4/s; `CancelOp { op }` request; `Arc<AtomicBool>` token passed to workers; mirror in api.types.ts + mock backend; one `<pc-operation-progress>` component (indeterminate + count, Cancel button).
2. Download pipeline (#1, #5, #6) using the token: digest carried through, byte progress, parallel checksum fetch.
3. Parallel walker module (`E/walk.rs`: bounded pool, per-entry tasks, count callback, cancel) used by #2, #3, #4, #8.
4. Delete pipeline for cleanup/cache (#2, #4).
5. Prune streaming + kill (#7), diagnostics off the loop (#9), check-update state (#10).
6. Replace per-command fixed UI timeouts (call-timeout.ts:9-10) with "no progress for N seconds" stall detection.

## Headline: the Debrief bug IS present in Pitwall (two places)

**Model download** (`S/egress.rs:131-200`, called from `S/library.rs:399`): the body is streamed to `<file>.gguf.part` with progress
(throttled 400 ms, `library.rs:401`), then `egress.rs:189` calls `sha256_file` (`egress.rs:204-221`), which re-reads the entire file
(1 MiB chunks, `spawn_blocking`) with **no progress callback and no cancel check**. For a 5-40 GB GGUF that is 10 s to minutes (disk bound) where the UI shows
`downloading`, bytes = 100 %, speed frozen. The `Verifying` state is set only **after** `download()` returns (`library.rs:423`), i.e. after the hash is already finished,
so it only covers the cheap GGUF header parse (`verify_gguf`, `library.rs:481`). The `Verifying` state exists in the DTO
(`pitwall-core/src/mgmt.rs:780`) and `UI/shared/labels.ts:168` but is effectively never visible for the real cost. Resume (`416` branch, `egress.rs:151`) also re-hashes the whole file.
UI: `UI/features/models/downloads-list.ts:36-44` draws one bar from `bytesDone/bytesTotal`; once done == total it sits at 100 % until the state flips.
No phase has its own scale; the hash phase has no scale at all (not "restart under the same label", but "silent + stuck at 100 %").
Fix is the standard one: hash incrementally while writing (the bytes pass through `write_all` at `egress.rs:177`; a resumed `.part` needs a one-time prefix hash, which is itself a labelled phase "Checking existing data" with its own bytes bar, cancelable). Then `Verifying` becomes ~instant.

**Engine (llama.cpp) install** (`S/engines.rs:373-460`, driven by `S/engine_setup.rs:68-165`): same download+rehash through `egress.download` (`engines.rs:401`) for each archive (50-300 MB, CUDA builds 500 MB+; ~1 s to several s), plus:

- `bytesTotal` for multi-asset builds is the sum of assets, one bar (acceptable) but unpack/self-test have no scale.

## Cross-cutting anti-patterns found (cite)
1. **Request timeout shorter than engine deadline**: cleanup scan 40 s (centre.rs:26) vs 15 s IPC (link.rs:21). Fix first, even before progress work: it creates false failures today.
2. **Work before first progress**: nothing emits progress at all; first feedback is the final reply.
3. **Static-text UI states**: `scanning ? 'Scanning…'` (cleanup-page.ts:37), `rescanning` spinner (issues-page.ts:32), `'Moving…'` (cleanup-page.ts:141).
4. **Sequential per-item/tree loops**: scan.rs:74-88, :106-148; walk.rs:70-100; usage.rs:62-100; centre.rs:108 (categories); issues.rs:75 (sources); run.rs:58 (items).
5. **Walk-then-measure in separate steps**: `children` lists, then each `candidate` re-walks its subtree with `measure` (scan.rs:37-62) on the same thread; no pipeline.
6. **Fixed-entry-budget truncation instead of cancel**: Budget (walk.rs:8-37) + 5 s/200k disk map cap yield biased partial results.
7. **No cancel token** in any walker; `Budget` is the natural place to add an `AtomicBool`/`CancelToken` check (one change covers scan, disk map, project walk).
8. **No unthrottled per-item IPC events** exist today (there are no events); when adding progress, coalesce to ~5 Hz on the engine side and keep the shell's `emit` (shell.rs:139) as a thin forwarder.

## Recommended shape (one design, reused by #1-#5, #7, #9)

- Suggested order: (1) raise/clear timeout mismatch + cancel token in Budget [S]; (2) job/progress plumbing [M]; (3) cleanup scan on the new walker [L]; (4) disk map [L, before its UI is built]; (5) issues per-source streaming [M]; (6) bench kill-on-cancel and sub-phase [M]; (7) the P2/P3 labels.

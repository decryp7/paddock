# Rust link time in the app crates (macOS arm64, debug)

Date: 2026-10-29. Question (user): can we cut Rust **link** time in the Paddock apps, and would stabby, abi_stable or a C
ABI help "just to save linking, not for plugins"? Measured on Debrief's and Dyno's app crates (`debrief-app`,
`dyno-app`) for a one-line change in the app crate, debug profile, macOS arm64. Windows is reasoned from documentation and
**not measured**.

Every number below is recorded with its conditions (rule 48) in
[Debrief's performance record](../../apps/debrief/docs/performance.md#2026-10-29-incremental-rebuild-and-link-time-docslink-time)
and [Dyno's](../../apps/dyno/docs/performance.md#2026-10-29-incremental-rebuild-and-link-time-docslink-time); this note
quotes medians from those blocks.

## Summary

- **Linking proper is small on macOS.** Apple's `ld` (ld-prime, `ld-27037.1`, Xcode 27.1) links the Debrief debug binary
  in 0.61 s and Dyno's in 0.21 s. Even with the extra cdylib link, real linker time is 14% (Debrief) and 18% (Dyno) of
  an incremental rebuild.
- **The biggest avoidable cost is not the linker but the Tauri template's `crate-type = ["staticlib", "cdylib",
  "rlib"]`.** Every build of the app library also writes a static archive of the whole dependency graph (1.0 GB for
  Debrief, 364 MB for Dyno) and links a cdylib nobody uses. Those exist only for Tauri's mobile targets ("The mobile
  interface of Tauri requires your project to output a shared library",
  [Tauri 2 migration guide](https://v2.tauri.app/start/migrate/from-tauri-1/)). No Paddock app targets mobile.
  `crate-type = ["rlib"]` cuts the incremental rebuild by **25% (Debrief, 5.88 s to 4.40 s) and 38% (Dyno, 1.91 s to
  1.19 s)**. The shipped `dist` binary is built from the same source with the same features, but it is **not
  byte-identical**: its `__text` differs by 1,664 bytes of 7.8 MB (0.02%; checked below). That is a decision for the user.
- **A Bevy-style dev-only `dylib` (option a) works and is the fastest**, 32% (Debrief) and 43% (Dyno) below today, but
  only 9% below the rlib-only change, and it needs rlib-only anyway (rustc refuses a staticlib with a dylib dependency).
  It brings real hazards: Debrief's mimalloc `#[global_allocator]` no longer covers the code in the dylib (two
  allocators in one process), the dylib's dependency list must mirror the app's, and on Windows a dylib of this size runs
  into the PE export limit. Not worth it for 0.1 to 0.4 s.
- **lld is slower than ld-prime on macOS** (1.6 to 1.7 times the link time) and cannot read the macOS 27 SDK at all.
  mold has no macOS support; sold is archived.
- **Debug info is already the cheap setting.** Both workspaces use `debug = "line-tables-only"` and the macOS default
  `split-debuginfo = "unpacked"` (verified in the rustc command line). Full debug info would cost +11% to +16%, no debug
  info would save only 5% to 7%.
- **stabby, abi_stable or a C ABI would save nothing beyond (a)**: they use the same dynamic-library boundary, add an
  FFI-safe interface layer that Tauri's generic API cannot cross, and target ABI stability, not build speed.
- **What remains is compiling the app crate itself**: about 3 s of Debrief's 4.4 s is rustc on the 76,500-line
  `debrief-app` library (incremental). Shrinking that means splitting the app crate, which is a separate decision.

**Recommendation:** (1) set `crate-type = ["rlib"]` in every app's `app/src-tauri/Cargo.toml` (Debrief, Dyno, Pitcrew,
Pitwall, Spotter): prepared as a separate `build:` commit on this branch. It cannot be limited to dev builds (cargo has
no per-profile crate type), so it also changes release builds slightly (faster, and not byte-identical); drop the commit
if release output must not change at all. (2) Keep Apple `ld` on macOS and `rust-lld` on
Windows (already the repo default). (3) Do not adopt the dylib feature, stabby, abi_stable or a C ABI for build speed.
Fallback, if a mobile target is ever added: restore the three crate types for that app only, or build the mobile
library with `cargo rustc --crate-type staticlib` in the mobile job.

## Method

- Worktree `docs/link-time` from `origin/main` cae1649f9, private target folders
  (`/Volumes/d7sst7/dev-targets/target/link-time-{debrief,dyno}`), `CARGO_BUILD_JOBS=2`, stable Rust 1.99.1 (LLVM 23.1.1),
  macOS 27.2, Mac mini M4 Pro (14 cores, 64 GB). The heavy cold builds ran through `heavy.sh`.
- **The change.** Each build appends or replaces a probe function at the end of the app crate's `lib.rs`
  (`pub fn __link_probe() -> u32 { N }` with a new `N`), then times `cargo build -p <app>`. This is the cheapest
  realistic edit: the app crate recompiles incrementally, then everything downstream (archive, cdylib, binary) is redone.
  The per-build costs measured here (archive, links) do not depend on the size of the edit.
- **Link time.** The target linker is a wrapper (`cc-timed.sh`) that runs `cc` and logs each link's duration. It picks
  the linker at run time from `LINKMODE`, so switching between `ld` and `lld` does not change cargo's fingerprint.
  The wrapper had to be set before the cold build: cargo fingerprints the linker, and setting it later rebuilt everything.
- **Phases.** `cargo build --timings` gave the duration of the library unit (incremental rustc plus staticlib plus cdylib)
  and of the binary unit (rustc on `main.rs` plus the link).
- **Interleaving.** 3 rounds; every round runs every configuration in turn, each as an uncounted warm-up build and then
  a measured one, so drift spreads over all configurations. 1-minute load 3.6 to 6.6 during the rounds (other agents
  were mostly idle); one heavy job (this one) at a time.
- **Configurations.** `base` (today: three crate types, `ld`), `rlib` (crate type rlib only), `dylib` (rlib only plus
  option a), each also with `-lld`; and `base` with the app crate's own debug info off (`dbg0`) or `full`, set through
  `--config profile.dev.package.<app>.debug=...` so the dependencies were not rebuilt.
- Synthetic: no data is read; the measured thing is the compiler.

## Options

### Crate type rlib only (not in the brief; the clear win)

- Tauri's template sets `crate-type = ["staticlib", "cdylib", "rlib"]` for iOS (staticlib) and Android (cdylib); a
  desktop `tauri build`/`tauri dev` only needs the rlib for the binary. Paddock has no `gen/android` or `gen/apple` and no
  script or workflow reads `libdebrief_app_lib.a/.dylib` (`git grep`, 2026-10-29). `#[cfg_attr(mobile,
  tauri::mobile_entry_point)]` in Debrief's `lib.rs` stays harmless.
- Release: the shipped binary is built from the rlib either way, but not byte-identically (see "Release identity").
- Cargo cannot make `crate-type` depend on the profile or a feature, so this is not a dev-only switch: it changes all
  profiles. (`cargo rustc --crate-type` overrides it per call, but `tauri dev` runs `cargo run`, so it does not help.)

### (a) Bevy-style dev-only dylib

- Built and measured: a `dyno-dylib`/`debrief-dylib` crate (`crate-type = ["dylib"]`, `pub use` of tauri, the plugins and
  the other dependencies), optional behind a `dynamic_linking` feature of the app crate, with
  `#[cfg(feature = "dynamic_linking")] use <app>_dylib;` in `lib.rs`, the pattern of
  [bevy_dylib](https://github.com/bevyengine/bevy/blob/main/crates/bevy_dylib/src/lib.rs). Cargo builds the dylib with
  `-C prefer-dynamic`, so the binary links `libstd-*.dylib` and the app dylib (`otool -L`); the Dyno binary shrinks from
  39 MB to 19 MB, Debrief's from 189 MB to 76 MB. Release builds are untouched (feature off).
- `tauri dev` works through `cargo run`, which puts `target/debug/deps` and the toolchain's library folder on the dynamic
  library path; `cargo test -p dyno-app --features dynamic_linking --lib` loaded and ran the library (2 tests passed).
  I did not start the app window (ER-14).
- Findings that make it a poor trade here:
  - **It requires the rlib-only change first**: with the template crate types rustc stops with "crate `dyno_dylib`
    required to be available in rlib format, but was not found in this form" (the staticlib). Its gain over rlib-only is
    0.41 s (Debrief) and 0.11 s (Dyno), 9%.
  - **Allocator split (Debrief).** With mimalloc in the dylib the binary did not link (`_mi_malloc_aligned` and friends
    undefined: a Rust dylib does not re-export the C symbols of a static library). With `debrief-alloc` kept out of the
    dylib it links, but the code in the dylib and in `libstd` then resolves `__rust_alloc` to the default allocator
    exported by `libstd-*.dylib` while the binary's own code uses mimalloc (`nm -m`: the binary's `__rust_alloc` is
    private). Memory allocated on one side and freed on the other is undefined behaviour. The feature would have to
    switch the global allocator off, so dev builds would measure a different allocator than the release.
  - The dylib's dependency list must mirror the app's (features included), by hand, in every app.
  - Windows: a PE/COFF DLL exports at most 65,535 symbols; Bevy's own setup page warns of "too many exported symbols"
    without optimisation ([Bevy setup](https://bevy.org/learn/quick-start/getting-started/setup/)). Debrief's dependency
    graph (about 650 packages in `cargo tree`) would likely exceed it. Not measured.
  - The bin link is already only 0.6 s; the dylib cannot save more than that.

### (b) Another linker on macOS

- **lld** (the toolchain's `rust-lld`, `gcc-ld/ld64.lld`, LLD 23.1.1): slower than ld-prime in every configuration
  (Debrief binary 1.04 s against 0.61 s, Dyno 0.34 s against 0.21 s). It also **cannot link against the macOS 27 SDK**:
  "could not load TAPI file at .../MacOSX27.0.sdk/usr/lib/libSystem.tbd: malformed file" (the SDK's `.tbd` lists an
  `arm64e.x1` target LLD 23 does not know). The measurements used the Command Line Tools' MacOSX26.5 SDK for lld only.
  Bevy's setup page says the same: "On MacOS, the default system linker `ld-prime` is faster than LLD."
- **mold**: MIT ([repository](https://github.com/rui314/mold)); its README and prebuilt binaries cover Linux and FreeBSD
  only, no Mach-O support is advertised. Not available on this Mac.
- **sold** (mold's macOS fork): MIT, **archived on 2024-11-25**; its README: "Xcode 15 or later are shipped with Apple's
  new faster linker. I recommend using that instead." ([repository](https://github.com/bluewhalesystems/sold)).
- Verdict: keep Apple's `ld`. (Linux: rust-lld is the default on x86_64 since Rust 1.90, and mold helps on aarch64
  Linux; already in [dev-setup.md](../dev-setup.md).)

### (c) Debug info

- Already done: both workspaces set `[profile.dev] debug = "line-tables-only"`, and cargo's macOS default
  `split-debuginfo = "unpacked"` applies ("The default value for this option is `unpacked` on macOS for profiles that have
  debug information otherwise enabled", [Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html)); the
  rustc command line shows `-C debuginfo=line-tables-only -C split-debuginfo=unpacked`. With `unpacked` the linker only
  records where the DWARF is, so debug info barely changes link time: the binary link stayed at 0.61 s (Debrief) for
  `false`, `line-tables-only` and `full`. The differences in the table come from rustc emitting less or more debug info.
- `split-debuginfo = "packed"` would run `dsymutil` on every link: not measured, avoid.

### (d) stabby, abi_stable, C ABI cdylibs

- They put a stable ABI between separately built Rust libraries: abi_stable is "For Rust-to-Rust ffi, with a focus on
  creating libraries loaded at program startup, and with load-time type-checking"
  ([abi_stable](https://github.com/rodrimati1992/abi_stable_crates), MIT or Apache-2.0, last release 0.11.3 on
  2023-10-12); stabby is "A Stable ABI for Rust with compact sum-types" and warns that "Compilation times suffer from
  `#[repr(stabby)]` enums" ([stabby](https://github.com/ZettaScaleLabs/stabby), EPL-2.0 OR Apache-2.0, crates.io
  2026-07). Licences: crates.io API, 2026-10-29.
- For link time they could only do what (a) does (move code behind a dynamic-library boundary), with more work: every
  type crossing the boundary must be FFI-safe (`RString`, `RVec`, `#[sabi_trait]`, `#[stabby::stabby]`, or `extern "C"`
  with raw pointers), and Tauri's API (generic `AppHandle<R>`, `Builder`, closures, `serde` types) cannot be wrapped
  that way. (a) gets the same dynamic linking with ordinary Rust types, because a debug build always uses one compiler.
- They also cannot touch the cost that remains after the rlib change, rustc on the app crate.
- Debrief already rejected in-process native plugin ABIs for plugins ([ADR 0004](../../apps/debrief/docs/adr/0004-stable-plugin-abi.md),
  superseded by ADR 0017's out-of-process plugins). Verdict: no, for build speed.

## Windows (not measured)

- Already done: every workspace links `x86_64-pc-windows-msvc` with `rust-lld.exe` (lld-link) since e368cda84
  (2026-10-25), locally, in CI and in releases (`.cargo/config.toml`, [dev-setup.md](../dev-setup.md)). There was no
  recorded link.exe/lld-link comparison then, and the Windows VM now only runs the CI runner, so none was taken here.
- Secondary sources only: the LLD project reports large speedups over GNU linkers but does not compare with link.exe
  ([lld.llvm.org](https://lld.llvm.org/)); a Firefox developer reported a 20% faster Windows build from replacing
  link.exe with lld-link ([bug 1535177](https://bugzilla.mozilla.org/show_bug.cgi?id=1535177)); making rust-lld the
  default on x64 MSVC is still an open tracking issue ([rust#71520](https://github.com/rust-lang/rust/issues/71520)).
  Unverified here.
- The rlib-only change should help Windows at least as much as macOS: the staticlib becomes a large `.lib` archive and
  the cdylib a full DLL link with lld-link on every build. Expected, not measured; the Windows CI job timings after the
  change will show it.
- The dylib option is worse on Windows (export limit above, `std-*.dll` must be on `PATH` outside `cargo run`).

## Release identity

Dyno, `cargo build -p dyno-app --profile dist` (thin LTO, one codegen unit, strip), Apple `ld`, private target folder,
run through `heavy.sh` at load 8 to 44 (other agents were building):

| Crate types | `dyno-app` SHA-256 | Size | `__text` |
|---|---|---|---|
| staticlib + cdylib + rlib (today) | `af25a650...2b366d70` | 11,205,808 B | 7,776,740 B |
| rlib only | `13b39130...4a5d1` | 11,205,824 B | 7,778,404 B |
| staticlib + cdylib + rlib again | `af25a650...2b366d70` (cargo reused the first build's artifact) | | |

- The binaries differ in code (`__text` +1,664 bytes, `__eh_frame` and `__gcc_except_tab` a few hundred bytes), not in
  what they contain: same sections, same exported symbol (`nm -U`: one), no string from a path or a crate type.
- The library rlib also differs (44.8 MB with the template crate types, 36.6 MB rlib only). Likely cause, **not
  verified**: when the rlib only feeds an LTO-ed binary, cargo asks rustc for bitcode only, and with a staticlib or cdylib
  in the list it needs object code and bitcode, so thin LTO starts from a different input and inlines slightly
  differently. Rlib only is cargo's normal path for a binary-only package.
- Not checked: whether a rebuild with identical settings is itself byte-identical (the third row was a cache hit).
- Release build time was not compared (the first build included all dependencies).

## Risks

- Release codegen changes slightly (above); it should get the usual release checks (the app's smoke and start-up
  tests) like any compiler or dependency change.
- A future mobile target needs the staticlib/cdylib back for that app (one line).
- Some tool might expect `lib<app>_app_lib.dylib` in the target folder; none in the repo does (`git grep`).
- All numbers are from one machine at load 3.6 to 6.6; read them as an A/B within one session.

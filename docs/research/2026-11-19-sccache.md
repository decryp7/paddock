## 1. What the non-cacheable calls are

**Measured** (the shared server on port 4226, read with `--show-stats` only; nothing was restarted or reset), 2026-11-19 05:58

| Non-cacheable calls | 14,991 | 100% |
| `incremental` | 8,452 | 56% |
| `crate-type (bin)` | 2,324 | 16% |
| `multiple input files` | 1,455 | 10% |
| `missing input` | 926 | 6% |

| `missing output_dir` | 110 | 1% |

Cache size 4 GiB of 60 GiB. Average compile 0.403 s, average hit read 0.003 s, 0 read or write errors, 159 compile failures.

What each reason is (read in `src/compiler/rust.rs` at v0.19.0 unless marked):

- **`incremental` (56%)**: `-C incremental=...` is a hard `cannot_cache!("incremental")` (rust.rs line 1468). Cargo passes it for
  the workspace's own crates and path dependencies in the dev and test profiles (`incremental = true` is the default there; cargo
  book, profiles). These are the Paddock crates (`paddock-*`, the app crates): 11 of 255 packages in `tools/paddock-dev`, 13 to 60
  of 618 to 902 in the app workspaces (counted from each `Cargo.lock`: packages without a `source`).
- **`crate-type (bin)` (16%) and `crate-type (proc-macro)` (6%)**: binaries, test binaries and proc-macros are never cached
  (`docs/Rust.md`: "crates that invoke the system linker"). Every `cargo test` and nextest target is a bin.
- **`multiple input files` (10%)**: inferred, not measured. The parser skips a first raw argument only when it is literally `rustc`
  (rust.rs lines 1499 to 1505, "likely called via clippy-driver"); with clippy as the workspace wrapper the first argument is rustc's
  full path, so it and the source file count as two inputs. The server log's one warning (`Failed to initialise RlibDepDecoder ...
  "clippy 0.1.100"`) shows clippy-driver does reach sccache. Clippy runs only on workspace crates, so these are the same crates as
  `incremental`. A `SCCACHE_LOG=debug` run on a private server would confirm it; it was not run (paused, see section 6).
- **`-` (5%) and `missing input` (6%)**: `-` is a `TooHardFlag` (line 1285): cargo's per-invocation target-information probe
  (`rustc - --crate-name ___ --print=...`) reads stdin. `missing input` is inferred to be the other probes without a source file.
  Both cost milliseconds; they are noise in the rate, not lost work.

**Reading:** the 61% is of what sccache can cache, and almost everything it refuses is what its design says it never caches. The
addressable part is the workspace's own crates (`incremental` plus most of `multiple input files`, about two thirds of the
refusals). Third-party crates already hit about 80% across worktrees (the 2026-11-16 blocks above).

**A side finding: the shared server's error log is mostly noise.** `~/.paddock-dev/sccache-run/sccache.log` held 495 lines, of which
494 were two lines per `--start-server` that found the server running (`failed to start server: Address already in use`, 247 times
between 2026-11-17 03:22 and 2026-11-18 21:57). `local_sccache::prepare` starts first and treats "Address in use" as running
(`already_running`, `tools/paddock-dev/src/local_sccache.rs`), and the server writes the failure to the same `SCCACHE_ERROR_LOG` that
every warning names (ER-27: a real error is hard to find among them). See WP-3.

## 2. Incremental off for agents and gates

**What the key says** (read, rust.rs `generate_hash_key` at v0.19.0, about lines 1840 to 1870): the key holds every `CARGO_*`
variable except four, which includes `CARGO_MANIFEST_DIR` and `CARGO_PKG_*`, and the working folder. A workspace or path crate in
worktree B therefore never matches worktree A's entry. Turning incremental off makes those crates cacheable, but in 0.19.0 a hit
needs the same crate, same source, same checkout path and same flags again: a second build folder in the same worktree (a gate's
folder next to the agent's own, a pruned folder, the xwin folder does not count as it is another target), or going back to an
earlier source state.

**Where the push gates build** (read, `tools/paddock-dev/src/pre_push/mod.rs` `work_base`, `Detached::new`): a push that is not
HEAD of a clean tree is checked in a throw-away worktree `<worktree root>/pre-push/trees/<pid>-<start>-<sha>` (a new path every run),
and its builds go to kept folders `<worktree root>/pre-push/targets/<workspace>`, shared by every agent's pushes.

**Measured, the gates' kept folders on 2026-11-19** (`du -sk`, read only):

| Kept folder | Incremental state | Whole folder | Incremental crate folders |
|---|---|---|---|
| apps-dyno | 11.1 GiB | 17.8 GiB | 1,755 |
| apps-debrief | 9.6 GiB | 11.8 GiB | 1,307 |
| crates | 5.6 GiB | 8.2 GiB | 1,123 |
| apps-pitwall | 4.2 GiB | 7.0 GiB | 516 |
| tools-paddock-dev | 1.8 GiB | 2.2 GiB | 144 |
| the other seven | 1.5 GiB | 7.2 GiB | 407 |

In `apps-dyno/debug/incremental`, 702 of 1,129 crate folders were last written on 2026-11-13, 140 on 11-14, 140 on 11-17 and 147 on
11-18: cargo starts a new folder for every new unit hash (a dependency, feature or profile change) and never removes the old ones,
and nothing caps these folders (`./dev disk` and `ci_host/prune.rs` do not look at `pre-push/targets`; `prune-folder` is CI's). Most of
the 34 GiB is state no build will read again. The recently written folders show that the current hashes are reused from push to push,
so incremental does save gate time on consecutive pushes: how much is the measurement below.

**Measured:** PENDING (section 6).

**Cost side, what incremental buys** (2026-10-29 link-time note, measured): a one-line change in an app crate rebuilds in 1.2 to 5.9 s
(Dyno, Debrief, debug, macOS). Without incremental rustc recompiles the whole edited crate and every workspace crate that depends on
it from scratch.

## 3. A shared S3 backend (RustFS)

**Measured 2026-11-19, from this Mac:** RustFS at 172.16.1.220:15000 answers (`/minio/health/live` 200 in 12 to 78 ms after the
first, 1.4 s cold; ICMP round trip 1.8 to 7.1 ms, average 3.2 ms, 5 of 5). The credentials file exists with mode 600 (only the
variable names were read). The Mac CI runners are launch agents on this same Mac (`~/Library/LaunchAgents`, three
`gitea-runner` agents), so they reach it the same way. The Linux and Windows runners are not on this Mac (no containers running
here); whether they reach 172.16.1.220 is **not measured** (it needs a job on them, the user's runner config).

**Measured 2026-11-16** (benchmarks block above): the same 80 to 83% hits on RustFS as on the local disk, and a warm build about
2 to 5 s slower (37 against 32 s, 48 against 46 s); the first series had a write error on every compile because sccache 0.19.0
latches a failed startup write check (lessons.md, fixed in the tool).

**History that weighs on it** (read): CI had a shared Dragonfly (Redis) backend; it filled up and the Mac job's server failed to
start, which failed every rustc call, so CI moved to the local disk on 2026-10-25 (commit 1383e9898, `setup-rust` input
`sccache-backend` default `local`, `ci_setup_rust.rs` `default_value = "local"`). The user decided on 2026-10-28 against a shared
backend and on 2026-11-17 that CI keeps its own per-slot caches. docs/dev-setup.md "Shared build cache" still describes Redis as in
use with default `auto`; that text is stale (fixed on this branch, WP-1).

## 5. Cheaper compiles

- **Linker.** macOS keeps Apple's ld-prime: linking is 14 to 18% of an incremental app rebuild (measured, 2026-10-29 link-time note),
  the perf book says an alternative linker is not needed on Mac (<https://nnethercote.github.io/perf-book/build-configuration.html>),
  and sold (mold for macOS) was archived on 2024-11-25 in favour of Apple's linker (<https://github.com/bluewhalesystems/sold>).
  Windows already links with `rust-lld.exe` (root `.cargo/config.toml`). x86_64 Linux uses rust-lld by default since Rust 1.90
  (<https://blog.rust-lang.org/2025/09/18/Rust-1.90.0/>). Nothing to do.
- **Debug info.** The cargo book's build-performance guide recommends `debug = "line-tables-only"` and `debug = false` for
  dependencies (<https://doc.rust-lang.org/cargo/guide/build-performance.html>). `crates/` does both; the five app workspaces set
  line tables but keep line tables for dependencies too; **`tools/paddock-dev` sets neither**, so every agent's and gate's build of
  `./dev` writes full debug info. Measured: PENDING (section 6).
- **Cranelift, `-Zshare-generics`, the parallel front end (`-Zthreads`)**: nightly only (cargo build-performance guide; 2026 goals
  <https://goals.rust-lang.org/2026/improve-cg_clif-performance.html>, <https://goals.rust-lang.org/2026/parallel-front-end.html>).
  Out while the toolchain is pinned to stable 1.100.0 (AGENTS.md, "Rust version").

## 7. Recommendation

Ranked:

1. **Keep sccache on the local disk for agents, and tune around it (common practice; option A plus F).** It already gives about
   80% hits on third-party crates across worktrees, which is the part a cache can give in 0.19.0. Its refusals are its documented
   limits (section 1), not a misconfiguration.
2. **Fix what the investigation found, at once** (WP-1 to WP-3): the stale Redis text, the gates' unbounded incremental state, and
   the error-log noise.
3. **Decide incremental for the push gates on the measurement (WP-4).** Turning it off would also stop the 34 GiB of state from
   building up. Agents' own worktree builds keep incremental: their edit loops use it. In 0.19.0, turning it off gives a workspace
   crate a cache hit only at the same path, so a new worktree gains nothing (section 2, read from the key).
4. **Revisit once an sccache release contains #2918 and #3022 (WP-6).** With `SCCACHE_BASEDIRS` over the worktree root, incremental
   off for the gates would let the workspace crates hit across worktrees. This is the only change that reaches the 56%.
5. **No S3 or Redis backend, for now (B).** On one Mac it adds nothing over the local disk, and it was 2 to 5 s slower when warm. The
   user declined a shared backend twice (2026-10-28, 2026-11-17), and the Redis attempt failed CI jobs (1383e9898). It would only
   pay for CI runners on other machines, and their reachability is not measured.

Fallback: today's setup. Nothing is lost if the work packages wait.

Not recommended: Bazel or Buck2 (E): agent-weeks of build files for a one-developer Cargo and Tauri repo, far beyond common practice.
A shared build-dir (C+): undocumented for cross-workspace use, contended locks, and the cargo cross-workspace cache is not on stable.
Cranelift and the other nightly flags: the toolchain is pinned to stable.

Risks:

- The unpruned gate folders keep growing on the dev disk until WP-2 lands (54 GiB today).
- An sccache release with #2918 may change key behaviour (a one-time miss for Windows env-deps, by the PR author).
- kache's claims are its vendor's.

## 8. WP-8: CI's sccache on RustFS

**Design, against the Redis failure** (commit 1383e9898, 2026-10-25: the shared Dragonfly filled up, the Mac job's server failed to
start, and every rustc call failed):

- **The job's local disk stays level 0.** `s3` means sccache's multi-level chain `disk,s3` with
  `SCCACHE_MULTILEVEL_WRITE_ERROR_POLICY=l0`. A compile is stored when the local disk stores it. An S3 write or a failed S3 startup
  check is logged, never fatal, and does not latch the server read-only (sccache v0.19.0 `docs/MultiLevel.md`: "With `l0`, L0 must
  pass its startup check while unavailable slower levels are best-effort"). Hits are never worse than today.
- **Fail-open before the start.** `./dev ci setup-rust` uses S3 only when the bucket, the endpoint and both keys are in the job's
  environment and the endpoint accepts a TCP connect within 3 s (`S3_CONNECT`: LAN round trip 1.8 to 7.1 ms). Otherwise it prints
  one `::warning::` with the reason and uses the local disk alone. As before, the wrapper is set only once the server answers.
- **One key prefix per runner class** (`paddock-ci/<RUNNER_OS>-<arch>`), so one OS's objects can be expired or dropped alone. The
  agents' local cache keeps its own prefix and never shares CI's entries: `CARGO_INCREMENTAL=0` is part of CI's key (lessons.md,
  2026-11-17).
- **Size: the store's job.** sccache never evicts from S3. The bucket keeps its 50 GiB quota, and the user adds a lifecycle rule that
  expires objects 14 days after they are written. RustFS documents `rc bucket lifecycle rule add <alias>/<bucket> --prefix <p>
  --expiry-days <n>` (<https://docs.rustfs.com/administration/data/lifecycle-management>, undated; expiry runs in the background
  scanner, not at once). A full bucket then means failed S3 writes, which `l0` ignores.
- **Credentials as runner secrets:** in each runner's own environment file, never in the repository, a workflow file or a log. The
  step masks both values (`::add-mask::`) and passes them only to the sccache server it starts, never to `$GITHUB_ENV`. A server that a
  later client starts by itself lacks them, and then serves from the local disk alone.
- **The switch:** the `setup-rust` input `sccache-backend` takes its default from the Gitea variable `PADDOCK_CI_SCCACHE_BACKEND`, and
  is `local` when that is unset. ER-41: it stays `local` until the first green run on one runner class, recorded by run id.

**Risk of runner-wide keys:** every step of every job on that runner sees them (ER-47: children inherit the environment), test code
included. The key is bound to `paddock-ci/*` of one bucket, so the worst a leak does is fill or poison the CI cache prefix. Expiry and
a key rotation clear it, and `l0` keeps builds on the local disk while that happens. The cheaper common-practice alternative is the one
GitHub documents: the keys as repository secrets, passed only to the setup step (`env: AWS_ACCESS_KEY_ID: ${{ secrets... }}` in each
calling workflow, because a composite action cannot read `secrets`). That costs a line in every workflow that uses `setup-rust`.

**Reach (step 1).** `diag/sccache-s3-reach` (not for landing) holds a probe workflow: three unauthenticated health checks per runner
class, no credentials. Its result: PENDING. It is dispatched with `./dev ci dispatch sccache-s3-reach.yml --trial diag/sccache-s3-reach`
when the runners are free.

**What the integrator changes in `.gitea/`** (a shared integration point, so not on this branch):

1. In `.gitea/actions/setup-rust/action.yml`, input `sccache-backend`: `default: ${{ vars.PADDOCK_CI_SCCACHE_BACKEND || 'local' }}`. The
   shell path for release and tag runs accepts `s3` as `local`, with a notice, until the release lane runs `./dev ci setup-rust`.
2. In the step that runs `./dev ci setup-rust`, pass nothing new: the runner's environment already carries the variables.
3. In `.gitea/actions/README.md`, the `setup-rust` row: "the local disk by default (a Redis or S3 second level only when chosen)",
   replacing "shared Redis backend on every OS" (stale since 1383e9898).

**What the user applies (runner and RustFS config):**

1. RustFS console (port 15001): create a policy `sccache-paddock-ci-rw` (read and write on `sccache-paddock/paddock-ci/*` only), and one
   access key per runner class bound to it. The agents' key stays separate.
2. RustFS lifecycle: `rc bucket lifecycle rule add <alias>/sccache-paddock --prefix paddock-ci/ --expiry-days 14`. Check it with
   `rc bucket lifecycle rule list <alias>/sccache-paddock`.
3. On each runner, in the act_runner environment file (`runner.env_file` in its config.yaml, mode 600, outside any checkout):
   `AWS_ACCESS_KEY_ID=...`, `AWS_SECRET_ACCESS_KEY=...`, `PADDOCK_SCCACHE_S3_BUCKET=sccache-paddock`,
   `PADDOCK_SCCACHE_S3_ENDPOINT=172.16.1.220:15000`. act_runner gives these "extra environment variables to run jobs" to every job,
   container jobs included (`runner.env_file` and `runner.envs` in act_runner's `config.example.yaml`, gitea/act_runner main, read
   2026-11-19). Then restart that runner while it is idle.
4. Gitea repository variable `PADDOCK_CI_SCCACHE_BACKEND=s3`, first for one trial run, then for good after it is green (ER-41).
5. To turn it off: delete the variable. Every job is back on its local disk at the next run.

**Not measured:** whether the Linux and Windows runners reach the store (the probe); the hit rate CI gets from S3 across slots and

# CI runs of the monorepo: where the runner hours go, and what to change

Date: 2026-10-29. Author: researcher agent (branch `ci/optimise-runs`). Status: final for the measurement; the proposals
marked **approval** wait for the user.
Scope: every Gitea Actions run of `decryp7/paddock` created in the 48 hours up to 2026-10-29 15:08:41 +08:00 (596 runs,
3,772 jobs that started), read through the runs and jobs API, plus the logs of 102 failed and 48 green jobs. Nothing was
dispatched. Results block (rule 48): [benchmarks.md, 2026-10-29 CI runs](../benchmarks.md#2026-10-29-ci-runs-of-the-monorepo-48-hours-cioptimise-runs).
Tool: [2026-10-29-ci-runs.mjs](2026-10-29-ci-runs.mjs) (`pull`, then `table`).

## Summary

- **Runner hours: 188 in 48 h** (Linux 119, Windows 43, macOS 26). Since the four app moves onto the shared kit
  (2026-10-28 14:00) the rate is 103 h/day: Linux 67, **Windows 22.2 (92 % of its one slot)**, macOS 14.2. Windows is the
  bottleneck; Linux is the queue for every plan job (ci.yml's plan waited a median 11 min, p90 47 min, for a slot).
- **Most of it is spent on runs that cannot pass or will not finish:** 122 h (65 %) in failed runs, 28 h (15 %) in
  cancelled runs, 36 h (19 %) in green runs. Main has had no green ci.yml push run since run 6502 (2026-10-28 07:10);
  43 of 55 main push runs of ci.yml and 41 of 55 of debrief.yml were cancelled by the next push (40 pushes a day).
- **Implemented (safe, mechanical):** (1) the Windows checkout is no longer cloned again every job, expected about
  2.3 h/day of the Windows runner (estimate, to be measured); (2) the planner finds the last green ci.yml run through the
  workflow's own run list, so a push to main no longer tests everything once 200 runs of other workflows have passed.
- **Needs the user:** get main green and stop cancelling main runs (10.7 h/day burnt in cancelled main runs), stop Debrief's
  installers on every main push, drop the four `*-release.yml` push triggers and fix their silently skipped nightly
  installers, the WebKit job on every main push, and two server/runner settings for lost tasks.

**Where Windows time goes** (42.6 h of Windows jobs that passed or failed): app-gates 19 %, `actions/checkout` 18 %,
`stable-workspace` 16 %, installers 11 %, crate tests 10 %. The checkout step fetches (`--depth=1`, about 25 s) and writes
all 11,386 files (about 35 s); `stable-workspace` then took a median 49 s (p90 76 s, 200 steps a day). On macOS it takes
1 s. Cause, from the action and a log (job of 2026-10-29 06:55 UTC): the step ran `rm -rf "$stable" && mv "$ws" "$stable"`;
the move fails on Windows (act holds the work folder), but the kept clone had already been deleted, so the fallback
cloned the repository and checked out every file again, every job. Fixed on this branch.

**Plan jobs that fail with empty logs (runs 6988, 7010 and six more).** Eight jobs on d-gtr9 in 48 h (6 plan jobs, one
conformance job, one benchmark job) have the same signature: started, then no log line ever (`unable to open task logs`),
every step stamped `failure` at the same second, 10 min 46 s to 14 min 27 s after the start, always at a minute
ending in 2 or 7 and 34 s. That is Gitea's zombie-task cleanup: a task in the running state that the runner has not
updated for `ZOMBIE_TASK_TIMEOUT` (default 10m) is stopped by the `stop_zombie_tasks` cron (default `@every 5m`), so it
fails 10–15 min after the start. The server had assigned the task; the runner never ran it. In 4 of the 8 cases 2–3
other plan jobs started on the same runner within the same minute (each push to main starts six workflows, each with a
plan job). The runner-side reason is **not verified** (the runner's own log on d-gtr9 was not read). The likely one: act_runner
polls `FetchTask` with a 5 s timeout; if the server assigns a task but the reply misses the timeout, the runner never
learns of it (Forgejo fixed exactly this with a request key, PR 11401; see Sources).

**Planner fallback to everything on main.** Run 6941's plan log (spotter-release.yml, 2026-10-29 03:47 UTC): `base: no
green ci run on main that HEAD contains: everything`. The last green ci.yml push run (6502) was 269 runs back; the lookup
read 4 pages of 50 runs of every workflow on main (six per push). The server's per-workflow endpoint
`/actions/workflows/ci.yml/runs?branch=main&event=push&status=success` returns 6502 first (checked 2026-10-29). Fixed on
this branch. Even with the fix, a red main keeps the base at the last green commit, so each push still tests everything
changed since then.

**Release workflows on push to main never build installers.** In all 104 green push runs and all 6 nightly runs of the four
`*-release.yml`, `gates` was skipped (correct: no tag) and `installers + release` was skipped too, although the plan said
the app was affected (run 6941: `spotter: affected (rust, ui)`). With `gates: true` (dispatch), installers ran (runs 6612,
6617, 6548, 6495, 6482, 6463). So the documented "installers on push to main" and "nightly installers" never run: the
release job's `!cancelled() && ... needs.gates.result == 'skipped'` condition does not save it from a skipped need on this
Gitea (version string 28.2.0). The mechanism is observed, the server-side reason not read. Each push still starts four plan
jobs (n = 131 started in 48 h, 24 s median, plus the queue).

**Duplication.** Debrief is not yet on the kit: debrief.yml runs its own lint, tests, e2e, installers and smoke on every

during a long day pushes branch runs back.

## Decisions (user, 2026-10-29)

- **Main lands in batches** (the steward merges a batch, then one main run). The main-push `concurrency` of ci.yml and
  debrief.yml stays as it is: group `workflow-ref-event`, `cancel-in-progress: true` (newest wins). The data shows no setting
  that makes things worse: the 43 and 41 cancelled main runs came from about 40 pushes a day landing faster than a run
  finishes, not from the setting, and a cancelled run loses no coverage, because the next push diffs from the last *green*
  run (with the planner fix on this branch it finds it). With one push per batch, runs finish, main gets green runs and the
  base narrows. nightly.yml already queues instead of cancelling (`cancel-in-progress: false`), which is right for a
  schedule. The four `<app>-release.yml` no longer run on a push to main, so their main-push groups no longer apply.
- Proposal 4 (Debrief) and proposal 6 (release workflows) are approved and done on this branch; see the commits.

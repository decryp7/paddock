`apps/debrief/crates/debrief-core/parsers/samples/billing.log`, `billing.xml` and `u_ex261014.log` (ADR 0021's list of
deliberate CRLF inputs).

**What the proposed default does to a CRLF blob (measured, revision 2).** A synthetic repository (git 2.56.0,
`core.autocrlf=false`): a file committed with CRLF under `*.txt -text`, then `.gitattributes` changed to the proposed
`* text=auto eol=lf`, then a fresh clone. `git ls-files --eol` shows `i/crlf w/crlf attr/text=auto eol=lf`; `git status`
is **clean** (git leaves a blob that already holds CRLF alone under `text=auto`); the bytes on disk stay CRLF; and `git
add --renormalize .` rewrites it to LF (`f.txt | 4 ++--`). So under the default a CRLF input is not damaged by a
checkout, but the next renormalise converts it silently: it must be `-text` first. (Revision 1 measured a different
attribute, `text eol=lf` without `auto`; there the fresh clone already showed the file as modified.) A further probe: a
CRLF file **added** under `* text=auto` is stored as LF at once (`i/lf w/crlf`), so new CRLF fixtures need their `-text`
line before they are committed.

## Pattern

**A test compares bytes it reads from a checked-out text file with bytes the program produces, and the checkout
changed the line ends.** The file's attributes decide this, not the file's folder name, so a policy written as a list
of folder names misses each new place a test reads from.

**Invariant.** Every tracked file resolves to exactly one of: binary or `-text` (byte-exact), `text eol=lf`, or `text
eol=crlf` for a declared Windows type. No tracked text file is left to the checkout's `core.autocrlf`.

## Change

1. **One default line (D-L1).** The root `.gitattributes` first line becomes `* text=auto eol=lf`. Kept below it, in
   this order: the `-text` lines (byte-exact inputs; plus ADR 0021 §4's `**/samples/** -text` and `**/testdata/**
   -text`), the binary lines, and the CRLF types `*.cmd text eol=crlf` and `*.bat text eol=crlf` last (later lines win).
   The CRLF type list is the one C38g (b) accepts; WP-L0 adds any type it finds a Windows tool needs, in both places.
   The narrow `eol=lf` lines of incidents 1 to 5 become redundant and go. `templates/repo/.gitattributes` and the seven
   app files carry the same default (C28 syncs the app files); `apps/debrief/.gitattributes` keeps its `-text` lines.
2. **CRLF inputs are `-text` before the default changes.** The three `text=auto` CRLF samples get `-text` (or their
   folder does, through `**/samples/** -text`). The landing checks itself: after the change, `git add --renormalize .`
   on a clean checkout changes nothing (`git status --porcelain` empty); WP-L1 records the command and its empty output.
3. **C38g, built now, over every tracked file (D-L2).** In the RT-5 Rust check host: `git ls-files -z` piped to `git
   check-attr --stdin -z text eol` once (one process, every file); a finding for (a) a file whose `text` is `set` or
   `auto` with `eol` unspecified, (b) `eol=crlf` on a type not in the declared list (`*.cmd`, `*.bat`), and (c) a blob
   stored with CRLF whose `text` is not unset (it would show as modified and be rewritten by a renormalise). Nested
   `.gitattributes` files are included because `check-attr` reads them. **Positive controls (ER-33):** a fixture tree
   with a `* text=auto` line alone and one text file (finding a), a `*.txt text eol=crlf` line (finding b), a committed
   CRLF blob under `text` (finding c), and the fixed tree (no finding).
4. **ADR 0087's line-ends control changes.** §4's canary asserts that "the sources arrived with CI's line ends" by
   reading a checked-in fixture and expecting `\r\n`. With this default every text file arrives with LF on Windows too,
   so that control would fail. It becomes two reads: a canary fixture **`crlf-canary.cmd`** (a declared CRLF type, so
   C38g (b) accepts it without an exception) must arrive with `\r\n`, and an ordinary text file must arrive with `\n`;
   together they show the attributes were applied on the guest.
   ADR 0087 §1.3's concern about `include_str!` baking the host's LF bytes no longer differs from the guest's checkout.

5. **Windows CRLF parsing keeps its coverage only through `-text` fixtures.** Today some parser tests may see CRLF input
   on the Windows legs only because the checkout converted an LF fixture; under the default they see LF on every OS.
   WP-L0 lists the parsers whose tests read checked-out text fixtures (Debrief's parsers and plugins first) and, for
   each that must handle CRLF, a `-text` CRLF fixture or a test that builds CRLF input in memory, so the coverage does
   not silently disappear.
6. **Binary-file risk goes down.** A binary that `text=auto` misdetects as text is stored with LF normalisation either
   way, but today a Windows checkout with `core.autocrlf=true` would also rewrite its LF bytes as CRLF; with `eol=lf`
   the checkout writes the stored bytes unchanged.

## What this does not cover

- Line ends inside generated output (a program that writes CRLF on Windows on purpose): tests compare through
  `testkit::text` (ADR 0021 §1) where the product's output is platform-dependent.
- TypeScript and Angular files: the default covers them; no separate rule.
- Files outside git (downloads, caches).

## Release impact (ER-31)

Shipped text files (notices, plists, Linux packaging, `.ps1` scripts in installers) are LF in the repository already
(`text=auto` stores LF) and become LF in Windows checkouts too. Windows reads LF in `.ps1`, `.json`, `.toml`, `.md` and
`.nsi` (**unverified here** for the NSIS templates of `tauri-bundle.sh`); WP-L0 lists every text type a Windows build
step or installer reads and declares any that needs CRLF. A release build runs on the CI Windows runner, so rule 54's
installer build before landing covers it.

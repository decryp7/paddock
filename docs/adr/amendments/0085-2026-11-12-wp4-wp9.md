  `origin/docs/adr-0085-release-cache-isolation` (`3a49d49a1`). It records how the minimum the user chose on 2026-11-12

  and is merged into the ADR's text when that branch lands. Revision 2 (same day) answers the first security review of
  `39ff9742a` (three P1s, seven P2s).
- Related: ADR 0085 §4 items 1, 5 and 6, D7, D9, D10, WP-4, WP-9; the amendment `0085-2026-11-10-rust-tool.md` (decision 7:
  `verify --tauri-pins`); Dyno 1.1.1 plan WP-2 and WP-17; rule 78.

## WP-9: the tools folder

1. **The ADR's folder is used: `<build folder>/.tauri`, through `useLocalToolsDir`.** Dyno WP-2 (`a3f3a54aa`) had put
   linuxdeploy and AppRun in the dirs cache folder (`~/.cache/tauri`). Moving them was low-risk, so the ADR is followed:
   `tauri-bundle.sh` (and Debrief's bundle step) pass `--config '{"bundle":{"useLocalToolsDir":true}}'` to every NSIS and
   AppImage build, and tauri-cli 2.12.3 then hands the bundler cargo's `target_directory` (`src/interface/mod.rs:79-83`),
   which the bundler joins with `.tauri` (tauri-bundler 2.10.3 `linuxdeploy.rs:45-50`, `nsis/mod.rs:82-85`).
   `conformance/ci/tauri-tools.mjs` asks `cargo metadata --no-deps` in `src-tauri` (where tauri-cli asks, so `.cargo/ci.toml`
   applies) and fills that folder. Why low-risk: the path is cargo's own answer, not a guess from `target/`; a Linux container
   gets a fresh folder every run; on a host runner the folder is in the kept build folder, so `install` empties it and
   writes every file again before each build (a kept NSIS tree could otherwise hold a changed `makensis.exe`, which Tauri never
   hashes: it checks only `NSIS.exe` and the plugin, `nsis/mod.rs:98-121`).
2. **Every run, not only release mode.** The ADR named `useLocalToolsDir` as part of release mode (WP-1a). It is passed on
   branch and dispatch runs too: one path for the tools, and the per-user folder (`%LOCALAPPDATA%\tauri`, reached through
   `SHGetKnownFolderPath`, §2.2) is no longer read by any build.
3. **NSIS is pinned.** The NSIS 3.13 zip and `nsis_tauri_utils.dll` v0.5.3 come from the URLs tauri-bundler itself uses
   (`nsis/mod.rs:38-44`), pinned by SHA-256 (equal to GitHub's release digests; the SHA-1 values equal Tauri's
   `NSIS_SHA1`, `NSIS_EXE_SHA1` and `NSIS_TAURI_UTILS_SHA1`). `install` unpacks the zip into `NSIS/` itself (no unzip tool on
   the Windows runner is assumed; size and CRC-32 checked per entry, no entry may leave its folder) and fails when the result
   would fail Tauri's own SHA-1 checks, since Tauri would then delete the folder and download it again, unpinned. A real run
   of `install` on the pinned zip gave the same 442 files as `unzip`.
4. **The manifest is the probe's pin file.** `install` writes `<build folder>/.tauri.sha256`, one `<sha256>  <path>` line per
   file the folder may hold after the build: the pinned files (linuxdeploy with the 3 bytes Tauri's `dd` zeroes, `:267-276`),
   every file of the NSIS zip, and the two plugin scripts tauri-bundler writes from its own binary (`:229-246`). This is the
   format `./dev ci release-isolation verify --tauri-pins` reads, so WP-3 passes that file. `check` compares the folder with
   it after the build: anything unpinned or changed warns, and fails a tag run.
5. **No tool cache on a tag (D9).** WP-2's `actions/cache` of the AppImage tools stays for branch and dispatch runs in the
   Linux container only; the step is skipped on a tag, and `tauri-tools.mjs` ignores any kept cache folder on a tag and
   downloads into a folder made for the run. (WP-2's comment that the cache was allowed on tags because every file is
   re-hashed is replaced: §4 item 1 says nothing kept is read.) A GitHub outage therefore stops a tag, as §9 accepts.
6. **linuxdeploy-plugin-appimage is pinned to the dated build `1-alpha-20250213-1` (user, 2026-11-12).** Its project
   publishes only the moving `continuous` release and dated `1-alpha-*` builds, no stable release. Tauri downloads the
   `continuous` build whenever the folder lacks `linuxdeploy-plugin-appimage.AppImage` (`linuxdeploy.rs:248-263`); `install`
   now puts the pinned x86_64 build there under that name, so Tauri downloads nothing. GitHub's release API lists no digest
   for this release (its assets predate digests), so the SHA-256 `992d502a…fccb3` was measured on two downloads that matched,
   and the size (15 889 136 bytes) equals the API's. There is no unpinned exception any more: `check` fails a tag on any file
   in the folder that is not in the manifest. The dated build is older than the `continuous` build Tauri used to fetch
   (2025-02-13 against 2026-06-07); whether the AppImage it makes is sound is measured by the train 6 runs below.
7. **Not pinned because not downloaded:** the WiX tools (`msi/mod.rs:60-62`, no app builds an MSI) and the WebView2
   installers (`windows/util.rs:56`, `:72`; the apps use the default `downloadBootstrapper` mode, which downloads nothing at
   build time). A change of either setting adds its pins here.

## WP-4: the key

8. **The release callers keep passing the secrets; the steps gate them, by the app's release tag.** `app-release.yml`'s
   tauri-bundle step gets the private key and its password as
   `${{ startsWith(github.ref, format('refs/tags/{0}v', inputs.tag-prefix)) && secrets.<name> || '' }}`, and `debrief.yml`'s
   "Build installers" step with `'refs/tags/debrief-v'`; any other ref, another app's tag included, gets nothing.
   `conformance/test/updater-key-tags.test.mjs` checks every workflow step and refuses the wider `'refs/tags/'`. Gating inside
   the called workflow covers every caller (the five release workflows and `nightly.yml`) without relying on expressions in a
   reusable call's `secrets:` block.
9. **Inside the step, only `tauri build` gets a key, in its environment.** `conformance/ci/updater-key.sh` (sourced by
   `tauri-bundle.sh` and Debrief's step) strips the keys (a failing `strip-keys.mjs` stops the step before its output is
   evaluated), moves them out of the environment before `npm ci` and the prepare command, and runs `tauri build` through
   `updater_key_exec`: a subshell that `export`s the three variables and `exec`s the command. Revision 1 used `env K=V npx
   tauri build`, which put the key in `env`'s command line, where every user of the machine can read it in the process list
   (review P1-1); a test now records the arguments of `env` and `npx` and finds the key only in the build's environment.
   In CI, a private key on a run that is not a tag fails the step before anything runs, and so does a tag run with the public
   key but no private key (it would ship unsigned installers). So a dispatch or any run on a tag that is not the app's
   release tag (another app's tag, a test tag) now fails closed: it gets the public key but not the private one. That is
   intended: such a run would otherwise ship nothing it could sign.
10. **The throw-away key.** On a CI run that is not a tag, with the public key given and no private key, the script makes a
    key pair in the job (`tauri signer generate --ci` from the app's own CLI) with an empty password, so no secret is on its
    command line (the CLI takes a password only as an argument, `src/signer/generate.rs`), and builds with it and its public
    key, so a rule 54 dispatch still signs and writes `.sig` files. A tag never makes one. Such installers cannot verify a real
    update and are never published (only a tag publishes). `paddock-setup.exe` still embeds the real public key
    (`PADDOCK_SETUP_UPDATE_KEY`), so **a dispatch build cannot test apply-update**: its app and its setup program verify with
    different keys. Apply-update is proven only by a tagged release installed over the previous one.
11. **The hook runs before the build, without the key (review P2-3).** tauri-cli runs `beforeBuildCommand` inside `tauri
    build` (`src/build.rs:203-211`, `helpers/mod.rs:68-111`), so in revision 1 the apps' UI builds and sidecar builds (npm
    scripts, Angular builders, cargo build scripts of the sidecars) ran with the key. `conformance/ci/before-build.mjs` now
    merges the hook as Tauri does (`tauri.conf.json`, `tauri.<platform>.conf.json`, each `--config`), runs it in the app folder
    through bash with `TAURI_ENV_DEBUG=false` before `tauri build`, and `tauri build` gets `{"build":{"beforeBuildCommand":null}}`
    last: `null`, so Tauri's merge patch deletes the key and the build has no hook at all. A `beforeBundleCommand` would run
    inside `tauri build` with the key, so it is refused (no app has one).
12. **What still runs with the key** (named, not closed): `tauri build`'s own `cargo build` of the app crate, so every build
    script (`build.rs`) and proc macro of the app's dependency graph, compiled from the sources in the runner's cargo registry
    (`CARGO_HOME`, kept and branch-writable on the hosts until release mode, WP-1a), and the Tauri CLI's own npm package from
    `npm ci`. Closing it needs either release mode (a fresh `CARGO_HOME`, WP-1a) or signing after the build (the note below).
13. **One key for every signature (review P2-6).** After the build, `conformance/release/updater-key-check.mjs` verifies every
    `.sig` (minisign, Ed25519 over BLAKE2b-512, as Tauri writes it; tested on real `tauri signer` output) against the public
    key the build carries (the one in `updater.conf.json`, which tauri-cli embeds as `plugins.updater.pubkey`); a signature by
    another key fails the step. On a tag, `check-per-machine-installer.mjs` also requires `paddock-setup.exe`'s self-test
    `key_fingerprint` to be that key's id (`PADDOCK_EXPECT_UPDATE_KEY`). The app binary itself is not searched for the key:
    in a built Dyno binary the updater plugin's endpoint URL from `tauri.conf.json` was not found as plain bytes (its
    identifier was), so a byte search could not be shown to see the key (rule 71).
14. **A tag's npm side is fresh (review P1-2).** On a tag, the bundle jobs of `app-release.yml` and `debrief.yml` skip the
    `node-caches` action and run `conformance/ci/tag-node-caches.sh` instead: `npm_config_cache` is a new folder under the
    job's `$RUNNER_TEMP`, and an `.angular/cache` link a branch run left in a kept checkout is removed as a link. Debrief's
    Windows tag removes the kept `node_modules` junction (`windows-node-modules.sh unlink`) instead of linking it, skips the
    kept npm cache folder, and its build step always runs `npm ci`.

**Prerequisite, open (user, 2026-11-12): protected release tags.** The key gate trusts the tag name: anyone who can push a
`<app>-v*` tag can run a workflow file of their choice from that tag with the key. Gitea protected tags (`*-v*`, pushers
restricted) would close that. The user decided on 2026-11-12 to keep release tags unprotected until things stabilise, so
this is a known, accepted gap, not a condition for the next tags; it is revisited with ADR 0085 WP-7 (the release identity).

## WP-4: signing after the build as a separate step (the note D7 asks for)

tauri-cli 2.12.3 signs the updater artifacts after the bundler finishes (`src/bundle.rs:230-325`, `sign_updaters`), and
`tauri signer sign` (`src/signer/sign.rs`) signs any file with the same key and `--app-version`. So a build without the key
followed by a signing step is possible in principle, which would keep the key away from every build script (`build.rs`,
proc macros) too, not only from `npm ci`. It is not done now, for three reasons found in the source:

- With `createUpdaterArtifacts` on and no private key, `sign_updaters` fails ("A public key has been found, but no private
  key", `bundle.rs:288-290`). The flag that skips it, `--no-sign`, also skips the macOS code signature
  (tauri-bundler `macos/app.rs:115`), and rule 23 needs the ad-hoc seal, so `--no-sign` cannot be used on macOS.
- Without `createUpdaterArtifacts`, macOS gets no `.app.tar.gz` (the updater archive), so a separate step would have to make
  that archive itself, the way Tauri does, and the release would then ship an archive Tauri did not make.
- The key would still be in a step of the same job on the same host, so on the hosts (T1, D6) the gain is limited until the
  release identity of WP-7 exists.

Recommended next step (not gating): a small research item with WP-7: on Linux and Windows, `--no-sign` plus
`tauri signer sign` on the installers, compared byte for byte with today's `.sig` files; on macOS, keep signing inside
`tauri build`.

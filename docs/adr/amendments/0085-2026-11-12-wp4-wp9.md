# Amendment to ADR 0085 (2026-11-12): what WP-4 and WP-9 built, and the note on signing after the build

- Status: Proposed (2026-11-12). An amendment to ADR 0085 (accepted 2026-11-10), which lives on
  `origin/docs/adr-0085-release-cache-isolation` (`3a49d49a1`). It records how the minimum the user chose on 2026-11-12
  (WP-4, WP-9 and the rule text gate the next tags of Dyno, Pitwall and Debrief) was built on branch `fix/adr0085-minimum`,
  and is merged into the ADR's text when that branch lands.
- Related: ADR 0085 §4 items 1, 5 and 6, D7, D9, D10, WP-4, WP-9; the amendment `0085-2026-11-10-rust-tool.md` (decision 7:
  `verify --tauri-pins`); Dyno 1.1.1 plan WP-2 and WP-17; rule 78.

## WP-9: the tools folder

1. **The ADR's folder is used: `<build folder>/.tauri`, through `useLocalToolsDir`.** Dyno WP-2 (`a3f3a54aa`) had put
   linuxdeploy and AppRun in the dirs cache folder (`~/.cache/tauri`). Moving them was low-risk, so the ADR is followed:
   `tauri-bundle.sh` (and Debrief's bundle step) pass `--config '{"bundle":{"useLocalToolsDir":true}}'` to every NSIS and
   AppImage build, and tauri-cli 2.12.3 then hands the bundler cargo's `target_directory` (`src/interface/mod.rs:79-83`),
   which the bundler joins with `.tauri` (tauri-bundler 2.10.3 `linuxdeploy.rs:45-50`, `nsis/mod.rs:82-85`).
   `conformance/ci/tauri-tools.mjs` asks `cargo metadata --no-deps` in `src-tauri` (where tauri-cli asks, so `.cargo/ci.toml`
   applies) and fills that folder. Why low-risk: the path is cargo's own answer, not a guess from `target/`; a Linux container
   gets a fresh folder every run; on a host runner the folder is in the kept build folder, so `install` empties it and
   writes every file again before each build (a kept NSIS tree could otherwise hold a changed `makensis.exe`, which Tauri never
   hashes: it checks only `NSIS.exe` and the plugin, `nsis/mod.rs:98-121`).
2. **Every run, not only release mode.** The ADR named `useLocalToolsDir` as part of release mode (WP-1a). It is passed on
   branch and dispatch runs too: one path for the tools, and the per-user folder (`%LOCALAPPDATA%\tauri`, reached through
   `SHGetKnownFolderPath`, §2.2) is no longer read by any build.
3. **NSIS is pinned.** The NSIS 3.13 zip and `nsis_tauri_utils.dll` v0.5.3 come from the URLs tauri-bundler itself uses
   (`nsis/mod.rs:38-44`), pinned by SHA-256 (equal to GitHub's release digests; the SHA-1 values equal Tauri's
   `NSIS_SHA1`, `NSIS_EXE_SHA1` and `NSIS_TAURI_UTILS_SHA1`). `install` unpacks the zip into `NSIS/` itself (no unzip tool on
   the Windows runner is assumed; size and CRC-32 checked per entry, no entry may leave its folder) and fails when the result
   would fail Tauri's own SHA-1 checks, since Tauri would then delete the folder and download it again, unpinned. A real run
   of `install` on the pinned zip gave the same 442 files as `unzip`.
4. **The manifest is the probe's pin file.** `install` writes `<build folder>/.tauri.sha256`, one `<sha256>  <path>` line per
   file the folder may hold after the build: the pinned files (linuxdeploy with the 3 bytes Tauri's `dd` zeroes, `:267-276`),
   every file of the NSIS zip, and the two plugin scripts tauri-bundler writes from its own binary (`:229-246`). This is the
   format `./dev ci release-isolation verify --tauri-pins` reads, so WP-3 passes that file. `check` compares the folder with
   it after the build: anything unpinned or changed warns, and fails a tag run.
5. **No tool cache on a tag (D9).** WP-2's `actions/cache` of the AppImage tools stays for branch and dispatch runs in the
   Linux container only; the step is skipped on a tag, and `tauri-tools.mjs` ignores any kept cache folder on a tag and
   downloads into a folder made for the run. (WP-2's comment that the cache was allowed on tags because every file is
   re-hashed is replaced: §4 item 1 says nothing kept is read.) A GitHub outage therefore stops a tag, as §9 accepts.
6. **linuxdeploy-plugin-appimage stays the named gap (WP-17).** Its project publishes only the moving `continuous` release
   and dated `1-alpha-*` builds (checked 2026-11-12 through GitHub's release API), no stable release. Tauri downloads it
   whenever the folder lacks it (`:248-263`) and falls back to linuxdeploy's built-in plugin when the download fails. `check`
   reports it as a gap (a warning, never a pass); `verify --tauri-pins` will report it as unpinned until WP-17 mirrors one
   build. Whether to pin the dated `1-alpha-20250213-1` build instead is a question for the user.
7. **Not pinned because not downloaded:** the WiX tools (`msi/mod.rs:60-62`, no app builds an MSI) and the WebView2
   installers (`windows/util.rs:56`, `:72`; the apps use the default `downloadBootstrapper` mode, which downloads nothing at
   build time). A change of either setting adds its pins here.

## WP-4: the key

8. **The release callers keep passing the secrets; the steps gate them.** `app-release.yml`'s tauri-bundle step and
   `debrief.yml`'s "Build installers" step get the private key and its password as
   `${{ startsWith(github.ref, 'refs/tags/') && secrets.<name> || '' }}`; a test checks every workflow step
   (`conformance/test/updater-key-tags.test.mjs`). Gating inside the called workflow covers every caller (the five
   release workflows and `nightly.yml`) without relying on expressions in a reusable call's `secrets:` block.
9. **Inside the step, only `tauri build` gets a key.** `conformance/ci/updater-key.sh` (sourced by `tauri-bundle.sh` and
   Debrief's step) strips the keys, moves them out of the environment before `npm ci` and the prepare command, and passes them
   with `env` to the one `tauri build` command. In CI, a private key on a run that is not a tag fails the step before anything
   runs (defence in depth: the workflow gate is the first line).
10. **The throw-away key.** On a CI run that is not a tag, with the public key given and no private key, the script makes a
    key pair in the job (`tauri signer generate --ci` from the app's own CLI, a random password) and builds with it and its
    public key, so a rule 54 dispatch still signs and writes `.sig` files and `latest.json` inputs. Such installers cannot
    verify a real update and are never published (only a tag publishes). `paddock-setup.exe` still embeds the real public
    key (`PADDOCK_SETUP_UPDATE_KEY`), which is public.

## WP-4: signing after the build as a separate step (the note D7 asks for)

tauri-cli 2.12.3 signs the updater artifacts after the bundler finishes (`src/bundle.rs:230-325`, `sign_updaters`), and
`tauri signer sign` (`src/signer/sign.rs`) signs any file with the same key and `--app-version`. So a build without the key
followed by a signing step is possible in principle, which would keep the key away from every build script (`build.rs`,
proc macros) too, not only from `npm ci`. It is not done now, for three reasons found in the source:

- With `createUpdaterArtifacts` on and no private key, `sign_updaters` fails ("A public key has been found, but no private
  key", `bundle.rs:288-290`). The flag that skips it, `--no-sign`, also skips the macOS code signature
  (tauri-bundler `macos/app.rs:115`), and rule 23 needs the ad-hoc seal, so `--no-sign` cannot be used on macOS.
- Without `createUpdaterArtifacts`, macOS gets no `.app.tar.gz` (the updater archive), so a separate step would have to make
  that archive itself, the way Tauri does, and the release would then ship an archive Tauri did not make.
- The key would still be in a step of the same job on the same host, so on the hosts (T1, D6) the gain is limited until the
  release identity of WP-7 exists.

Recommended next step (not gating): a small research item with WP-7: on Linux and Windows, `--no-sign` plus
`tauri signer sign` on the installers, compared byte for byte with today's `.sig` files; on macOS, keep signing inside
`tauri build`.

## Measured in train 6 (to fill in)

The change is proven by the release runs of train 6, none of which this branch dispatched:

- a rule 54 dispatch of `dyno-release.yml` (Linux AppImage, Windows NSIS, macOS): the bundle logs show
  `tauri-tools: ... from the download` or `from the cache`, the `::notice::` of the throw-away key, no
  `Downloading https://github.com/...` line from Tauri for AppRun, linuxdeploy or NSIS, and the `check` summary (on Linux the
  named WP-17 gap);
- a `debrief.yml` full run (its Windows bundle: NSIS from the pins, the throw-away key);
- `pitwall-release.yml` (same shared path as Dyno);
- the first tag of each app: the tag log shows the real key used and no cache read (`a tag run reads no kept cache`).

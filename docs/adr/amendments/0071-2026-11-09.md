# Amendment to ADR 0071 (2026-11-09): the first command after a start is part of the start

- Status: Proposed (2026-11-09). An amendment to ADR 0071 (accepted 2026-11-09), which is not on `origin/main` yet: it
  lives on `origin/docs/adr-0071-ready-or-exit` (`f6bb5b3ef`). This file is merged into the ADR's own text when that
  branch lands; until then it stands next to it.
- Related: ER-12, ER-21 / rule 40, ER-27, ER-28, rule 55 (copies), ADR 0031 (product starts judged by
  `paddock_proc::StartJudge`, C51), ADR 0071 §4 (C71's start kinds, C51's name list) and D4 (product start windows left
  to ADR 0031).

## Trigger

ADR 0071 made *test-side* start waits ready-or-exit and left product start windows to ADR 0031 (its D4). On loaded macOS
runs the failing step is the product's own **first command** to a program it has just started, under a fixed deadline
that is not a start window by name, so neither ADR nor C51 sees it.

## Evidence

- CI runs 7771, 7796 and 7810 (macOS, loaded runners): real-browser tests failed in the first DevTools command after a
  browser start (as reported by the coordinator; the job logs are not re-read for this draft and WP-A0 records the
  timings in `docs/benchmarks.md`, rule 48).
- `crates/paddock-chromium/src/launch.rs:692-695`: `pages()` sends `Target.getTargets` with a fixed **5 s** deadline;
  `start_page()` (`:646`) calls it right after the launch, inside `START_PAGE_WAIT` (`:40`, 5 s).
- `crates/paddock-chromium/src/page.rs:15`: `CALL` = **10 s** for every page command, the first one after a page opens
  included (`:224`, `Target.getTargets`).
- The registered copies have the same constants: Debrief `chromium-driver/src/launch.rs:18`, `:336`, `:351` and
  `page.rs:9`; Spotter `spotter-render/src/page.rs:12` (`docs/known-copies.toml`, mechanism driving Chromium over CDP).
- A fast-track fix is in progress on `fix/chromium-start-liveness` (a local branch, no commits of its own yet at
  `087570da4` on 2026-11-09).

## Change

1. **Scope.** ADR 0071's rule covers, besides test-side waits, the **first command a product sends to a program it
   started** (and the first command on a page it opened): it is judged ready-or-exit, not by a fixed deadline. While the
   child is alive and its connection open, the product keeps waiting, up to the start's hang guard (ADR 0031's
   `Patience`), logging each phase with its duration (ER-27); when the child ends, the product reports at once with the
   exit. Later commands keep their own deadlines.
2. **Mechanism.** `paddock_proc::StartJudge` gains a `first_call` phase that a driver enters after its connect and leaves
   after the first answer; `paddock-chromium` uses it for `pages()` in `start_page()` and for a page's first `CALL`.
3. **Copies (rule 55).** The canonical and both copies change together with a failing test each, or a copy is waived
   with `Copies-waived:` until its registered `delete_by`.
4. **Rule text.** Proposed rule 60's added sentence (ADR 0071 §5) gains "and so does a product's first command to a
   program it started".

## Check

- **C51** (product code, report-only) widens its names with first-call deadlines: a `Duration` literal or constant passed
  to a call within the function that started or connected to a child. **C71's R4 list** (`conformance/start-windows.json`)
  gains `paddock_chromium` `pages`/`CALL` and the copies' twins as "first call" entries.
- **Positive control:** `crates/paddock-chromium/src/launch.rs` at `b51c72509` must be reported at line 695 and `page.rs`
  at line 15; the fixed file must not.
- **Failing test first:** in `paddock-chromium`, a fake browser that answers its first `Target.getTargets` after the old
  deadline on an injected clock while staying alive must start successfully, and one that exits must fail at once with the
  exit status.

# Amendment to ADR 0022 (2026-11-15): the launcher is Rust, `./dev` is a stage 0

- Status: decided by the user on 2026-11-15 (shell-to-Rust plan, docs/plans/shell-to-rust.md on branch docs/shell-to-rust-plan,
  D3 and D4: a std-only Rust launcher that keeps the downloaded binary; one change, `git revert` as the fallback, no switch
  variable; D9: this amendment). Built by WP-1 on `feat/dev-launch-rust`.
- Changes: section 3.2 (what `./dev` and `dev.cmd` are) and section 3.3 (how the wrapper computes the hash, takes the binary and
  installs the toolchain). Nothing else in ADR 0022 changes: the input hash, the content-addressed cache, the download rules
  (R0b), the amendment of 2026-11-09 (owner, credentials) and release and tag jobs that never download.

## What changes

1. **`./dev` is a stage 0 of 111 lines of sh and `dev.cmd` of the same steps in batch (about 70).** Each finds the root with `git
   rev-parse --show-toplevel`, and builds the launcher `tools/dev-launch` with `cargo build --release --locked` only when no
   binary exists for the stamp of its sources: git's tree id of the folder, plus a hash of `git status` and `git diff` when
   something is uncommitted. The build is copied to `target/bin/dev-launch-<stamp>` by a rename and that copy is run, so an
   up-to-date launcher costs two git calls and no `cargo` start, a running launcher is never replaced (Windows cannot, and cargo
   replaces its own uplifted file even on a build that changes nothing), and the launcher of another stamp is removed. The
   launcher then runs with the caller's arguments in the caller's folder. Only shell builtins, `git`, `cargo` and `rustup` are
   used: no `grep`, `tr`, `sed`, `awk`, `touch` or `ps`. `dev.cmd` no longer needs Git for Windows' `bash.exe`. `GIT_DIR`,
   `GIT_WORK_TREE` (a git hook's) and `CARGO_BUILD_TARGET` are not passed on, as before.
2. **`tools/dev-launch` is the old wrapper in Rust, with the standard library only.** Its own Cargo workspace and lockfile (ADR
   0014's third kind). It does what the 639-line shell did, in the same order and with the same messages: the repository, the
   input hash, the cache (`bin`, and `bin-source` when `PADDOCK_DEV_DOWNLOAD=0`), the checked download (`curl`, the token on
   stdin, the checksum and the embedded hash), the build with the one restart when the compiler changes mid-build, the cache
   prune, `--wrapper-hash`, `--print-binary`, `--ensure-toolchain`, `--install-toolchain` and `PADDOCK_DEV_FRESH`.
3. **One copy of the hash (rule 55).** The input hash code moved from `tools/paddock-dev/src/input_hash.rs` to
   `dev_launch::hash`; `paddock-dev` depends on the crate and `dev self hash` calls it. `tools/dev-launch` is in
   `tools/paddock-dev/inputs.txt` (the tool depends on it), so the hash of every tool changes once, with this change. The hash
   of a given tree is otherwise unchanged: the golden test holds the values the shell printed on the same tree, environment
   and cargo configs.
4. **The toolchain install lock is the operating system's.** One `rustup toolchain install` of a pin at a time per
   `RUSTUP_HOME` is an advisory file lock (`File::lock`, std 1.89: `flock`, `LockFileEx`) on
   `.paddock-install-<pin>.flock`, released with the handle however the holder ends. The `mkdir` lock folder with the owner's pid
   and start time is gone, and with it every pid and start time compared to judge a lock (rule 53). A lock folder an earlier
   wrapper left is ignored. The wait for a live holder is still bounded by `PADDOCK_DEV_TOOLCHAIN_TIMEOUT` (default 900 s).
5. **The checksum is computed in Rust.** SHA-256 in `std`, not `sha256sum` or `shasum`, which Windows without Git Bash lacks.

## What it asks of a machine, and the limits

A toolchain of Rust 1.89 or newer that `cargo` can run, to build the launcher. When `cargo` does not run (rustup 1.28 installs no
pinned toolchain by itself), stage 0 builds the launcher with the first installed toolchain whose `rustc --version` says 1.89 or
newer (`rustup toolchain list` is read word by word: "no installed toolchains", an old one and one that does not run are skipped),
and only that build sees it. It installs nothing while any toolchain is listed: every install of a pin on a machine that has
toolchains is the launcher's, under its file lock, with its time limit, `--no-self-update` and the `PADDOCK_TOOLCHAIN_FAILED` check
(run 8060: two jobs installed 1.100.0 at once; `setup-rust` reaches the launcher through this stage 0). The one install stage 0
makes is the one on a machine whose rustup lists no toolchain at all, where there is no compiler to build the launcher with. The
`dev` script makes it under a lock folder (`.paddock-stage0-install.lock` in `RUSTUP_HOME`, removed on any exit but SIGKILL; after a
kill, delete it by hand), bounded by `PADDOCK_DEV_TOOLCHAIN_TIMEOUT`, with `--no-self-update`, and not after
`PADDOCK_TOOLCHAIN_FAILED=1`. This lock judges no pid or age; it is the one mkdir lock left, and it is there because no launcher
exists yet. `dev.cmd` takes no lock there: a person runs it, and CI starts through the `dev` script (Git Bash). With no rustup, both
stop with one `::error::` line. With toolchains listed but none new enough, both say which command to run.

Limits left, with their reasons:

- The stamp does not see the content of an untracked file that already existed when the stamp was made (`git status` lists it, but
  its content is not hashed): edit-and-rerun on an untracked source file needs `git add -N` or a commit.
- The stage 0 costs two git calls (about 8 ms each on the Mac, Linux 3 ms) on every run; see docs/benchmarks.md.
- Windows: the start-up time was not measured, and `dev.cmd` was run on the test VM with stand-ins for `cargo` and `rustc` (the VM
  has no toolchain), not with a real build. The paddock-dev tests of the launcher run on the Mac and Linux; on Windows the launcher's
  own tests run (`tools/dev-launch/tests/it`) and the `ci.yml` leg "Launcher" runs them on every Windows job.

## Common practice (ER-37)

rust-lang's `x.py` and the `xtask` pattern start a small program with `cargo run`. Rustup itself is a Rust launcher that
chooses and runs the toolchain's own programs. Visual Studio Code and Chrome start through a native launcher. The
content-addressed binary (ADR 0022 section 3.3) is ours alone, and this change keeps it; the cheaper option (the plan's D1:
keep the shell wrapper and fix only the Windows PATH and the kit's scripts) was offered and the user chose the launcher.
Cost: 4 agent-days (plan estimate).

## Switch and fallback

One change: the launcher, the stage 0 and the callers' parity tests land together, and there is no variable that picks the old
wrapper. The fallback is `git revert` of that change. The parity is not the launcher compared with itself: the shell wrapper's own tests (`tools/paddock-dev/tests/it/wrapper.rs`,
`wrapper_download.rs`, and WP-2's `wrapper_ci.rs`) were pointed at the launcher and pass; the hash goldens in
`tools/dev-launch/tests/it/launcher.rs` are values the old shell printed on the same files, environment and configs (plain, a
compiler flag, a registry config, a build-folder-only config, an uncommitted input, the order of config files, include files, a
carriage return); and `dev_stage0.rs` and the Windows run of `dev.cmd` test the stage 0. The log line is byte-identical to the old
one.

## Measured

Start-up cost on a cached tool, and the cold build of the launcher, Mac and Linux container (Windows not measured): [docs/benchmarks.md](../../benchmarks.md), "2026-11-15, the `./dev`
launcher against the shell wrapper".

## Windows run of `dev.cmd` (2026-11-16)

Windows 11 Arm test VM, under the test-machines lock, `vm-win.sh run --ci-like` at the branch head, with the launcher and its tests
cross-built on the Mac and stand-ins for `cargo` (a program that copies the cross-built launcher where `--target-dir` says and logs
each call) and `rustc` (the VM has no toolchain, so no real build ran). Results: the launcher's 14 unit and 9 integration tests pass
(the old shell's hash goldens, config order, include files, CRLF, a PATH of git's folder only, a planted `GIT_DIR`, outside a
repository, a closed stdout); `dev.cmd --wrapper-hash` builds once (one cargo call), publishes
`target\bin\dev-launch-<stamp>.exe` and prints the hash the Mac prints; a second call builds nothing; with the launcher kept running
for 8 s by a pinned slow tool (`GITHUB_ACTIONS=true`, `PADDOCK_DEV`, `ci`), a second `dev.cmd` runs at once (exit 0, no "Access is
denied", still one cargo call); two `dev.cmd` started together on an empty `target` folder both exit 0 with one launcher published; a
source change gives a new stamp and removes the old file; outside a repository it exits 2 with the message; a planted `GIT_DIR` is
ignored; `CARGO_BUILD_TARGET` does not reach the build. Not covered: a real cargo build of the launcher on Windows, and the
no-toolchain branch of `dev.cmd` (rustup install).

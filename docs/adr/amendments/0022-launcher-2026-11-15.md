# Amendment to ADR 0022 (2026-11-15): the launcher is Rust, `./dev` is a stage 0

- Status: decided by the user on 2026-11-15 (shell-to-Rust plan, [docs/plans/shell-to-rust.md](../../plans/shell-to-rust.md),
  D3 and D4: a std-only Rust launcher that keeps the downloaded binary; one change, `git revert` as the fallback, no switch
  variable; D9: this amendment). Built by WP-1 on `feat/dev-launch-rust`.
- Changes: section 3.2 (what `./dev` and `dev.cmd` are) and section 3.3 (how the wrapper computes the hash, takes the binary and
  installs the toolchain). Nothing else in ADR 0022 changes: the input hash, the content-addressed cache, the download rules
  (R0b), the amendment of 2026-11-09 (owner, credentials) and release and tag jobs that never download.

## What changes

1. **`./dev` is a stage 0 of 29 lines, `dev.cmd` of the same steps in batch.** Each finds the root with `git rev-parse
   --show-toplevel`, builds the launcher `tools/dev-launch` with `cargo build --release --locked` when a source is newer than
   its binary (a pure shell `-nt` test, so an up-to-date launcher costs no `cargo` start), and runs it with the caller's
   arguments in the caller's folder. When `cargo` cannot run (rustup 1.28 installs no pinned toolchain by itself) and `rustup`
   exists, the launcher is built with the first installed toolchain, and only that build sees it. Only shell builtins, `git`,
   `cargo`, `rustup` and `env` are used: no `grep`, `tr`, `sed`, `awk`, `touch` or `ps`. `dev.cmd` no longer needs Git for
   Windows' `bash.exe`. `GIT_DIR` and `GIT_WORK_TREE` (a git hook's) and `CARGO_BUILD_TARGET` are not passed on, as before.
2. **`tools/dev-launch` is the old wrapper in Rust, with the standard library only.** Its own Cargo workspace and lockfile (ADR
   0014's third kind). It does what the 639-line shell did, in the same order and with the same messages: the repository, the
   input hash, the cache (`bin`, and `bin-source` when `PADDOCK_DEV_DOWNLOAD=0`), the checked download (`curl`, the token on
   stdin, the checksum and the embedded hash), the build with the one restart when the compiler changes mid-build, the cache
   prune, `--wrapper-hash`, `--print-binary`, `--ensure-toolchain`, `--install-toolchain` and `PADDOCK_DEV_FRESH`.
3. **One copy of the hash (rule 55).** The input hash code moved from `tools/paddock-dev/src/input_hash.rs` to
   `dev_launch::hash`; `paddock-dev` depends on the crate and `dev self hash` calls it. `tools/dev-launch` is in
   `tools/paddock-dev/inputs.txt` (the tool depends on it), so the hash of every tool changes once, with this change. The hash
   of a given tree is otherwise unchanged: the golden test holds the values the shell printed on the same tree, environment
   and cargo configs.
4. **The toolchain install lock is the operating system's.** One `rustup toolchain install` of a pin at a time per
   `RUSTUP_HOME` is an advisory file lock (`File::lock`, std 1.89: `flock`, `LockFileEx`) on
   `.paddock-install-<pin>.flock`, released with the handle however the holder ends. The `mkdir` lock folder with the owner's pid
   and start time is gone, and with it every pid and start time compared to judge a lock (rule 53). A lock folder an earlier
   wrapper left is ignored. The wait for a live holder is still bounded by `PADDOCK_DEV_TOOLCHAIN_TIMEOUT` (default 900 s).
5. **The checksum is computed in Rust.** SHA-256 in `std`, not `sha256sum` or `shasum`, which Windows without Git Bash lacks.

## What it asks of a machine, and two limits

A toolchain of Rust 1.89 or newer that `cargo` can run, to build the launcher. The stage 0 gets it as the old wrapper did: when
`cargo` does not run and `rustup` exists, it runs `rustup toolchain install` in `tools/paddock-dev` (rustup reads the version,
profile and components from `rust-toolchain.toml`); if that fails it builds the launcher with the first installed toolchain. With no
rustup it stops with one `::error::` line. This first install takes no lock (the launcher's lock needs the launcher); two stage 0s
that both find no toolchain at once can install the same pin at once. Every later install goes through the launcher's lock.

The launcher binary is built by cargo, which removes and links it again on every build that runs. A second `./dev` that starts while a
first one is rebuilding (a source changed) can find the binary missing: the stage 0 waits up to 5 s for it before it runs it. A
`-nt` check that sees a missing binary builds it. Left: a binary replaced between the check and the `exec`, which needs a second build
to finish at that instant; the fix would be a lock or a copy per call, which costs a program start on every call (about 5 ms), so it
is not made.

## Common practice (ER-37)

rust-lang's `x.py` and the `xtask` pattern start a small program with `cargo run`. Rustup itself is a Rust launcher that
chooses and runs the toolchain's own programs. Visual Studio Code and Chrome start through a native launcher. The
content-addressed binary (ADR 0022 section 3.3) is ours alone, and this change keeps it; the cheaper option (the plan's D1:
keep the shell wrapper and fix only the Windows PATH and the kit's scripts) was offered and the user chose the launcher.
Cost: 4 agent-days (plan estimate).

## Switch and fallback

One change: the launcher, the stage 0 and the callers' parity tests land together, and there is no variable that picks the old
wrapper. The fallback is `git revert` of that change. The parity tests (`tools/paddock-dev/tests/it/wrapper.rs`,
`wrapper_download.rs`, `dev_stage0.rs`, `tools/dev-launch/tests/launcher.rs`) ran the old shell and the launcher on the same
inputs before the shell was deleted: the hash, the log line, the download on and off, a missing toolchain, outside the
repository, a planted `GIT_DIR`, the cache prune, the restart.

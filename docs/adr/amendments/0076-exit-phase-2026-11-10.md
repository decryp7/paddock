## Trigger

ADR 0076 makes every thread an owned member whose owner stops it within a bound, and its Quit path "stops its top-level
groups, then settles" (§3). But a process can end without any owner being asked: `std::process::exit` "terminates the
process, [and] no destructors on the current stack or any other thread's stack will be run", while it still runs the
`atexit` handlers and the C++ static destructors (std's own doc of `exit`, `library/std/src/process.rs`, Rust 1.99.1).
A thread inside DuckDB (C++) then runs on while DuckDB's statics are destroyed under it. Debrief has crashed this way at
least four times in two weeks, and each fix patched the hand-made `atexit` handler a little further.

**Windows is not spared, it fails differently.** `ExitProcess` (what std's `exit` calls on Windows, `sys/exit.rs`) first
terminates every other thread "without receiving a DLL_THREAD_DETACH notification", then runs the DLLs' process-detach
code; "if one of the terminated threads in the process holds a lock and the DLL detach code ... attempts to acquire the same
lock, then calling ExitProcess results in a deadlock" ([Microsoft Learn, ExitProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-exitprocess),
read 2026-11-10). A DuckDB statement is cut mid-write, and a static destructor that takes a lock the killed thread held
hangs the exit. Not observed in Paddock yet (no Windows crash or hang report was looked for); it is the documented risk.

## Pattern

**The end of a process is treated as an event, not a phase.** Any thread may end the process at any moment (a lifeline,
a watch, a usage error deep in a library, the GUI loop), and whatever runs at that moment, a DuckDB statement, a Tantivy
merge, a SQLite transaction, a child's start, keeps running while the runtime tears the process down around it. Each owner
then tries to protect itself from inside the teardown (an `atexit` drain, a guard count, a leaked connection), which runs
too late and in an order nobody controls.

**Invariant.** A Paddock process ends in exactly one way: one exit phase, entered once, that stops every registered
owner of native or durable state within the process stop budget and joins it, then ends the process. Nothing that holds a
native handle (a database, an index writer, a C or C++ library context, a child process) runs when the end step starts;
if one did not stop in time, the end step does not run C++ static destructors under it.

## Change

### 1. One exit function, `paddock_jobs::exit` (D-E1)

```rust
/// Ends the process through the exit phase. Never returns.
pub fn exit(code: i32, why: ExitWhy) -> !;
/// For `fn main`: runs `body`, then ends through the phase with its code (a `main` never returns into the C runtime).
pub fn main(body: impl FnOnce() -> i32) -> !;
/// Registers an owner the phase must stop before the end step (held weakly: a dropped owner leaves the list).
pub fn register(owner: Weak<dyn ExitOwner>) -> ExitRegistration;
pub trait ExitOwner: Send + Sync {
    fn name(&self) -> &str;
    /// Stop within what is left of `budget` (signal, interrupt, join, close the handle). Never blocks past it.
    fn stop_for_exit(&self, budget: Deadline) -> StopOutcome;
    /// Whether this owner holds native state that must not run during static destruction.
    fn native(&self) -> bool;
}
```

`ExitWhy` is a closed enum (`Quit`, `HostGone`, `Updated`, `Usage`, `CannotStart`, `Signal`, `Watchdog`, `Finished`),
logged with the code. `TaskGroup` (0076 §2) implements `ExitOwner`; a `TaskGroup` built as **top-level** registers
itself, so most owners register by being built, not by a separate call. A `paddock_proc::Supervised` child is ended
through `end_all` as a step of the phase (behind the `proc` feature, 0076 D1).

### 2. The phase

1. **Once.** The first caller takes a process-wide once-flag. A second caller on another thread **parks** (it does not
   return and does not run handlers; it is the one thread the phase does not join, item 2), so two exits can never run
   at once on any OS; std's own lock exists only on Linux.
2. **Stop: everything except the calling thread.** From the caller's thread (or, on the Tauri main thread, from a helper
   thread the main thread waits for, §2a.7), stop every registered owner in parallel within the **process stop budget**,
   which the composition root declares (ADR 0037; the 2026-11-09 amendment; D4's 2 s quit bound is its default where a
   root declares none), then settle the reaper with what is left. **Only the calling thread is excluded from the joins**
   (revision 1 excluded the caller's whole group, which would leave its other members running; that broke the
   invariant). Every other member of the caller's group is stopped and joined like any other. Owners stop in reverse
   registration order only where one declares it depends on another (the store before its connection pool); otherwise in
   parallel.
3. **Where `exit` may be called from.** The phase records on entry whether the caller is safe to wait from:
   - a plain thread with no native frames on its stack: the normal path;
   - a thread **with native frames on its stack** (a call made from inside a DuckDB callback, a registered C callback or
     a member's statement; the owner marks these regions with a guard, as `Active` does today), or a **re-entrant** call
     (a stop hook that calls `exit`): logged, and the phase goes straight to the **overrun end step** (item 5), because
     static destructors would run under the caller's own native frames;
   - an **`atexit` handler** (a C or Rust handler that reaches `exit` while the C runtime is already exiting): logged,
     and ends with `_exit` at once. **How it is detected:** a sentinel `atexit` handler that does one thing: when the C
     runtime calls it, it sets a process-wide `RUNTIME_EXITING` flag. Handlers run last-registered first, so the sentinel
     only sees the runtime's exit early if it was registered after the other handlers and after the lazily built C++
     statics (whose destructors are registered when they are first built, as DuckDB's are). It is therefore registered
     **lazily and again**: at `register`'s first call, at every later `register` call whose count is a power of two
     (the cost of `shutdown.rs`'s present scheme, about 20 registrations in a million), and once more at the end of the
     phase's step 2, just before the end step; a repeat run of the sentinel only sets the flag again. The flag is set when
     the first sentinel runs, that is, once the runtime is running handlers registered no earlier than it. An
     `exit` call that finds the flag set, or that finds the once-flag already taken by its own thread (the re-entrant
     case), was reached from inside the C runtime's exit and goes to `_exit`. On Windows, std's `exit` calls `ExitProcess`
     directly; that the CRT then runs the exe's `atexit` table (during the exe's process detach, from the exiting thread,
     after the other threads are terminated) is **unverified** here and is settled in WP-X2 by the probe of §Check 4; until
     then the Windows leg of that detection counts as not measured;
   - a **signal handler: forbidden.** Signals are turned into a flag or a message by a watch thread (Dyno's signal watch,
     `ctrlc`), and that thread calls `exit`; the C42 rule below rejects a call from a function registered as a signal
     handler.
4. **Report.** One log line per owner (name, outcome, duration) and one summary ("Exit phase: code, why, N owners stopped
   in T ms, overran: ..."). The log must reach its sink before the end step: `paddock-log`'s `log` bridge has a no-op
   `flush` (`crates/paddock-log/src/bridge.rs:53`), so the phase flushes the underlying writer through its handle
   (`paddock_log` gains a `flush_and_wait(deadline)` on the writer the app installed; WP-X1). A child whose log goes to its
   parent over **stderr** (the store worker, plugins) only gets its last lines through if the parent keeps reading stderr
   until the child has exited; the parent's stop (§3.1) does so.
5. **End step (D-E2).** If every `native()` owner ended: `std::process::exit(code)` (stdio flushed, the remaining
   handlers and static destructors run, with nothing native alive). If a native owner overran or was abandoned, or item 3
   asks for it: the log line names it, then the process ends **without** running static destructors: `libc::_exit(code)`
   on Unix, `TerminateProcess(GetCurrentProcess(), code)` on Windows (which notifies no DLL, so no detach code can deadlock
   on a killed thread's lock, per the same Microsoft page). Dyno's signal watch already does this on Unix; on Windows it
   still calls `std::process::exit` (`cli.rs:58-59`) and moves to this end step.

### 3. Every route goes through it

1. **The parent's stop fits the child's budget (budget-fit across processes; extends the 2026-11-09 amendment's
   "the stops must fit the process stop budget").** A parent that stops a child process waits, before any kill, at least
   the child's **stop budget plus a margin**, and that wait is itself part of the parent's own budget.
   **Direction (revision 3):** the bootstrap goes only parent → child, on the child's stdin
   (`debrief-ipc/src/launch.rs:21-34`, `crates/paddock-ipc/src/launch.rs:34-47`), so the **parent assigns** the child's
   budget: it writes `stop_budget_ms` into the bootstrap, and the child's exit phase uses **the smaller of that and its own
   declared budget**. The parent then knows the child's budget without being told, and a child can only be faster than
   what the parent waits for. (The alternative, the child reporting its budget in the handshake, makes the parent trust a
   number the child chose; not taken.)
   **The default split:** child budget = parent budget − margin − the parent's own stop work. With D4's defaults (a 2 s
   quit bound for each process), a child given 2 s inside a parent's 2 s can never fit, and every default composition
   would be a start error. So the default is derived, not fixed: the parent's composition root has its 2 s; it reserves
   its own declared stop work (its groups' bounds, default 0.5 s) and a margin (default 0.25 s, covering the kill
   and the reap), and assigns each child the rest, 1.25 s, in parallel (children are stopped together, so the
   sum is not taken). A child declaring more is clamped to 1.25 s and logs it once at start. A composition root whose
   declared numbers leave a child less than a floor (250 ms, enough for an interrupt and a join, not a checkpoint) is a
   composition error at start, logged with all the numbers. Test: `the_default_composition_fits`, which builds each
   app's composition root with the defaults, reads the assigned child budgets and asserts the fit, so a change of a
   default that breaks it fails a test, not a Quit. **The split nests:** a child that starts children of its own applies
   the same rule to its assigned budget, so a plugin under the store worker gets 1.25 s − 0.25 s − 0.5 s = **0.5 s**
   (with the worker's default stop work), above the 250 ms floor; `the_default_composition_fits` walks the whole process
   tree each app declares (app → store worker → plugin; app → agent → helper) and asserts the fit and the floor at every
   level. For a child the parent does not start through a bootstrap (a service,
   a relaunched app), the parent's declaration names the budget it waits. This
   replaces `KILL_GRACE` (150 ms, `debrief-ipc/src/process.rs:45`) on the path `Supervisor::shutdown` → `Child::stop` →
   `kill`, and fixes its shared peers: `paddock-ipc`'s `launch::Child::stop(grace)` callers (`crates/paddock-ipc/src/launch.rs:199-209`)
   and `paddock-proc`'s supervised stop grace, which pass a fixed grace today. While it waits, the parent keeps reading the
   child's stderr (§2.4).
2. **The lifelines stop calling `exit`.** Once the peer is up, a lifeline that sees stdin close **closes the peer**
   (`Closing::ByPeer` in ADR 0072 terms) instead of calling `exit`; `main`, whose `wait_closed` then returns, is the only
   exit, through `exit::main`. Before the peer is up (no owners exist yet), the lifeline may still end the process, through
   `exit(0, ExitWhy::HostGone)`. **Fallback:** after closing the peer the lifeline waits for the phase to begin; if it has
   not begun within the child's stop budget plus the margin (a `main` that hangs and would keep the store's DuckDB lock,
   which the orphan guardian does not cover: it ends only `Supervised` children), the lifeline calls
   `exit(0, ExitWhy::HostGone)` itself, which runs the phase from its thread and joins everything except itself. Both copies change in the same merge (rule 55): `debrief-ipc/src/child.rs:73-82` (also
   reached by every Debrief plugin through `debrief-plugin-api/src/serve.rs:30`) and `crates/paddock-ipc/src/child.rs:50-61`
   with `serve` (`:65-78`).
3. **Explicit exits:** the one allowed `std::process::exit`, `libc::exit`, `libc::_exit` and the Windows end calls are
   inside `paddock_jobs::exit` (§Check's ban).
4. **`main`:** every shipped binary's `main` is `paddock_jobs::exit::main(|| ...)`, so a returning `main` never reaches
   the C runtime's `exit` with owners alive.
5. **Tauri:** `RunEvent::Exit` runs the phase's stop and report (§2 items 1, 2 and 4) through the shared shell
   (`paddock-shell`'s `on_run_event`, `crates/paddock-shell/src/builder.rs:1006`, and Debrief's own `lib.rs:801-807`
   until it is on the shell); tao's own `process::exit` is then the end step, with nothing native alive. If the phase
   reports a native overrun, the callback ends the process itself with the overrun end step instead of returning to tao.
   **Owners that need the main thread** (a window, a tray icon, an AppKit or WebView2 object) are not joined from a helper
   thread while the main thread waits, which would look like an overrun every time: they declare `main_thread = true`
   and are stopped on the main thread, in the `RunEvent::Exit` callback itself, before it waits for the helper. A restart
   uses **`AppHandle::request_restart`** (`app.rs:633`), which goes through `ExitRequested` and `Exit`, instead of
   `restart` (revision 1 banned `restart` and rebuilt it; `request_restart` already exists).
6. **The updater plugin:** tauri-plugin-updater's Windows install ends the process with `std::process::exit(0)`
   (`updater.rs:1050`). Every app (and `paddock-updater`) either installs only from `RunEvent::Exit`, after the phase has
   stopped the owners (Debrief's `updater::on_exit` already runs last there, `lib.rs:806`), or registers the phase's stop and
   report as `on_before_exit` (`:403-409`) so the plugin's own `exit` is the end step with nothing native alive. If the
   phase run from that hook reports a native overrun, the hook ends the process itself with the overrun end step (§2.5)
   instead of returning to the plugin's `std::process::exit`; the installer was already started, so the update goes on. WP-X1
   puts the hook in `paddock-updater` once; the C42 rule below rejects an updater builder without it.
7. **The single-instance plugin** exits a second launch before any owner exists (macOS `macos.rs:39`, Windows
   `windows.rs:160`, Linux `linux.rs:117`): allowed, registered in the ratchet as `before-owners` with its reason; the C42
   rule checks that the plugin is the first one registered (it is today in Dyno, `apps/dyno/app/src-tauri/src/lib.rs:617`).
8. **Watchdogs:** the shared quit watchdog and Debrief's copy call `exit(code, ExitWhy::Watchdog)` instead of
   `std::process::exit` (`manager.rs:355`, `lifecycle.rs:604`); a teardown step that timed out is reported as overrun, and
   if it is native the end step skips destructors.
9. **tokio:** an async `main` returns its code to a sync `paddock_jobs::exit::main` after `Runtime::shutdown_timeout`
   with the stop budget, never through the runtime's unbounded drop.
10. **Library code never ends the process.** `Dirs::current()`-style helpers that exit (Dyno `paths.rs:72-75`) return a
    `Result`; only a composition root (ADR 0037) calls `exit`.

### 4. The hand-made machinery is retired (rule 55)

`debrief-store-duck/src/shutdown.rs` becomes the store's `ExitOwner`: `stop_for_exit` sets `down`, fires the interrupts,
waits for the `Active` count on a condvar within the budget (no sleep loop), joins the store's threads and closes the
connections and databases before the end step, so the connection-leaking rule of `e3f6cdead` and the power-of-two
re-registration are no longer needed. Its `atexit` handler stays as a **backstop** that logs one `error` line ("exit
without the exit phase", with the calling thread's name) and ends with `_exit` (§2.3) instead of draining, until the
ratchet is empty in Debrief; then it is deleted (D-E6). The test helpers' `atexit` clean-ups become exit-phase steps of
the test process (the clean-up runs after the owners stopped, so `38b8f3edb`'s retry loop goes too, ER-12).

## Parallelism and cost (rule 51)

- No thread added in steady state; the registry is a mutex-held `Vec<Weak<..>>`, touched at registration and at exit.
- Exit latency: owners stop in parallel, so the phase costs the slowest owner up to the stop budget (2 s default), not
  the sum; today the store's `atexit` drain may already take up to 5 s (`shutdown.rs:17`), with a 1 ms sleep loop that the
  condvar replaces. A parent now waits up to its child's budget plus a margin instead of 150 ms before a kill; a
  well-behaved child ends sooner and the wait ends with it.
- The exit tests cost one child process per owner per round (20 rounds, about a dozen owners in Debrief, plus 20 rounds
  of each control); they run in the owners' crates only, not around every test.
- To measure and record (rule 48): Quit time p50/p99 before and after WP-X3 to WP-X5; the crash count of
  `debrief-store-worker` over a recorded number of runs after WP-X0 (expected 0).

## Risks

- A stop hook that blocks (a DuckDB `CHECKPOINT` on a large WAL) eats the budget; the store's owner interrupts first and
  checkpoints only if time remains, and the overrun end step skips destructors rather than crash. Data written before the
  last commit is safe either way (DuckDB and SQLite recover their WAL at the next open; from their documentation as known,
  not re-read for this draft; WP-X3 and WP-X4's exit tests check it by reopening, and WP-X3's Tantivy check by searching).
- A longer parent grace makes a stuck child take longer to kill (up to its budget plus margin); the budget-fit rule bounds
  it within the parent's own budget, and Quit stays bounded.
- A library that calls C `exit` itself (none found in the dependency reading beyond the updater and single-instance
  plugins handled above; C sources not searched) bypasses the phase; the `atexit` backstop logs it and ends with `_exit`.
- Parking a second exit caller forever is safe only because the first caller ends the process; a phase that itself
  hangs is bounded by the budget, and the Tauri watchdog stays as the outer bound.

# Addendum to the ADR 0025 amendment of 2026-11-10: the definition of `{src}`, and who computes it

- Status: Proposed addendum, written with RT-1 (`dev ci isolation`, Rust tooling plan). It makes one sentence of the amendment exact.
- Amends: `0025-2026-11-10.md` §1 ("`{src}` is the first 10 hex digits of the SHA-256 of the canonical workspace root").

## Definition

`{src}` is the first ten lower-case hex digits of the SHA-256 of the **root text** of the workspace folder, where the root text is:

1. the operating system's final path of the folder: `realpath` on Unix and macOS; on Windows `GetFinalPathNameByHandleW` (what Rust's
   `canonicalize` returns) with a leading `\\?\` removed;
2. with `/` as the only separator and no trailing `/`;
3. a Git-bash spelling (`/c/x`) is first read as the drive path `C:/x`, so `/c/x`, `C:\x` and `c:/x` are one folder;
4. the drive letter lower-cased.

The text is hashed as bytes with no trailing newline.

## One implementation

`./dev ci isolation source-key <dir>` prints the key. `path <kind> <name> --source <dir>` uses the same function. A shell caller (the
`build-folder.sh` of WP-1, deleted in WP-2 of docs/plans/shell-to-rust.md) asks `source-key` and never hashes on its own: a second implementation of this text is a
second copy of the mechanism (rule 55) and would give another folder for the same root. The shell scripts are gone (WP-2 of docs/plans/shell-to-rust.md), so the `ci-job-isolation` entry of
`docs/known-copies.toml` left with them; the one copy that remains is the wrapper's CI-home rule (`ci-home-rule`).

## Wiring note for the release step

The pinned tool is `"$PADDOCK_DEV"`: `acquire` writes it (`PADDOCK_DEV --print-binary`, which the binary answers with its own path), and
the release step must run `"$PADDOCK_DEV" ci isolation release`. The workflow wiring passes `PADDOCK_DEV_HOME` and
`PADDOCK_DEV_TARGET_DIR` under the CI home, so a build of the tool never lands inside a job folder.

## Addendum, 2026-11-15 (WP-2 of docs/plans/shell-to-rust.md): the shell kit is gone

`conformance/ci/kit.sh` and the shell scripts behind it are deleted; every action calls `./dev ci <step>`. What `kit.sh` did before the
tool existed is now the `dev` wrapper's, in one marked block each, with its tests in `tools/paddock-dev/tests/it/wrapper_ci.rs`:

- the tool and its build folder live in the CI home's `tools` folder on a host runner (the rule of `ci_isolation::home::ci_home`, held
  equal by a test; `ci-home-rule` in `docs/known-copies.toml`);
- a CI job without a read token builds the tool from source and never downloads;
- the tool's own build runs without the job's compiler wrapper and with 4 build jobs when the job has none yet;
- once the first step has pinned the tool (`PADDOCK_DEV`), a later `ci` command runs that binary as it is, with no hash, build or rustc;
- `./dev --job-setup ci <step>` marks the job (`PADDOCK_JOB_ABORTED=1`, tested by C117's guard on every later step) and says so once when a
  setup step fails, a tool that cannot be built included; the build-jobs and job-isolation (acquire) actions and setup-rust use it;
- a failed pinned-toolchain install writes `PADDOCK_TOOLCHAIN_FAILED=1` to the job's environment, so no later step tries the 900 s
  install again.

**Decision: a job whose tool cannot be built needs no clean-up the next job does not already do.** `host-cleanup` and `prune-build-folder`
run the pinned tool, which `ci isolation acquire` pins as its first act; if the tool cannot be built, `acquire` fails before it takes a
slot, so the job has no kept folder, no socket folder and no process of its own to clean up (its runner temp folder is the runner's to
delete). A job whose acquire succeeded has the pinned binary for every later step, whatever happens to the toolchain. What a failed
`host-cleanup` or `prune-build-folder` of a job that did acquire can leave behind is a build folder over its cap, which the next job's own
`prune-build-folder` caps again, and the socket and temp folders of the finished job, which the next `acquire` sweeps (with the kept folders
of idle slots, and the disk floor). A stray test process is the runner's to end with the job's process tree; `host-cleanup`'s patterns are
a second net, and `acquire` does not kill processes, so a process that survives both is not covered by this decision.

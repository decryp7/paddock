# Addendum to the ADR 0025 amendment of 2026-11-10: the definition of `{src}`, and who computes it

- Status: Proposed addendum, written with RT-1 (`dev ci isolation`, Rust tooling plan). It makes one sentence of the amendment exact.
- Amends: `0025-2026-11-10.md` §1 ("`{src}` is the first 10 hex digits of the SHA-256 of the canonical workspace root").

## Definition

`{src}` is the first ten lower-case hex digits of the SHA-256 of the **root text** of the workspace folder, where the root text is:

1. the operating system's final path of the folder: `realpath` on Unix and macOS; on Windows `GetFinalPathNameByHandleW` (what Rust's
   `canonicalize` returns) with a leading `\\?\` removed;
2. with `/` as the only separator and no trailing `/`;
3. a Git-bash spelling (`/c/x`) is first read as the drive path `C:/x`, so `/c/x`, `C:\x` and `c:/x` are one folder;
4. the drive letter lower-cased.

The text is hashed as bytes with no trailing newline.

## One implementation

`./dev ci isolation source-key <dir>` prints the key. `path <kind> <name> --source <dir>` uses the same function. A shell caller (the
`build-folder.sh` of WP-1 while it exists) asks `source-key` and never hashes on its own: a second implementation of this text is a
second copy of the mechanism (rule 55) and would give another folder for the same root. The mechanism is registered in
`docs/known-copies.toml` as `ci-job-isolation` (canonical: the Rust module; members: the three shell scripts).

## Wiring note for the release step

The pinned tool is `"$PADDOCK_DEV"`: `acquire` writes it (`PADDOCK_DEV --print-binary`, which the binary answers with its own path), and
the release step must run `"$PADDOCK_DEV" ci isolation release`. The workflow wiring passes `PADDOCK_DEV_HOME` and
`PADDOCK_DEV_TARGET_DIR` under the CI home, so a build of the tool never lands inside a job folder.

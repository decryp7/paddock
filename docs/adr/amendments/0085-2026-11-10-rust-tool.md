# Amendment to ADR 0085 (2026-11-10): the release-isolation tool is Rust, and what its review changed

- Status: Proposed (2026-11-10). An amendment to ADR 0085 (accepted 2026-11-10), which lives on
  `origin/docs/adr-0085-release-cache-isolation` (`3a49d49a1`). This file stands next to it until that branch lands, then is
  merged into the ADR's text.
- Related: ADR 0085 §4, §5, §5.1, WP-1a and WP-2; ADR 0022 (`./dev`; no new tooling in shell or Node); rule 71 / ER-33;
  `docs/plans/rust-tooling-2026-11-10.md` package RT-2.

## Decisions

1. **The tool is `./dev ci release-isolation setup|record|verify`, in Rust**
   (`tools/paddock-dev/src/release_isolation/`). Wherever ADR 0085 names `conformance/ci/release-isolation.sh`, the
   conformance test `conformance/test/release-isolation.test.mjs` or `node --test`, read this command and its Rust tests
   (the planted-leak fixture is `release_isolation::fixture`, reusable by ADR 0025's build-folder check). No `.sh` or
   `.mjs` file is written for it (user decision, 2026-11-10).
2. **Equality is on device and inode** (§5 item 2): the volume serial and the 128-bit file id on Windows
   (`GetFileInformationByHandleEx(FileIdInfo)`, falling back to the 64-bit index on `ERROR_INVALID_PARAMETER`), `st_dev`
   and `st_ino` on Unix. A folder that is another object fails whatever its times say.
3. **Freshness is a birth-time floor against the job's start**, not a change-time floor against `setup`'s start. The birth
   time (`Metadata::created()`: `statx` btime on Linux, creation date on APFS, `ftCreationTime` on Windows) does not change by
   itself and is not changed by writing into the folder, but it can be set on purpose (macOS `setattrlist` `ATTR_CMN_CRTIME`,
   APFS mtime back-dating, Windows `SetFileTime`): it guards against mistakes, not against an attacker. A directory's ctime moves with every entry written, so a ctime floor passes
   a kept folder that was written to during the run and, with `setup` as the start, fails the dev-tool folder that `./dev`
   built before `setup` ran. The job's start is the birth time of `$RUNNER_TEMP`; when that folder is on overlayfs (statfs magic `0x794c7630`, the Linux
   container case) it is the older of that and the birth time of `/`. Never a fallback to ctime.
   WP-3's positive-control run on the real Linux runner prints `stat -c %w` for `/tmp` and for a new folder under it (ER-33),
   to show that birth times are reported there. A file system that reports no birth time
   makes the check *broken* (ER-33), never a pass.
4. **Modes per kind.** `run` is allowed only for `dev-tool`, and only for a folder named `release-<GITHUB_RUN_ID>-<job>`;
   `off` only for `sccache` (and `libduckdb` where the job does not expect it); every other kind is `job` (inside the job
   folder). `setup --dev-tool <path>` records the dev-tool folder `./dev` was built into.
5. **The link scan.** Every `job` and `run` folder is walked without following links; any symlink or junction whose target
   is outside the job folder fails (an npm workspace link into the clone passes). `<clone>/node_modules` is absent, a real
   folder, or the ledger's `node-modules` folder. The registry cache and the Tauri tool folder are read without following
   links, and a link there is a finding.
6. **npm is asked, not guessed.** `npm config get userconfig` and `npm config get globalconfig` run bounded (10 s) with the
   job's environment; a missing or failing npm is *check broken*. As a second reading, `<prefix>/etc/npmrc` is checked for the
   node on PATH under both its PATH spelling and its canonical one (Homebrew's `bin/node` is a link into the Cellar).
7. **Unpinned Tauri tools fail.** Without `--tauri-pins`, `verify` is check broken. `--allow-unpinned-tauri` is for a local
   trial and is refused on a tag run and when `GITHUB_ACTIONS=true` with `PADDOCK_RELEASE_MODE=1`.
8. **Tracked configuration means the tag's file.** A cargo configuration counts as "of the tagged tree" only when the
   clone's `HEAD` equals `GITHUB_SHA` and `git diff HEAD` of the file is empty.
9. **The crate union is keyed by registry source**, and an index folder that matches no lock source is a finding; a
   `CARGO_HOME/git` with no git source in any lock file is a finding.
10. **Sccache statistics are required**: `sccache --show-stats` would start a server, so the wiring passes a stats file and
    its absence is check broken.

## Not done here (wiring, ADR 0085's integration step)

The workflow and action changes of WP-1a and WP-3 (`setup-rust`, `build-folder`, `kept-clone`, `node-caches`, the `./dev`
wrapper's `release-<run id>-<job>` folder) and the conformance check of §5 item 7 stay with that step.

# Amendment to ADR 0072 (2026-11-09): half-close and close only on the one owned handle; a stop never reconnects

- Status: Proposed (2026-11-09). An amendment to ADR 0072 (accepted 2026-11-09), which is not on `origin/main` yet: it
  lives on `origin/docs/adr-0072-ordered-close` (`62541d08a`). This file is merged into the ADR's text when that branch
  lands.
- Related: ER-21 / rule 40, ER-27, ER-28, ADR 0072 §2 step 4 (half-close), §4 (the MCP transport), §5 (C102, the endpoint
  register and the ending harness), ADR 0076 (owned background work).

## Trigger

Two `paddock-mcp` defects of CI run 7810 (Windows, three jobs per VM for the first time) share ADR 0072's subject, the end
of a connection, and neither is an instance in its table: one ended through a duplicated socket handle, one woke its
own accept loop by connecting again after the stop.

## Evidence

- **`0e92ad955`** (`fix(mcp)`, on `origin/fix/train1-shared-crate-ci`): the bridge (`crates/paddock-mcp/src/bridge.rs:129`,
  `:153`) used `try_clone` for its reader and its writer. Under load, `shutdown(Write)` on the writer's duplicate answered
  `WSAENOTCONN` (10057) though writes through it had worked; the bridge ignored the error, the app never saw the end, and
  both waited for ever (nextest TIMEOUT at 60 s, two listener tests). Measured on the Windows test VM: 9 of 10 runs of
  the new test and 46 of 48 cancelled-call runs hung before, 0 of 10 and 0 of 48 after. The fix shares one
  `Arc<TcpStream>` for reader, writer and end, and logs a failed half-close.
- **`76399b11a`** (`fix(mcp)`): `Serving::stop` ran the shutdown and `Drop` ran it again; the second pass connected to
  the closed listener's port (`loopback.rs:155`, the accept wake). On Windows a refused loopback connect is retried for
  about 2 s (2,163 ms measured on the VM), so every stop took 2.04-2.17 s there against 0.02 s on macOS, and a process
  that bound the freed port meanwhile received a stranger's connection.

## Change

1. **One owned handle ends a connection.** A connection's half-close and close are done only on the handle its owner
   holds; reader and writer threads share that handle (`Arc<TcpStream>`, or the transport's own shared shutdown event on
   pipes), never a `try_clone` copy. A copy may read; it never ends anything. A failed half-close or close is logged with
   the OS error (ER-27) and ends the connection by the ADR 0072 order anyway.
2. **A stop is idempotent and never reconnects.** The accept wake runs once, only while the accept thread is there; a
   second stop or the drop after a stop does nothing on the network. A wake that must connect uses the listener's own
   address only while the listener is held (rule 53 for names: an address freed is someone else's).
3. **Windows cost recorded.** A refused loopback connect costs about 2 s on Windows: no stop, retry or probe path may
   depend on one (ADR 0072 §7 bounds gain this line).
4. **`paddock-ipc` Unix closer** moves to the same shape (the owned stream behind an `Arc`, closed through it) in ADR
   0072's M1, so the family has one way to end a connection on every OS. This **adds work to M1** (0.5 day below), and
   M1 gates Dyno's next tag under 0072's D8.

## Check

- **C102** (ADR 0072 §5): the endpoint register `docs/ipc-endpoints.toml` gains, per endpoint, its owned handle; the
  check fails on `shutdown(` or a close called on a value that came from `try_clone` in the same function or field
  (a syn pass), and on **a connect inside a `stop` or `Drop` of a type that holds a listener** (a `TcpStream::connect`
  or `connect_timeout` reached from either; the one listed wake site must be guarded by the accept thread still being
  there).
- **Ending harness:** a stop-twice case per listener (the second stop makes no connection: a test binds the freed port and
  sees nothing, as `a_stopped_listener_never_connects_to_its_old_port_again`), and the many-bridges case
  (`every_bridge_ends_when_its_host_closes_even_with_many_at_once`, 32 at once) on the Windows runner.
- **Positive control:** `git show 0e92ad955^:crates/paddock-mcp/src/bridge.rs` must be flagged, its fix not;
  `76399b11a^:crates/paddock-mcp/src/loopback.rs` must be flagged for the second wake.

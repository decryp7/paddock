## The class (ER-21)

Privileged code trusts a folder tree because it checked or locked only the top folder. Folders made earlier in
`C:\ProgramData` inherit `(A;CIID;DCLCRPCR;;;BU)`, which lets Users add files and folders. A standard user then plants
what SYSTEM runs or reads, or swaps a folder for a junction during a delete.

## Comparable practice (ER-37)

Fetched 2026-11-11:

- **Windows Installer.** `LockPermissions` and `MsiLockPermissionsEx` give a listed object "an explicit security
  descriptor", and the rest "the attributes of its parent or container object"
  ([1](https://learn.microsoft.com/en-us/windows/win32/msi/lockpermissions-table),
  [2](https://learn.microsoft.com/en-us/windows/win32/msi/msilockpermissionsex-table)). Nothing repairs a tree.
- **`SetNamedSecurityInfo`** "propagates any inheritable ACEs to existing child objects"
  ([3](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setnamedsecurityinfow)). Through a planted
  hard link that is CVE-2019-0841, which is why `lock_dir_with` (`trust_real/windows.rs:194`) sets one object with
  `SetKernelObjectSecurity`.
- **ProgramData** is "available to anyone using the computer"
  ([4](https://learn.microsoft.com/en-us/windows/win32/shell/csidl)). Project Zero: users can "create new files in its
  subdirectories" ([5](https://projectzero.google/2015/12/between-rock-and-hard-link.html)). I found no Microsoft page
  on how a service should lock its subfolder.
- **Docker** (Windows): `setupDaemonRoot` calls `MkdirAllWithACL` with `SddlAdministratorsLocalSystem`
  (`"D:P(A;OICI;GA;;;BA)(A;OICI;GA;;;SY)"`), for created folders only (`if dir.IsDir() { return nil }`)
  ([6](https://raw.githubusercontent.com/moby/moby/master/daemon/daemon_windows.go),
  [7](https://sources.debian.org/src/docker.io/26.1.5%2Bdfsg1-9/engine/pkg/system/filesys_windows.go)). On Unix it
  chmods the top folder to 0711 ([8](https://raw.githubusercontent.com/moby/moby/master/daemon/daemon_unix.go)).
- **containerd** chmods its root to 0700 on upgrade, top folder only
  ([9](https://raw.githubusercontent.com/containerd/containerd/main/cmd/containerd/server/server.go)).
- **GitHub Actions runner** runs as NETWORK SERVICE and adds one inheritable entry for a group, with no walk
  ([10](https://raw.githubusercontent.com/actions/runner/main/src/Runner.Listener/Configuration/NativeWindowsServiceHelper.cs),
  [11](https://docs.github.com/en/actions/hosting-your-own-runners/managing-self-hosted-runners/configuring-the-self-hosted-runner-application-as-a-service)).
- **Mozilla Maintenance Service** (CVE-2019-11736) is the one SYSTEM service found that repairs an existing
  ProgramData tree. It moves the folder aside, recreates it, moves the contents back, checks for hard links and locks
  files in use ([12](https://bugzilla.mozilla.org/show_bug.cgi?id=1551913)).

**The cheapest standard option** is rights at creation, top folder only (`create_dir_protected` here), and refusing a
tree this version did not create (about 3 days). The user chose Mozilla's shape (D1 (a)), at about 12.5 days.

## Decision

### API: `paddock_service::privileged::adopt`

```rust
pub fn adopt_tree(port: &mut dyn TreePort, parent: &str, name: &str, policy: &TreePolicy) -> Result<Adopted, AdoptError>;
pub fn drain_quarantine(port: &mut dyn TreePort, parent: &str, name: &str, budget: Budget) -> Drained;
pub fn reset_tree(port: &mut dyn TreePort, parent: &str, name: &str) -> Result<(), AdoptError>; // Dyno's per-install reset

pub struct TreePolicy { pub id: &'static str, pub version: u32, pub keep: &'static [Keep],
                        pub max_entries: usize /* 10_000 */, pub max_time: Duration /* 30 s */ }
pub struct Keep { pub name: &'static str, pub what: What, pub need: Need }
pub enum What { File, Folder(&'static [Keep]) /* recursive; empty = every entry */, Roots /* see below */ }
pub enum Need { Required, IfPresent /* only where dropping would widen access */, Optional }
pub enum AdoptError {
    Container(Untrusted),                       // the parent fails verify_container: nothing touched
    Required { path: String, reason: Reason },  // a Required or IfPresent entry fails; it stays in the aside
    Busy { path: String, code: u32, holders: Vec<Holder> }, // after the retries; Holder = process name + pid only
    Squatted { path: String, owner: String },   // <name> appeared during the adoption
    TooLarge { examined: usize, limit: usize },
    Io { step: Step, path: String, error: String },
}
```

**`TreePort`** is a new small port; `TrustPort` is unchanged. Every operation is relative to a held handle (NT
`RootDirectory`, `openat`), and every open uses `FILE_OPEN_REPARSE_POINT` / `O_NOFOLLOW`. The operations are
`open_parent`, `list(dir)` (name, `Node`, link count), `open_child`, `create_dir_in`, `move_into`, `lock(dir)` (one
object, no propagation), `write_owner_only`, `read_checked` and `delete(dir, name)` (POSIX delete by handle).

- Kept files are opened with `FILE_SHARE_READ` only and held through the move.
- **Invariants:** `create_dir_in` and `move_into` are create-new and no-replace. An existing name is an error and is
  never adopted.
- **Names:** generated names carry a random 64-bit decimal: `.new-<r>`, `.adopting-<r>`, `.untrusted-<r>`, which
  `inside_aside` already accepts. After 8 collisions the step fails with `NoFreeName`.
- **The fake:** `FakeTree` (in `trust_fake.rs`) shares `FakePort`'s nodes and SDDL fixtures, and adds alternate
  streams and extended attributes.

**The checks, each made on the open handle:**

- **Kept file:** a regular file, not a reparse point, link count 1, owner SYSTEM, Administrators or TrustedInstaller,
  and the full inside rule (`check_windows`/`check_unix`).
- **Kept folder:** a real folder, not a reparse point, with a trusted owner. Its DACL is ignored, because the folder
  is **rebuilt**: a new protected folder gets the entries that pass, and the old object (its streams, extended
  attributes and held handles) stays in the aside.
- **`Roots`:** a child moves into the new folder only if it passes the kept-folder rule, and it then gets its own
  adoption with the new folder as its parent. A child that fails (a user-owned folder, a junction, a file) stays in
  the aside and goes into `left`.
- **A kept name already in the new tree:** the new tree's entry wins, and the aside's stays and goes into `left`.

### Steps (single-flight per tree; the journal lives until the last step)

| # | Step | After a crash here, step 1 does |
|---|---|---|
| 0 | Open the parent by handle; `verify_container`; else `Container` | — |
| 1 | **Finish or resume** (see below) | — |
| 2 | Create `<name>.new-<a>` (protected at creation). Write the journal `.paddock-adopting` in it (owner-only: `{id, version, aside: <b>}`). | resume `.new-<a>` from the journal |
| 3 | Rename `<name>` to `<name>.adopting-<b>` by handle (skipped if `<name>` is absent) | journal: the aside exists, or `<name>` is still in place |
| 4 | Move back the kept set from the aside into `.new-<a>` | the moves are atomic; re-list and go on |
| 5 | Write the marker `.paddock-adopted` `{id, version}` in `.new-<a>`. The journal stays. | the journal and marker in `.new-<a>`: go to 6 |
| 6 | Rename `.new-<a>` to `<name>` with no-replace. If `<name>` exists, the result is `Squatted`. | the journal is in `<name>`: go to 7 |
| 7 | Rename `.adopting-<b>` to `.untrusted-<b>` | go to 8 |
| 8 | Delete the journal inside `<name>` | done |

**Step 1, finish or resume.** "Trusted" means a real folder (not a reparse point) whose owner, read by handle without
following a link, is SYSTEM or Administrators.

- **`<name>` is trusted and holds a valid marker of this `id` and `version`:** if it also holds a journal, finish
  steps 7 and 8. Return `already`.
- **Otherwise, if a trusted `.new-<a>` holds a valid journal:** resume it at the first step not done, whatever its
  marker. If `<name>` is in the way at step 6, it is a squatter: it is moved to that root's one squat aside (below),
  and step 6 is retried. A journal of an older `version` is finished first, and then the tree is adopted again.
- **Otherwise:** a new adoption starts at step 2.
- A trusted `.new-*` without a journal (crashed before the journal was written: it is empty) and a trusted
  `.adopting-*` that no journal names go to `.untrusted-*`. Nothing a journal names is ever quarantined, so the tree
  holding `pitcrew.toml` cannot be.

**Retries and Busy.** Steps 3, 4 and 6 retry when the error is busy. Busy means a sharing violation
(`STATUS_SHARING_VIOLATION`, 32) or an access denial (`STATUS_ACCESS_DENIED`, 5) **after** the open with `DELETE` has
already succeeded, which shows that the service holds the right and something else is in the way.

- The waits are 0.5, 1, 2, 4, 8 and 8 s: 6 retries, 23.5 s in total. Then the result is `Busy` with the raw code.
- **Holders:** a bounded walk by handle lists up to 2,000 files below the root, for at most 2 s. Restart Manager
  (`RmStartSession`, `RmRegisterResources`, `RmGetList`) registers them, and only the process name and pid are kept.
- **Fallback:** Restart Manager sees files only, not folder handles such as a shell's current folder. When it names
  nobody, the message is "a program holds a folder or file below <path> open".
- The tree's worker retries every 60 s. Only one adoption of a tree runs at a time, and a retry resumes the same
  `.new-<a>` from its journal; it never makes a new one.

**Draining (D2 (a)).** Only the latest failed aside per root is kept, named in the error. It is drained after that
root's next successful adoption, and a successful aside is drained at once.

- **How:** `drain_quarantine` locks each folder by handle before it lists it, then opens and deletes each child
  relative to that held handle with `FILE_OPEN_REPARSE_POINT`, never by path. A link is deleted as itself. Nothing is
  read.
- **Privileges:** a user-owned object whose DACL leaves SYSTEM out is opened with backup intent, after
  `SeBackupPrivilege` and `SeRestorePrivilege` are enabled on the drain thread only. If that fails,
  `SeTakeOwnershipPrivilege` takes ownership, then the object is locked. LocalSystem holds all three, disabled by
  default.
- **Bounds:** bulk work (rule 52). At most 50,000 entries or 60 s per pass. It stops after 20 passes with no progress
  or 200 passes in all, and then the aside is left and logged.

**Squatters.** A root keeps one squat aside. A new squatter is moved there, and the older one is drained. Each owner
SID is logged once.

**Logs (ER-27).** Until the data root is adopted, nothing is written into either the old or the new tree:

- The lines go to a bounded in-memory buffer (1,000 lines) and to the OS log (`paddock_service::os_log`, ADR 0054
  §2.3: the Application event log on Windows).
- The buffer is flushed into the new `logs` once the root is installed.
- Each step logs its outcome and duration, with the root, policy id and version, an adoption id, `kept`, `left` and
  the aside name. Only entry names are logged, never contents.

### Pitcrew (the Pitcrew agent adopts this for round-3 P1-1)

**Start order (P1-B).** T3 changes `platform/windows.rs:96-110` and `host.rs:29` on the branch:

- The service reports **Running** right after its control handler is registered.
- The host serves IPC at once in a service-level state, **`Securing`** or **`Busy`** with the holders.
- The data-root adoption runs on the worker, with the 60 s retry.
- The supervisor, and anything that reads the configuration, starts only after it ends.
- SCM therefore never waits on adoption, and a busy data root never becomes a failed start or a restart-on-failure
  loop.

**What is adopted:**

- **The data root** `%ProgramData%\Pitcrew`. This replaces `ensure_protected_root`.
  - Kept: `pitcrew.toml` (Required), `pitcrew.toml.bak` and `state.json` (Optional: dropping them loses the backup,
    the run history and the "wanted" flags, never access), and `runners` (`Roots`).
  - `logs` and `logs\blocked` are not kept. They are made again inside the new root.
- **Each child of the new `runners`.**
  - A configured runner is adopted on its own worker, and the runner is blocked until its adoption is done.
  - A child that no configuration names (a removed runner) is quarantined.
  - **No `runners` child stays weak.**
  - Kept in a runner: `.runner` and `config.yaml` (Required; fix-it: register again) and `bin` (`Folder`, Optional:
    the managed binary is installed again from its checked release source).
  - `work`, `cache` and `logs` cost one rename each. This replaces `settle_runner_dir`.

**The gate (P1-D).** One function, `Request::tree_scope() -> Scope { None, DataRoot, Runner(name) }`, is a `match`
naming every request. Every request and every housekeeping path asks `TreeGate::ready(scope)` first. Until the data
root is done, only `Hello`, `Status` and `Subscribe` are served, and they report the service state. Until a runner is
done, every request whose `folder_runner()` names it is refused with "securing" or "busy", including `CleanDisk`.

The housekeeping paths that ask the gate are:

- the probe tick;
- the update check and update install;
- disk and cache scans and cleaning;
- log tail and log search;
- reveal;
- the blocked-log writer.

**Serialising against `Register`, `AddRunner` and `RemoveRunner`:** each takes the runner's adoption lock.

- `Register` and `AddRunner` wait until that runner's adoption is done.
- `RemoveRunner` cancels a pending adoption at the next step boundary. The runner's folder is then quarantined (it
  is no longer configured), so it never stays weak.

`check_runner_folder` stays as the per-request check. A runner folder outside the data folder is checked, never
adopted, and ADR 0004's limit (3) then applies only there.

### Dyno helper

- `C:\ProgramData\Dyno` keeps `Helper` (`Folder`). `Helper` keeps:
  - `config.json`: Required at start (a failure leads to Repair), Optional at Repair, where setup writes it fresh.
  - `policy.toml`: IfPresent. Dropping it would widen visibility to the default, so a failing `policy.toml` blocks
    the helper until Repair. That is a denial of service by design; the admin's next step is Repair.
  - `audit.jsonl`: Optional (dropping it loses history, not access).
- `helper.log`, `tools` and `staging` are not kept.
- The helper starts serving only after `Helper` is adopted; its lines go to `os_log` meanwhile. `TrustGuard::ensure`
  and `move_aside` are deleted. `reset_root` becomes `reset_tree` on `TreePort`.

**Unix:** root-owned 0755 system folders. Adoption runs the bounded `verify_tree`, and when it passes it only writes
the marker. The Unix `TreePort` is costed as test infrastructure.

## Consequences

- One mechanism. ADR 0004's limit (3) is gone for trees in the data folder, as are Dyno's repair copy and the second
  `.untrusted` sweep.
- An upgrade from `pitcrew-v1.0.1` loses old job folders, caches and logs (release notes).
- **Denial of service by a standard user, accepted:**
  - **Holding a handle** below a tree keeps that tree blocked. The log names the process and pid when Restart Manager
    can. The admin's next step is to end it or log the user off; the 60 s retry then finishes.
  - **Winning the squat race** at step 6 delays the start by one 60 s retry each time. The admin's next step is to
    deal with the account whose SID is logged.
  - **A failing `policy.toml`** blocks the Dyno helper until Repair.
- The guarantee rests on four things: adoption before the first trust, the create-new invariant, the gate on every
  SYSTEM path, and nothing ever reading inside an aside. The aside is not unreachable, because traversal is not
  checked for users; it is never read.

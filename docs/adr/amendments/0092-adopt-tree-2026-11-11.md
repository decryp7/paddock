# Amendment to ADR 0092 (2026-11-11): a privileged component adopts a folder tree once, before it trusts it

- Status: **Proposed 2026-11-11.** The user decided on 2026-11-11 to build one shared mechanism in
  `crates/paddock-service/src/privileged/` and to move Pitcrew and Dyno's helper folder onto it. This note gives its
  shape. Nothing here is built yet. ER-23 does not apply (no drawings).
- Amends: ADR 0092 §4 (S4: a process with more rights reads or writes where one with fewer rights can change things,
  and the proposed rule 75). It adds the case §4 does not cover: a tree that an **older version** made with weak rights.
- Why an amendment and not a new ADR: the class is 0092's S4, and the mechanism extends the canonical S4 code §4
  already names (`paddock_service::privileged::trust`). It adds no rule, register or gate. Rule 75 is still only
  proposed (ADR 0092 §4, WP-9). It is not in `docs/rules.md` on `origin/main`.
- Evidence: read on 2026-11-11 with `git show`, `git grep`, `git merge-base` and `git tag --contains` after
  `git fetch`. Paths without a branch are at `origin/main`. Nothing was built or run. The heads, re-read right before

## The class (ER-21)

Privileged code (a SYSTEM service or a root helper) trusts a folder tree because it checked or locked only the top
folder. On Windows, folders made earlier inside `C:\ProgramData` inherited `(A;CIID;DCLCRPCR;;;BU)`, which lets
Users add files and folders. A standard user can then plant content that SYSTEM later runs or reads, or swap a folder
for a junction while SYSTEM deletes. Instances:

| # | Where | State |
|---|---|---|
| 1 | Dyno helper data folder made by builds before `790c6e100` (the fake's `SDDL_DYNO_HELPER_UNFIXED`, `trust_fake.rs:190`) | `790c6e100` locks it; `git tag --contains` lists only `dyno-v1.1.0`. Dyno's own copy of a repair (`TrustGuard::ensure`, `move_aside`, `apps/dyno/crates/dyno-helper/src/protect.rs:166-296`) walks and moves entries aside. |
| 2 | Pitcrew `%ProgramData%\Pitcrew`, `data\runners` (ADR 0004, first amendment) | shipped in `pitcrew-v1.0.1` (`paths.rs:3` at that tag: "the folder is writable by"). |
| 3 | Pitcrew rounds 2 and 3, `origin/fix/pitcrew-service-caller-check` `ba0fda293` | `ensure_protected_root` (`protected.rs:257`) locks the top and checks named files. `settle_runner_dir` (`:138`) and `check_runner_folder` (`:70`) lock and check only the direct children. ADR 0004's second amendment says so in its own limit (3): "an older entry deeper down with a weak ACL would not be detected". |

Two more gaps in the shared code: `walk_no_follow` (`trust_real/mod.rs:32`) reads by path (`read_dir`, then
`node(path)`), so a folder swapped for a junction between the two calls is entered. And no check refuses a hard link
(link count above 1). Mozilla's CVE-2019-11736 had exactly that shape.

## Comparable practice (ER-37)

Sources fetched on 2026-11-11:

- **Windows Installer.** `LockPermissions` and `MsiLockPermissionsEx` give each listed file, registry key or created
  folder "an explicit security descriptor". An object that is not listed gets "the attributes of its parent or
  container object" ([LockPermissions](https://learn.microsoft.com/en-us/windows/win32/msi/lockpermissions-table),
  [MsiLockPermissionsEx](https://learn.microsoft.com/en-us/windows/win32/msi/msilockpermissionsex-table)). Nothing
  walks or repairs an existing tree.
- **`SetNamedSecurityInfo`.** "the system automatically propagates any inheritable ACEs to existing child objects"
  ([docs](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setnamedsecurityinfow)). Propagating
  through a hard link a user planted rewrites the target's DACL. That is the CVE-2019-0841 shape, and the reason
  `lock_dir_with` (`trust_real/windows.rs:194`) uses `SetKernelObjectSecurity` on one folder.
- **ProgramData.** Microsoft describes it as data "available to anyone using the computer"
  ([CSIDL_COMMON_APPDATA](https://learn.microsoft.com/en-us/windows/win32/shell/csidl)). Project Zero: "ProgramData's
  default permissions allow a normal user to create new files in its subdirectories"
  ([Between a rock and a hard link](https://projectzero.google/2015/12/between-rock-and-hard-link.html)). I found no
  Microsoft page that says how a service must lock its subfolder.
- **Docker.** On Windows, `setupDaemonRoot` calls `MkdirAllWithACL(root, "D:P(A;OICI;GA;;;BA)(A;OICI;GA;;;SY)")`. The
  descriptor applies only to folders it creates, and "if dir.IsDir() { return nil }"
  ([daemon_windows.go](https://raw.githubusercontent.com/moby/moby/master/daemon/daemon_windows.go),
  [filesys_windows.go (Debian 26.1.5)](https://sources.debian.org/src/docker.io/26.1.5%2Bdfsg1-9/engine/pkg/system/filesys_windows.go)).
  On Unix it runs `chmod 0711` on the top folder only
  ([daemon_unix.go](https://raw.githubusercontent.com/moby/moby/master/daemon/daemon_unix.go)).
- **containerd** makes its root 0700 and then chmods it, "needed for upgrading from an older release that created the
  dir with 0o711". It touches the top folder only
  ([server.go](https://raw.githubusercontent.com/containerd/containerd/main/cmd/containerd/server/server.go)).
- **GitHub Actions runner.** The service runs as NETWORK SERVICE by default (`GetDefaultServiceAccount`). It adds one
  inheritable FullControl entry for a local group to the runner and work folders, with no walk and no reset
  ([NativeWindowsServiceHelper.cs](https://raw.githubusercontent.com/actions/runner/main/src/Runner.Listener/Configuration/NativeWindowsServiceHelper.cs),
  [service docs](https://docs.github.com/en/actions/hosting-your-own-runners/managing-self-hosted-runners/configuring-the-self-hosted-runner-application-as-a-service)).
  The tree belongs to an account that is less than SYSTEM.
- **Mozilla Maintenance Service (CVE-2019-11736).** This is the one comparable SYSTEM service that had to repair an
  existing `ProgramData` tree. The fix "no longer changes directory permissions directly": it moves the folder aside,
  recreates it with the right permissions and moves the contents back, checks for hard links, and locks files while
  in use ([bug 1551913](https://bugzilla.mozilla.org/show_bug.cgi?id=1551913)).

**The cheapest standard option** is what Docker, containerd and MSI do: set the descriptor when the folder is
created, touch the top folder only, and trust the tree because nobody else could write it from the start. Paddock
already has this: `create_dir_protected`. It does not cover our case, because trees made by `pitcrew-v1.0.1` and
early Dyno helper builds already hold weakly protected entries deep down. The cheap answer to that is to refuse any
tree this version did not create and tell the administrator to delete it (D1 (b)). What this note builds is Mozilla's
answer: move aside, recreate, move back.

## Decision

### API: `paddock_service::privileged::adopt`

```rust
pub fn adopt_tree(port: &mut dyn TreePort, root: &str, policy: &TreePolicy) -> Result<Adopted, AdoptError>;
pub fn drain_quarantine(port: &mut dyn TreePort, parent: &str, name: &str, budget: Budget) -> Drained;

pub struct TreePolicy {
    pub id: &'static str,              // "pitcrew-runner"; written in the marker
    pub version: u32,                  // a higher version adopts the tree again
    pub keep: &'static [Keep],         // entries of the root moved back if they pass the inside rule
    pub max_entries: usize,            // kept entries examined in total (default 10_000)
    pub max_time: Duration,            // default 30 s for the move-back
}
pub struct Keep { pub name: &'static str, pub kind: FileKind, pub required: bool }
pub struct Adopted { pub already: bool, pub kept: usize, pub left: Vec<String>, pub aside: Option<String> }
pub enum AdoptError {
    Container(Untrusted),                          // the way to the root fails verify_container: nothing touched
    Required { path: String, reason: Reason },     // a required entry is missing or fails; it stays in the aside
    TooLarge { examined: usize, limit: usize },    // over max_entries or max_time; nothing drained
    Io { step: Step, path: String, error: String } // Step: Examine, MoveAside, Create, MoveBack, Marker, Finish
}
```

Anything that is not named in `keep` is not moved back. That covers `work`, `cache`, `logs`, foreign entries and
anything unknown, so the policy needs no list of disposable names, and a huge tree is never walked. The decision
core is pure over a new small port, `TreePort`. The port works on handles: `open_root`, `list(dir)` (each entry gives
its name, `Node` and link count), `open_child(dir, name)` (never follows a link), `create_dir_in(dir, name)` (the
protected descriptor is given at creation), `move_into(entry, dir, name)` (renames by handle, never replaces),
`write_marker` and `read_marker` (owner-only, checked from the handle), and `remove_no_follow(entry)`. `TrustPort`
stays as it is (interface segregation). The fake (`FakeTree` in `trust_fake.rs`) is built on the same nodes and SDDL
fixtures as `FakePort`. Its handles name an object, not a path, so a swap after an open is visible to the test.

### Steps (each is atomic or idempotent; the marker is written last)

1. If `<root>\.paddock-adopted` passes the inside rule, is a real file with link count 1 and parses with this `id`
   and `version`, return `already` after the cheap check (the root plus its direct children, today's
   `check_runner_folder`). The marker is read by handle. A forged marker is owned by a user or is a hard link, and is
   ignored.
2. Check the root's parent with `verify_container`. If it fails, return `Container` and change nothing.
3. **Resume.** If a sibling `<name>.adopting-<n>` owned by SYSTEM or Administrators exists, an earlier run stopped
   after step 4: continue at step 5 with it. A look-alike a user made is not trusted and is left alone, as
   `sweep_aside` already does.
4. Rename the root, by handle, to `<name>.adopting-<n>`. A user holding a handle inside the root makes the rename fail
   with a sharing violation, which is an `Io` error and the tree stays blocked. The VM row records it.
5. Create the root if it is missing, with the protected descriptor given at creation. Never `lock_dir`, never
   propagate.
6. For each `Keep` entry, open it relative to the held aside handle without following a link. Check it on that same
   handle:
   - not a reparse point;
   - link count 1;
   - owner SYSTEM, Administrators or TrustedInstaller;
   - no write, delete or ownership right for anyone else (the existing inside rule, `check_windows`/`check_unix`).

   Move it into the new root by handle. A kept folder is rebuilt the same way, one level at a time: a new protected
   folder, its passing entries moved in. A held handle a user opened in the old folder then points into the aside,
   never into the new tree. An entry that fails stays in the aside and is named in `left` and in the log. A required
   one returns `Required`, and the component stays blocked with a fix-it message.
7. Write the marker (unique temp name, created new, renamed inside the held root).
8. Rename `<name>.adopting-<n>` to the existing `<name>.untrusted-<secs>-<n>` form. `verify_tree` already skips it
   (`inside_aside`), and `drain_quarantine` removes it later.

A crash at any point resumes at step 1 or 3 and ends in the same state; a test runs every crash point. The aside is
not unreachable: a user can still reach a folder inside it by path, because Windows does not check traversal for
them. Nothing inside it is ever read, run or followed. Draining removes each entry by handle, and removes a link by
its name, never its target. **The component stays blocked until `adopt_tree` returns `Ok`.**

### Pitcrew (the Pitcrew agent adopts this for round-3 P1-1)

- **Data root** `%ProgramData%\Pitcrew`, at service start, before anything is read. It replaces `ensure_protected_root`.
  Kept: `pitcrew.toml` (required) with its backup and `state.json`, and `runners` as a folder entry: only the folder,
  each runner inside is adopted on its own. Not kept: `logs`, and with it the old `logs\blocked`. The service makes
  them again inside the new root, where they inherit the protected entries (SY and BA full, BU read and execute).
- **Each service runner under `data\runners\<name>`**, on a worker after the service reports running (the 30 s start
  limit). The runner is shown blocked, "securing its folder", until it is done. It replaces `settle_runner_dir`.
  Kept: `.runner` and `config.yaml`, both required (fix-it: register the runner again), and `bin` (optional). If the
  managed binary is not moved back, the existing update path installs it again from its checked release source
  before the first start. Not kept: `work`, `cache`, `logs`, which become one rename each.
- `check_runner_folder` stays as the cheap check on every request. A runner folder **outside** the data folder (for
  example under Program Files) is the administrator's choice: it is checked, never adopted. Limit (3) of ADR 0004's
  second amendment then applies only there, where everything inherits Program Files' rights.

### Dyno helper

- `C:\ProgramData\Dyno` (the vendor folder) keeps only `Helper`. `Helper` keeps `config.json`, required at start (a
  failure leads to Repair) and not at Repair (setup writes it fresh). `tools` and `staging` are not kept: tools are
  downloaded again and checked before every use.
- This replaces `TrustGuard::ensure`, `move_aside` and `reset_root` (one copy fewer, ER-22). The per-run
  `verify_tree` moves to `TreePort::list` (by handle), and Dyno gains the hard-link refusal. macOS and Linux keep
  their root-owned 0755 folders. Users cannot plant there, so on Unix the adoption is one pass with nothing to move.

### Bounds and logs (ER-20, ER-27)

- The move-back examines only what the policy keeps. Pitcrew keeps 2 files and `bin` per runner, Dyno keeps 1 file.
  The caps are `max_entries` (10_000) and `max_time` (30 s); over either, the result is `TooLarge` and the tree stays
  blocked.
- A `work` tree of any size costs one rename.
- `drain_quarantine` is bulk work: utility QoS, `BELOW_NORMAL` on Windows (rule 52). Each pass is capped at 50_000
  entries or 60 s, then the next pass continues. It logs a growing count every 5 s (the total is unknown).
- Every step logs its outcome and its duration in ms. The fields are the root, the policy `id` and version, an
  adoption id, `kept`, `left` and `aside`. An error carries its cause and the next step. No file contents are logged,
  only entry names.

## Tests

The failing tests come first (ER-11). Fake `TreePort` cases, in `paddock-service`:

1. **Inherited grandchild:** `bin\plugins` carries the `SDDL_DYNO_HELPER_UNFIXED` entries, with a `evil.dll` owned by
   a user. The new `bin\plugins` is protected, `evil.dll` is in `left`, and `lock_dir` is never called.
2. **Junction in the middle:** `bin` is a junction, and a second case swaps an entry for a junction between `list`
   and `move_into`. Nothing is followed, the swapped object is not the one moved, and the target is untouched.
3. **Hard link:** `config.yaml` is owned by SYSTEM but has a link count of 2. The result is `Required`, and the entry
   stays in the aside.
4. **Interrupted adoption resumes:** the fake fails at call *k*, for every *k*. A second run ends in the same tree,
   marker and aside as an uninterrupted run.
5. A forged marker (owned by a user, or a hard link) and an old `version` both adopt again. A valid marker means no
   rename.
6. An untrusted container means no call that changes anything.
7. `drain_quarantine` removes a link by its name, keeps the target and stops at its budget.

Real-port tests on the dev OS (Unix: symlink, hard link, `O_NOFOLLOW`) and on the Windows CI runner (junction, hard
link, a held handle). **Windows test VM rows** (`docs/testing/windows-test-vm.md`; `paddock-test` is the standard
user):

- **V1, positive control (ER-33):** install `pitcrew-v1.0.1`. As `paddock-test`, plant a file in
  `runners\a\bin\plugins`, a junction in `runners\a\cache` and a file in `logs\blocked`. Upgrade. The runner is
  blocked, then runs. Nothing planted is in the new tree, and the junction target's hash is unchanged.
- **V2, plant after adoption:** as `paddock-test`, try to create a file, a folder, a junction and a hard link in
  every folder of the adopted tree. Every attempt is denied (V1 shows the probe can see a success).
- **V3:** `paddock-test` holds a handle in `work` across the upgrade. Record either the sharing violation (the tree
  stays blocked) or that a write through the handle lands in the aside.
- **V4:** kill the service during the move-back and during the drain. The restart resumes.
- **D1:** a Dyno helper folder set to `SDDL_DYNO_HELPER_UNFIXED` with `icacls`, with planted entries. The helper's
  start refuses, and Repair adopts it.

## Decisions for the user

- **D1, scope.** (a) **Adopt, as above (8 days, recommended).** It keeps runner registrations and Dyno's config
  across the upgrade, removes Dyno's copy, and matches the one comparable SYSTEM service that had this bug (Mozilla).
  (b) Common practice, about 3 days: create protected at first use, write the marker, and **refuse** any tree without
  it, with the fix-it step "delete this folder and register the runner again". This fits a personal tool and "no
  migrations before v1". It costs a hand step on every machine that has `pitcrew-v1.0.1`.
- **D2, the aside of a failed adoption.** (a) **Keep it, named in the error, until the next successful adoption of
  the same root; drain every successful one at once (recommended).** (b) Keep all asides for 7 days.

## Consequences

- One mechanism, with no new rule, register or gate. ADR 0004's limit (3) is gone for trees inside the data folder,
  and so are Dyno's own repair code and the `.untrusted` sweeping logic in two places.
- An upgrade from `pitcrew-v1.0.1` loses old job folders, caches and logs (moved aside, then drained). Its release
  notes say so.
- The guarantee rests on the adoption running before the first trust, and on nothing ever reading inside an aside.

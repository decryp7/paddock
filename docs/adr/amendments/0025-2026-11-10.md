# Amendment to ADR 0025 (2026-11-10): a kept build folder is keyed by the source it builds

- Status: Proposed (2026-11-10). Drafted at the user's request of 2026-11-10 (ER-21 redesigns). Needs the decisions below
  and an independent review before any build.
- Amends: ADR 0025 (CI job isolation), §2 (kept folders per slot) and §4 (declared lists), whose premise "cargo's build
  folder, whose fingerprints hold absolute paths" is wrong for workspace members (Evidence 2). ADR 0025 is still
  `Proposed` in its own header while its code runs on every host job; this amendment changes the code it describes.
- Why 0025 and not 0080 or 0085: the defect is in how a kept folder is named (`kept-folders.txt`, `job-isolation.sh path`,
  `build-folder.sh`), which ADR 0025 owns. ADR 0080 only added the second source root (the kept clone) that exposed it, and
  ADR 0085's release mode already makes tag runs immune (their build folder is job-local, its §4 item 1, and its T5 names
  this very class for tags). Branch runs, rule 54 dispatches, nightly and the landing run are not covered by 0085, and they
  are what ER-31 and ER-33 judge a release on.
- Related: ER-21 / rule 40, ER-27 (logs explain every failure), ER-28 (cause confirmed by a reproduction), ER-33 / rule 71
  (a check counts only with a positive control), rule 2 (own worktrees and build folders), ADR 0014 §1 (build folders per
  app), ADR 0022 (`./dev`), ADR 0060 (every check runs somewhere), ADR 0080 (kept clone), ADR 0085 (release mode).
- Evidence read at `origin/train/2026-11-09-3` `66b600669` and in the job logs the coordinator saved in the session scratch
  folder (`triage-7872-7873/`, read 2026-11-10). The reproduction is synthetic, in this researcher's scratch folder.

2. **Why cargo called it fresh (reproduced, ER-28).** For path packages cargo hashes the package location relative to
   the workspace root and judges freshness by comparing the mtimes of the sources listed in the dep-info files, which it
   stores relative to the package, with the mtime of the last build. A second checkout of the same workspace at another
   path, whose files are **older** than the last build in the folder, is therefore up to date. Synthetic reproduction
   (cargo 1.99.1, macOS, scratch folder; two copies of a crate `demo` whose binary prints `answer=1` (root A) or
   `answer=2` (root B), and an integration test asserting its own answer through `CARGO_BIN_EXE_demo`):

   | Step | Result |
   |---|---|
   | Root B written first (mtimes 01:00), root A written now; `cargo test` of A into folder T | builds, test passes |
   | `cargo test` of B into the same T | "Finished `test` profile ... in 0.00s", no `Compiling`; **1 passed**: A's test binary ran against A's binary |
   | `T/debug/demo` after B's "build" | prints `answer=1`, while B's `main.rs` says `answer=2` |
   | Control: B into an empty folder | prints `answer=2` |
   | Control: `touch` one file of B, build into T | `Compiling demo`, prints `answer=2` |

   So the stale result needs only (a) two source roots building one workspace into one folder and (b) the second root's
   files older than the first root's last build. A kept clone that is "reused" and only rewrites changed files has old
   mtimes on everything the commit did not touch, which is the normal case. (The file times on the Windows runner were
   not read; that condition (b) held in run 7873 is inferred from the reproduction, the "reused" checkout and the absent
   `Compiling` lines. WP-0 may confirm it on the host if the folders are still there.)

## Pattern

**A build output kept between runs is reused for a different source whenever two source roots write one kept folder,
because the folder's key (app and job) does not name the source and cargo's freshness check does not either.**

**Invariant.** A kept build folder is only ever built from one source root; the folder records which root, toolchain,
commit, run and job last built it; a job that finds another root's record cleans the folder before building and says so
in its log.

## Change

### 1. The source is part of the folder's key

- `kept-folders.txt`: `target  target-{name}-{src}-{slot}  slot`. `{src}` is the first 10 hex digits of the SHA-256 of
  the canonical workspace root path (`pwd -P`; `cygpath -m` on Windows, lower-cased drive letter), the folder that
  `build-folder.sh` is given. `{slot}` stays last, so ADR 0025 §5's `{slot}` anchoring of clean-up patterns and
  `job-isolation.sh owns` keep working.
- `job-isolation.sh path target <name> --source <dir>` fills `{src}`; `path` refuses a `{src}` layout without
  `--source`. Linux keeps `<workspace>/target` (already keyed by the root: a new container each run).
- Old `target-{name}-{slot}` folders are not migrated: they stop being named, and the existing orphan sweep
  (`PADDOCK_CI_ORPHAN_DAYS`, 14) or the free-disk floor removes them. The first job per slot and root is cold once.

### 2. A stamp records who built it, and a mismatch cleans

`build-folder.sh` (before the build) reads and writes `<folder>/.paddock-build-source`:

```text
format = 1
root = "C:/users/<runner>/.paddock-ci/src/paddock-checkout-windows-s2/apps/pitwall"   # canonical, as hashed
checkout = "kept-clone paddock-checkout-Windows"                                     # the action and its name
commit = "92e65ead4fb3..."
rustc = "rustc 1.99.1 (... 2026-...)"                                                # `rustc -V`, for the log only
run = 7873
job = 34416
written = 2026-11-10T05:19:11Z
```

- **Root differs** (a hash collision, a hand-made folder, or a local folder reused across worktrees, §4): the folder is
  renamed to `<folder>.stale-<run>` and deleted (the slot is held, so `prune-build-folder`'s ownership rule applies), with
  one `::warning::build-folder: <folder> was last built from <root> by run <run> job <job>; cleaned before building from
  <root'>`.
- **No stamp** in a non-empty folder: same, with the reason "no record of its source".
- **Toolchain differs**: logged only; cargo already puts the compiler version in every unit's fingerprint.
- **Log line on every job** (ER-27), replacing today's `build folder: <dir>`:
  `build folder: <dir> (source <root> at <commit>; last built by run <run> job <job> from the same source <age> ago)` or
  `(new)` or `(cleaned: last built from <other root>)`.
- After the build (`if: always()`), `build-folder.sh verify` checks that the stamp still names this job's root and that
  the folder holds at least one file newer than the stamp when the job compiled anything (the step's own count), and
  prints the number of files it saw (0 is `check broken`, rule 71).

### 3. One source per name in the workflows (static)

The existing `ci-actions.test.mjs` test "every job that builds Rust on a host sets its build folder with the build-folder
action, in a stable checkout" (`conformance/test/ci-actions.test.mjs:372`) gains a second assertion: across all workflows
**on the tree under test**, each build-folder `name` expression is paired with one checkout action and name. This cannot
see a pairing on another branch (the run 7873 collision was `main` against train 3), which is why §1 keys by the root at
run time; the static test catches the same-tree case before a run.

### 4. Local build folders

The same mechanism, in Rust, for agents (ADR 0022: new tooling is `./dev`): `./dev target-dir <cargo-workspace>` prints
the folder to use, `<targets-root>/<worktree-key>-<workspace-key>` (default root `/Volumes/d7sst7/dev-targets/t`, set in
`devkit.toml`; `heavy` already refuses one under `~`), writes the same stamp, and cleans on a root mismatch with the same
message. `AGENTS.md`'s "kept between tasks for the same app" becomes "kept for the worktree; `./dev target-dir` names it".
The CI script and `./dev` share the stamp format and a golden test (rule 55: one mechanism, one format; the CI shell copy
is registered in `docs/known-copies.toml` until ADR 0022 moves the CI kit to Rust).

## Decisions for the user

| # | Question | Options | Recommendation |
|---|---|---|---|
| D1 | How the folder is keyed | (a) the source root in the folder's name, plus the stamp as a guard; (b) the stamp only: clean whenever another root builds (one folder, but while `main` and a train with different checkouts alternate on a slot, every job is cold); (c) fix the instance only (after train 3 lands, `ci.yml` uses only the kept clone) | (a): it makes the class impossible without cold builds; (c) leaves the next checkout change exposed |
| D2 | What the key holds | (a) the canonical workspace root only; (b) plus the toolchain; (c) plus the commit | (a): cargo already keys units by the compiler; (c) would make every job cold |
| D3 | On a stamp mismatch | (a) clean and warn; (b) fail the job | (a): the build is still correct, and the warning is logged |
| D4 | Local folders | (a) `./dev target-dir` with the same stamp; (b) guidance in `AGENTS.md` only | (a): the 2026-10 lesson was guidance only and recurred in CI |
| D5 | Where §1 and §2 are built | (a) in the shell kit now (`build-folder.sh`, `job-isolation.sh`), registered as a copy of the `./dev` stamp until ADR 0022 ports the kit; (b) wait for the Rust port | (a): 1.5 days, and ADR 0022 G.10 forbids only new shell tools |
| D6 | Release gating | (a) WP-1 lands before the next app's landing run is trusted as release evidence (host test legs can be falsely green today); (b) no gating, because ADR 0085's release mode makes the tag's own build job-local | (a) |

## Release impact (ER-31)

No product code changes. Under D6 (a) the next app tag waits for WP-1 (1.5 days), because until then a host test leg of a
landing run can pass on another branch's binaries, which ER-33 does not accept as evidence. Tag builds themselves are
covered by ADR 0085 once its WP-1 and WP-2 land.

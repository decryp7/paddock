# 26. The shared dialog API: Rust-owned contracts, DialogFrame with declared actions, windows that open fitted

- Status: Proposed (2026-10-28); the user answered its four open questions on 2026-10-28 (button order native per OS,
  three width steps, Dyno is monitoring-only, `unexercised` commands under a ratchet), recorded below
- Date: 2026-10-28
- Related: rule 17 (every dialog is a real OS window), rules 39, 40, 42, 43; ADR 0008 (long operations), ADR 0009
  (dialog kinds and declared contracts; this ADR amends its §2 and §3), ADR 0012 (app shell), ADR 0016 (dialog window
  sizing; this ADR is how decisions 1-7 are built and amends decision 2's role list), ADR 0022 decision 5 (the dialog
  command contract is generated from Rust); plan `docs/plans/debrief-1-2.md` packages 0.5, 1.1, 1.2, M2b; the work
  packages and per-app lists are in [`docs/plans/debrief-1-2-api-dialogs.md`](../plans/debrief-1-2-api-dialogs.md)
- Mockups: [`docs/images/dialog-api/`](../images/dialog-api/) (generated by `docs/images/src/dialog-kinds.mjs`)

## Context

On 2026-10-28 the user moved Dyno 1.0, Spotter 1.0 and Pitwall 1.1 onto the shared shell in those releases. Before
any of them adopts dialogs, the shared dialog API must be the one ADR 0016 describes, or each app copies today's bugs
(Close cut off, a gap below the footer, a window that jumps after it opens) into new code.

Today (read on `origin/main`, 2026-10-28):

- **Two sources for one contract.** The TypeScript registry (`defineDialog` in `ui/projects/paddock-ui/shell/src/define.ts`)
  declares kind, modality, sizes and commands. `serializeDialogContracts` writes them to a JSON file that
  `paddock_dialogs::Contracts::parse` reads at run time. The kind policy is written twice: Rust `Kind::policy` in
  `crates/paddock-dialogs/src/contract.rs` and TypeScript `KIND_POLICY` in `shell/dialogs/src/kind.ts`. They already
  disagree on the viewer (`fitsContent` vs `is_fitted`, ADR 0016 cause 6).
- **A 633-line TypeScript type-checker analysis** checks that each Debrief dialog declares exactly the commands it
  reaches (`apps/debrief/app/scripts/check-dialog-commands.mjs`, `dialog-commands-analysis.mjs`). ADR 0022 decision 5
  keeps it only until the contract is generated from Rust.
- **No footer contract.** `DialogShell` (`shell/dialogs/src/dialog-shell.ts`) mounts the content in a scrolling body. It
  looks for a Close by label (`hasCloseAction`) and for a default action by CSS class (`findDefaultAction`). Every
  component draws its own `.foot`: the shared `channel-remove-dialog.ts`, Debrief's `parser-import-confirm.ts` and about
  40 more. Button order, Enter and initial focus differ from dialog to dialog.
- **The window opens at a guess.** `paddock_dialogs::tauri::open` creates the window visible at 520 px high (when the
  dialog is fitted). The shell then fits it after `afterNextRender` and `document.fonts.ready`, so the user sees it jump.
  Fits only grow, and a blank or paused webview shows an empty window.
- **Each app has its own confirm.** There are four in-page copies of one decision:
  - Pitcrew's `pc-confirm-dialog` (6 uses) and its `pc-stop-process-dialog`;
  - Dyno's `dy-confirm-dialog` (3 uses that survive the monitoring-only change);
  - Pitwall's `pw-confirm-dialog` (11 uses);
  - Spotter's `sp-confirm-dialog` (2 uses).

## Decision

### 1. Kinds and sizing (ADR 0009 §1 and ADR 0016 decision 1, made concrete)

| Kind | Modality | Width (logical px) | Height | Remembers | Default actions | Escape, Cmd/Ctrl+W, OS close |
|---|---|---|---|---|---|---|
| `decision` | modal | `narrow` 400 (or `medium`) | measured, shrinks and grows | offset only | Cancel + one affirmative | Cancel; nothing for a required choice |
| `form` | modal or modeless | `medium` 560 (`narrow`, `wide` allowed) | measured, shrinks and grows; never declared | width and offset | modal: Cancel + primary; modeless: Close + primary | Cancel (modal) / Close (modeless) |
| `viewer` | modeless | `wide` 720 | preferred 560, grows to the cap; never shrinks below the smaller of its content and the preferred height | size and offset, clamped | Close | Close |
| `tool` | modeless | preferred 960 x 680 | user-sized; OS minimum = measured minimum content | size and offset, clamped | Close | Close |

- Widths are three named steps (user, 2026-10-28): `narrow` 400, `medium` 560, `wide` 720, defaulted by kind as in
  the table; a `tool` alone may declare a number. No dialog declares another width.
- The cap is 75 % of the work area. It applies to the preferred size only and never pushes below the minimum content
  size (ADR 0016 decision 4).
- The minimum content size becomes the OS minimum (`set_min_size`):
  - height: header + footer + the body's declared minimum (default two lines);
  - width: the footer's buttons on one line + padding.

### 2. DialogFrame with declared actions (ADR 0016 decisions 2, 3 and 5)

`DialogShell` hosts a `DialogFrame`:

- an optional header slot (a stepper, a toolbar);
- a body that alone scrolls;
- a `flex: none` footer that the frame renders from declared actions.

A content component no longer draws buttons for the footer. It declares them as a signal on the existing
`DialogContent` interface:

```ts
/** Every action has an id (test id `dialog-action-<id>`) and an already localised label. */
interface ActionBase { readonly id: string; readonly label: string; readonly enabled?: boolean }

/** Closes the dialog with the value `answer` resolves to. A rejection keeps it open (see "Rejected" below). */
export interface AnswerAction<R> extends ActionBase {
  readonly kind: 'answer';
  readonly role: 'primary' | 'secondary' | 'destructive';
  readonly answer: (signal: AbortSignal) => R | Promise<R>;
  /** The work honours `signal`: Escape, Cancel or an OS close while it runs aborts it and closes with no answer. */
  readonly abortable?: boolean;
  readonly lead?: boolean;   // at the leading edge (secondary, or a destructive beside a primary)
}

/** Does something and never closes (Copy, Show cited rows). */
export interface RunAction extends ActionBase {
  readonly kind: 'run';
  readonly role: 'primary' | 'secondary';
  readonly run: (signal: AbortSignal) => void | Promise<void>;
  readonly lead?: boolean;
}

/** The one way out without an answer: Cancel (modal) or Close (modeless). The label defaults by modality. */
export interface DismissAction extends ActionBase { readonly kind: 'dismiss'; readonly label: string }

export type DialogAction<R = unknown> = AnswerAction<R> | RunAction | DismissAction;

/** What the opener's promise resolves to: never an ambiguous `undefined`. */
export type DialogOutcome<R> = { readonly kind: 'answered'; readonly value: R } | { readonly kind: 'dismissed' };

export interface DialogContent<R = unknown> {
  dialogCanClose?(injector: Injector): boolean;               // unchanged
  readonly dialogActions?: Signal<readonly DialogAction<R>[]>;
  readonly dialogStatus?: Signal<string | null>;              // the footer's leading status line (tools)
  readonly dialogMinBodyHeight?: number;                      // the body's declared minimum, px
}
```

The states of an action are part of the contract:

- **Answered.** `answer` resolves: the dialog closes with `{ kind: 'answered', value }`. An answer of `undefined` is a
  value like any other; it is not a dismissal.
- **Dismissed.** The dismiss action, Escape, Cmd/Ctrl+W or an OS close request resolve `{ kind: 'dismissed' }`. A
  required choice has no dismiss action and ignores all three.
- **Busy.** While `answer` or `run` is pending, every action is disabled, the pressed one shows a spinner and
  `aria-busy`, and the body's controls are inert.
  - If the action is `abortable`, the dismiss action stays enabled. Dismissing aborts the signal and closes with
    `dismissed`; a late resolution is ignored.
  - If it is not, a dismissal (button, key or OS close) waits until the work settles and then applies. The footer says
    "Finishing…". Work that can last longer than a moment is a job (ADR 0008), not a busy action.
- **Rejected.** `answer` or `run` rejects (throws): the dialog stays open, the user's input is kept, and the frame shows
  an inline alert above the body with the error's user message (`DialogActionError.message`, else a generic sentence)
  and a **Try again** button that runs the same action again. Focus moves to Try again. The rejection is logged with the
  dialog id (no user content).
```

The frame applies one pure function, `layoutActions(kind, modality, requiredChoice, actions, platform)`, which is
tested as a table. It defines:

- **Order, native per OS** (user, 2026-10-28). Apps declare roles only; the frame orders them for the OS it runs on
  (`data-platform`, from the shell):
  - macOS and Linux: `[lead secondaries] … [secondary] [cancel] [primary | destructive]`, primary on the right with
    Cancel to its left (the design guide's order);
  - Windows: `[lead secondaries] … [primary | destructive] [secondary] [cancel]`, primary first and Cancel last,
    right-aligned.

  When a dialog has both a primary and a destructive action, the destructive one moves to the leading edge on every OS
  (Save / Cancel / Don't save). The mockups show both orders. Tests read the order from
  `layoutActions(…, platform)` and never assume one.
- **Counts.**
  - At most one primary.
  - At most one destructive.
  - Exactly one `dismiss`, except for a required choice, which has none.
  - Without a declared `dismiss`, the frame adds Cancel (modal) or Close (modeless) itself. The `hasCloseAction`
    label heuristic goes.
- **Enter.** Enter runs the primary when it is enabled. A destructive action is never the Enter target: a destructive
  decision's Enter is Cancel. Enter keeps its own meaning in text areas, buttons, links, lists and editable text (the
  `keys.ts` rules, moved into the frame).
- **Initial focus.**
  - A form: the content's first field (an `autofocus` the content marks), else the first field.
  - A destructive decision: Cancel.
  - Anything else: the Enter target.
  - When the dialog closes, focus returns to the element that opened it (the opener's `DialogService` keeps it).
- **Busy and rejected:** as above. A modal is never a long wait (ADR 0009 §1).
- **Accessibility.**
  - A decision's body is `role="alertdialog"`, with its heading as the label and its first paragraph as the
    description.
  - Destructive buttons say what they destroy ("Revoke key", "Delete 3 runners"). Colour is never the only sign:
    position and words are.
- **Invalid declarations do not throw** (components never throw). The frame renders the defined fallback (one Close),
  logs the problem, and the boot harness fails on it.

The frame also measures and refits, as ADR 0016 decision 5 describes:

- a measuring wrapper with `height: auto`;
- refits on fonts ready, a natural-height `ResizeObserver`, theme, density or font change, `ScaleFactorChanged`, and
  `requestFit()`;
- at most one fit per animation frame;
- decisions and forms shrink as well as grow.

### 3. The contract lives in Rust; TypeScript is generated (ADR 0022 decision 5; amends ADR 0009 §2)

- **Source of truth.** A `dialogs!` table beside the owner's `command_table!`:
  - `pd.*` dialogs in the crate of the feature (`paddock-shell`, `paddock-channels`, `paddock-mcp`, ...);
  - an app's own dialogs in `apps/<app>/app/src-tauri/src/dialogs.rs`.

  An entry holds the id, kind, modality, width step, preferred height (viewer, tool), `instanced`, `required_choice`
  and `commands`.

  The compile-time check works like this:
  - `command_table!` emits, for every command whose window classes include `DIALOG`, a marker constant
    `dialog_callable::<name>: DialogCallable` in the owner's module. A command not open to dialogs gets no marker.
  - `dialogs!` expands each listed command into a reference to that marker
    (`const _: DialogCallable = crate::commands::dialog_callable::app_status;`). A typo, a removed command or a command
    closed to dialogs is therefore an unresolved name, a compile error that names the command.
  - A `prefix*` entry expands to a `const` assertion over the generated `DIALOG_CALLABLE: &[&str]` list (a `const fn`
    prefix match): at least one dialog-callable command must match.
  - Plugin commands are written plugin-qualified, `plugin("dialog", "open")`. They cannot be resolved at compile time,
    so a unit test in the owner checks each one against the plugin's generated permission list.
  - Kind and modality are a typed pair (`Kind::Decision` takes no modality; `Kind::Form(Modality)`), so a forbidden
    pair does not type-check.
- **Registration.** `Contracts` is built from the static tables (`Contracts::from_tables(&[&paddock_shell::DIALOGS,
  &app::DIALOGS])`). The JSON contract file, `serializeDialogContracts`, `dialogContractFile` and the manifest copy are
  deleted, and so is the run-time parse of a file the UI wrote.
- **Generated TypeScript** (the `ts-rs` pattern every crate already uses, stale file = failing test,
  `PADDOCK_WRITE_TS=1`):
  - `ui/projects/paddock-ui/shell/generated/dialog-kinds.ts`: the kind table (floors, defaults, width steps, `fits`,
    `growsOnly`, `rememberHeight`). This is the one "is fitted" table of ADR 0016 decision 7. `kind.ts` keeps only the
    functions over it.
  - `<owner>/generated/dialog-contracts.ts`: `DIALOG_CONTRACTS` (`as const`), `type DialogId`, `type
    DialogCommandOf<Id>`.
- **The TypeScript side** keeps what only TypeScript can know: title, typed result, component loader, providers.

  ```ts
  defineDialog(DIALOG_CONTRACTS['pw.quit'], { title: msg('pw.quit.title', 'Quit Pitwall?'), result: type<QuitChoice>(), load: () => import('./quit').then((m) => m.Quit) })
  ```

- **What replaces the TypeScript analysis.** The four checks of `check-dialog-commands.mjs` move as follows:

  | Check | Replaced by |
  |---|---|
  | 3. The command exists and is open to dialogs | Compile time, in Rust |
  | 1. The dialog reaches a command it does not declare | The run-time guard (unchanged, fails closed with the denial line), plus a recorder at the TypeScript invoke layer (below) that fails the harness or e2e run on an undeclared command |
  | 2. The dialog declares a command nothing reaches | The recorder's `dialog-commands-seen.json`, compared by `dev check dialog-commands` in **nightly and full runs only**; it fails on a declared command no run sent, unless its entry says `unexercised = "<reason>"` |
  | 4. The base providers reach a command the base lists do not name | The harness |

  **The recorder sits at the TypeScript invoke layer**, the one `invoke` wrapper of `paddock-ui`'s IPC module that
  every backend calls. It tags each call with the active dialog id: the window label in a dialog window, and the
  `DIALOG_ID` of the injector in an in-page dialog. So browser-build dialogs (`in-page.ts`, the e2e runs) are counted
  as well as windows. The "declared but never sent" comparison needs the union of every run, so it never runs in
  affected-only CI (ER-7). In a branch, only the undeclared-command failure applies.

  The analysis is then deleted (ADR 0022 phase 6). This is weaker than the static walk for a path that no test drives.
  **`unexercised` is allowed under a ratchet** (user, 2026-10-28): each one carries a written reason, which a reviewer
  reads like any other change; `dev check dialog-commands` counts them per app and fails when the count rises above the
  committed baseline (`dialog-commands-unexercised.count`), so the count may only fall.

### 4. Dialogs as OS windows: lifecycle (rule 17; ADR 0009 §1; amends ADR 0012 §3's start-up for dialog windows)

1. **Open.** `dialog_open` validates the request against the Rust contract, reserves the label `d-<host>-<n>`, places
   the window and creates it **hidden** (pending). It is created at the placed inner size, with the contract's floor as
   its OS minimum and a background colour matching the theme's window surface, so a late paint is never white.
   Placement is on the parent's monitor (mixed DPI and negative coordinates included). A remembered offset is used only
   when the whole dialog stays on that monitor. A second open of the same id (or instance key) focuses the open window;
   while the first is still pending, it is a no-op that marks the window to be focused when it shows.
2. **Ready handshake.** The dialog webview boots (rule 34). After the first layout and `document.fonts.ready`, the frame
   sends `dialog_ready { content, minContent }`. This replaces `window_ready` for dialog windows and is also the first
   fit.
   - Sizes are the dialog's own **inner** logical size. Rust sets them through `set_size`/`set_min_size` with
     `LogicalSize` (Tauri's sizes are inner sizes), converting once and rounding the physical size up.
   - The cap is checked against the work area minus the dialog window's own decorations: its outer minus inner size,
     read from the hidden window itself, not from the parent.
   - Rust then shows and focuses the window. **The parent is disabled (or the macOS scrim drawn) at show, not at
     create**, so a dialog that never shows never locks its parent.
3. **Show deadline.** If `dialog_ready` has not arrived within the show deadline (about 1 s after create,
   `Config::dialog_show_deadline`), Rust shows the window anyway at its placed size. The shell renders its Loading
   state with a Close from its first paint, so what appears is "Loading…" and Close, never a blank window (mockup
   `loading`). A later `dialog_ready` fits it (one resize, accepted in this fallback only). The deadline is separate
   from `paddock-startup`'s reload watchdog: that one still reloads a page that never reports ready (about 10 s) and
   asks the user after a failed reload. The UI never times out the content itself (ER-19).
4. **Spike first (package 1.1-0).** Whether a hidden window runs layout and resolves `fonts.ready` differs by webview.
   WKWebView may throttle hidden windows, WebView2 may skip layout in a hidden controller, and WebKitGTK may not map the
   surface. The spike measures all three. It compares (a) hidden, then `dialog_ready`, then show, against (b) a visible
   window at alpha 0 (or off-screen), then show, and against (c) a synchronous layout after `fonts.ready`. It records
   the time to ready, and whether the measured height equals the height after show, at scales 1, 1.25 and 1.5. 1.1b
   implements the mechanism the spike picks per OS. The contract above (show on ready or at the deadline, parent
   disabled at show) holds for any of them.
5. **Refit.** `dialog_fit { content, minContent }` (renamed from `dialog_fit_height`) runs on the triggers in §2.
   Moving to a monitor with another scale refits.
6. **Parent and modality.**
   - A modal is owned by its parent. The parent is disabled natively on Windows and Linux. On macOS the host draws a
     scrim instead, because a sheet would block key focus.
   - A modal opened from a modal is owned by the top one.
   - Modeless dialogs are owned on Windows and Linux. They are independent on macOS so that they can move to another
     display.
   - Closing or hiding a host closes or hides its dialogs. Quitting closes all of them.
7. **Close.** A dialog closes only from its content: its dismiss action, Escape or Cmd/Ctrl+W, or an OS close request
   forwarded to the frame as the dismissal (busy rules in §2). A required choice ignores them.

   `dialogCanClose` can keep it open. The opener receives a `DialogOutcome`. `closed` carries the bounds to remember.
   Rust re-enables and refocuses the parent, and the opener returns focus to the trigger.
8. **In the page** (the browser build, e2e, and the fallback when a window cannot be created: `in-page.ts`,
   `pd-dialog-host`). The same `DialogFrame`, `layoutActions` and contract apply.
   - The overlay stays hidden until the frame's ready signal or the same show deadline.
   - A modal blocks the page with `ModalGate` and the scrim, and focus is trapped in the dialog (CDK `FocusTrap`).
   - Escape and the dismiss rules are identical.
   - Sizes are the overlay's inner size, clamped to the viewport by the same kind table.
   - The command recorder tags the calls with the dialog id.

   Only placement, OS parenting and the native scale handling are window-only.

### 5. One shared confirm (rule 42)

`pd.confirm` is a shared `decision` in `paddock-ui` with typed input:

```ts
{ heading, message, details?: string[], confirm: { label, destructive?: boolean }, cancelLabel? }
```

It replaces the four copies of one decision (ER-22): `pc-confirm-dialog` and `pc-stop-process-dialog` (Pitcrew),
`dy-confirm-dialog`, `pw-confirm-dialog`/`pw.confirm` and `sp-confirm-dialog`. Its contract allows no commands: it
answers `answered: true` or `dismissed`, and the opener acts.

### 6. Testing helpers

- **Boot harness** (`shell/testing`, with `untilDialogLoaded` from `fix/dialog-boot-flake`, which waits on the dialog's
  own load and `whenStable` and has no turn budget). `bootDialog` adds:
  - the `layoutActions` problems;
  - "draws its own footer";
  - "Enter would run a destructive action";
  - the `dialog_ready` payload;
  - the commands recorded at the invoke layer;

  It reads the generated contracts.
- **`FakeDialogIo`** records `ready`, `fit` and `minContent`, and can withhold `ready` to drive the show deadline.
- **`paddock-e2e`:**
  - `expectDialogFits(page, contract, fixture)` runs ADR 0016 check 1: scales 1, 1.25 and 1.5 x 1920x1080 and

  - `openEveryDialog` writes the visited ids for the conformance count.
  - `measureDialogWindow` is the real-window helper for `e2e-tauri`.
- **Lint `paddock/dialog-frame-footer`.** A registered dialog component may not contain a `.foot`, `.actions` or
  `footer` element, or a Close, Cancel or OK button, outside `dialogActions`.
- **Rust.**
  - The 1.1-0 spike's probe, kept as an `#[ignore]` real-window test that the full suite runs on each OS.
  - A placement property test: scale 1-3, work areas 800x600 to 7680x4320, any remembered size.
  - Compile-fail tests (`trybuild`) of `dialogs!`.
  - Staleness tests of the generated TypeScript.

## Consequences

- One definition of each contract, checked by the compiler. TypeScript can no longer disagree with Rust on kind,
  modality, size or commands.
- Dialog components lose their footers and their keyboard code. Button order, Enter, focus and busy state are the
  same everywhere.
- Windows appear once, at the right size. A slow or paused webview shows Loading with Close instead of a blank window.
- Packages 1.1 and 1.2 grow from 4.5 to 10.5 agent-days: the spike, the Rust-generated contract and the
  `dialog_ready` handshake are added (the figures are in the plan). The apps' adoption shrinks accordingly.
- A command reached only on a path no test drives is no longer found statically. It is listed with a reason instead.

## Alternatives considered

- **Keep the TypeScript registry as the source and generate Rust from it.** This keeps a TypeScript build step in front
  of every Rust build. It is the opposite of ADR 0022, and the command names would not be checked by the compiler.
- **Actions as content-projected buttons with a role attribute.** This keeps markup in every component and needs a DOM
  query to find the default. Declared data can be laid out, tested as a table and linted.
- **One button order on every OS** (primary right, Cancel to its left). Rejected by the user on 2026-10-28: dialogs are
  OS windows and should feel native; the frame owns the order, so apps still declare roles only.
- **Show the window at once with a skeleton and fit later.** The jump is the defect users report. A hidden window that
  is shown at the ready handshake costs one frame of latency, and the watchdog covers the failure case.

# 57. Paddock apps never block on the macOS Keychain

- Status: Proposed (2026-11-06). Decisions D1 to D5 below are open for the user.
- Date: 2026-11-06
- Related: ER-21 / rule 40 (a recurring bug means a missing design rule), ER-33 (a release check counts only with a
  positive control), rule 10 (nothing long on the UI thread), rule 12 (the UI never times out a job), rule 23 (ad-hoc
  macOS bundles), rule 42 (share first), rule 54 (the release path builds installers), rule 55 and ADR 0034 (one
  implementation per mechanism), ADR 0032 D6 (`SecureOn` in `paddock-secrets`; Dyno's amendments of 2026-11-05),
  Pitcrew ADR 0022 (a design for the service's `FileSecrets` with backup exclusion, not built), Debrief ADR 0059
  (Pitwall as the AI engine; the key "never in a file"), memory note "code signing dropped" (2026-11-05: the apps stay unsigned).
- Number: 0057. The highest ADR file on `origin/main` is 0049; 0053 to 0056 are on open branches
  (`git ls-tree --name-only <branch> docs/adr/` over all branches, 2026-11-06). The highest check named anywhere is C98
  and the highest rule 71 (ADR 0054 on `origin/docs/adr-os-lifecycle-and-edges-amend1`, ADR 0055 on
  `origin/docs/adr-family-logging`), so this ADR claims check **C99** and rule **72**. Renumber at landing if those
  branches land first with more.

## Evidence

Measured facts come from the research note `docs/research/2026-11-05-keychain-unsigned-updates.md` on
`origin/docs/keychain-unsigned-updates` (`95b27810d`, not yet on `main`; link it once it lands), with its raw log, screenshots and test program in
`/Volumes/d7sst7/dev-targets/handoff/evidence-keychain-research/` (`kc.log`). They ran in a throw-away Tart VM (macOS
26.6.2, Apple Silicon) with an invented test program using the apps' own call path (`keyring` 4.2) and with two real
Dyno 1.1.0 DMGs (runs 7575 and 7570). Single runs, not benchmarks. Everything else here is marked as read in code or as
judgement.

Measured (research note, table "Measured"):

- **Every update loses silent access.** A login-keychain item made by an ad-hoc build is bound to `cdhash:<build>`. The
  next build gets a SecurityAgent dialog that asks for the login password, once per item and per program.
- **Always Allow lasts only until the next build.** It adds that one build's hash to the partition list.
- **Self-signed does not help.** With the same certificate for builds A, B and C, the partition stayed `cdhash:` and each
  new build needed a new grant. Apple's source agrees: only Apple-chained identities get `apple:` or `teamid:`
  (`securityd` `clientid.cpp`, read 2026-11-05).
- **A blocked read waits with no time limit.** Nobody answered, and a launchd agent in `gui/501` with no window was
  still blocked after 15 minutes. A read from the main thread holds the first window back (real Dyno 1.1.0: dialog at
  once, no Dyno window).
- **Interaction off never blocks.** After `SecKeychainSetUserInteractionAllowed(false)` the read returns `-25293` in 2
  to 6 ms. The switch is process-wide. The per-call `kSecUseAuthenticationUIFail` was ignored for this keychain.
- **Writing over an item prompts too.** Another build that writes an existing item gets `-25299` (duplicate item) with
  interaction off, and a dialog with interaction allowed.
- **Deleting needs no dialog.** Another build deletes the item through the API with interaction off, with no dialog.
- **The data protection keychain is closed.** Without an entitlement it refuses (`-34018`); with one and no
  provisioning profile the kernel kills the program (`AMFI ... restricted entitlements`).

Read in Apple's source, not measured: Developer ID gets a `teamid:` partition, so its items would survive updates. The
user dropped code signing on 2026-11-05, so that route is closed for now.

Read in code on `origin/main` (`87c9b8449`): five manifests use `keyring` directly
(`apps/debrief/app/src-tauri/Cargo.toml:42`, `apps/pitcrew/app/src-tauri/Cargo.toml:40`,
`apps/pitwall/app/src-tauri/Cargo.toml:43`, `apps/pitwall/crates/pitwall-cli/Cargo.toml:29`,

`FileSecrets` (`src/file.rs`: one `0600` file per secret, written through a temporary file, refused on read if others
can read it). `security-framework` 3.7.0, the crate under `keyring`'s macOS store, is already in the lockfiles of Debrief,
Dyno, Pitcrew, Pitwall, Spotter, both demos and `crates/`, and `crates/paddock-workspace-hack` (generated by `cargo

today: no `.rs` file runs `tmutil`, and the one backup exclusion is Dyno's cache folder
(`apps/dyno/crates/dyno-agent/src/cache/backup.rs`, `exclude_from_backup`, which sets the
`com.apple.metadata:com_apple_backup_excludeItem` attribute).

Dyno on `origin/main` has no `keyring` at all. Its Keychain use is on `origin/steward/dyno-1.1.0` (`e9bfbb5b7`, read):
`apps/dyno/app/src-tauri/Cargo.toml:57` and `apps/dyno/crates/dyno-platform/Cargo.toml:29` enable

and the Wake-on-LAN password (`crates/dyno-platform/src/wol/mod.rs:122`).

Dyno's fix on `origin/fix/dyno-mcp-keys-file` (head `da4201dc5`, read): the MCP client key list moved to an owner-only

running user in a safe folder), and the Wake-on-LAN `SecureOn` password moved to `FileSecrets` on macOS
(`apps/dyno/crates/dyno-platform/src/wol/secrets.rs`, `91bffa558`). `dyno-platform` enables `paddock-secrets/keyring`

two ways, each with a positive control: a scan of every manifest in Dyno's Cargo graph for any table naming `keyring`
that can reach macOS (control: it must find `dyno-platform`'s own entry), and `cargo tree --offline -i keyring` per
macOS target (control: the Windows graph must show `keyring`; offline failure reports `not measured`). The scan reads

"4.2"`) is missed. That branch is being fixed separately, and C99 below checks header lines.

## Context

The same bug has now shown up in five shapes: Dyno's MCP key list read on the main thread before the first window, a
Wake-on-LAN job in a windowless background agent, Debrief's Pitwall key probe every 15 s
(`apps/debrief/app/src-tauri/src/ai/pitwall.rs:22`), Spotter's scheduler and mail notifier, and Pitcrew's notification
path. Each is a blocking OS dialog reached from code that nobody designed as UI. Under ER-21 that is a missing rule, not
four bugs. Fixing each app by hand already happened once (Dyno), and the other apps still carry the shape.

The Keychain cannot be made to work silently for unsigned apps, because the partition is tied to each build's hash. The
honest choices are to stop reading it, or to read it without UI and ask the user to allow access after every update.

## Decision

### 1. The rule (proposed rule 72)

> **No Paddock process reads or writes the macOS Keychain where it can block.** Never before the first window, never
> on the main thread, never in a background job or agent, and never without a bound. If a Keychain backend stays
> anywhere, interaction is off, reads and writes return a typed `NeedsPermission`, and `ask()` (the only call that may
> show a dialog) runs only from a user action. *Why:* ad-hoc and self-signed builds lose silent Keychain access on every
> update, reads and writes of an older build's item both raise the dialog, and a blocked call waits with no time limit
> and no window (research 2026-11-05).

### 2. One mechanism (rule 55)

- **One door.** Only `paddock-secrets` may depend on `keyring`. Apps code against the `Secrets` port and never name
  `keyring::Entry`.
- **One platform default.** `paddock_secrets::for_app(...)` returns `FileSecrets` in the app's data folder on macOS and
  the OS store on Windows and Linux. The `keyring` feature is enabled only under `cfg(not(target_os = "macos"))`, as
  Dyno's `dyno-platform` does on `fix/dyno-mcp-keys-file`, so the Keychain adapter is not compiled into a macOS build.
  `FileSecrets` gets backup exclusion, so every app has it. It is new work, because Pitcrew ADR 0022 only plans
  `tmutil addexclusion`. It reuses Dyno's `exclude_from_backup` attribute writer, which moves into shared code
  (rule 42) instead of being copied.
- **Presence is not a read.** The port gets `contains(&Name) -> Result<bool, SecretsError>`. Screens that only show a
  tick ("token set") call it and never fetch the value. On `FileSecrets` it is a metadata check.
- **If a Keychain backend stays** (option (b) in section 5), the process sets
  `SecKeychainSetUserInteractionAllowed(false)` once at start, before any Keychain call, because only the process-wide
  switch works (measured; the per-call flag is ignored). `OsVault` serves every call behind one mutex. `-25293`,
  `-25299` and `-25308` become `SecretsError::NeedsPermission`, never `None`. An interactive call exists only as
  `ask()`, which turns interaction on and off again under that mutex, refuses the main thread, and is called only from a
  user action. Whether
  `SecKeychainSetUserInteractionAllowed` is marked deprecated was not checked (research note, "Not verified").

### 3. The check (C99)

Dyno's test becomes a family conformance check, C99 "no Keychain on macOS". It looks for the Keychain API, not one
crate name, because `keyring` is only one way in: `security_framework::passwords::get_generic_password`,
`keyring_core::Entry`, the `apple-native-keyring-store` crate and a spawned `/usr/bin/security find-generic-password`
reach the same items. Its workspaces are `crates/`, `tools/paddock-dev` and the `cargo` folder of every
`apps/*/paddock.ci.json`. A `Cargo.lock` under `apps/` that this list does not reach fails the check, so a new app
cannot escape it. Apps with no `cargo` field and no lockfile (Pacenotes and Sighter today) are listed as "no Rust".

1. **Manifest scan.** Every `Cargo.toml` table that names `keyring`, `keyring-core`, `apple-native-keyring-store`,
   `security-framework` or `security-framework-sys` fails unless the table's `cfg` is one of `not(target_os =
   "macos")`, `windows`, `target_os = "windows"`, `target_os = "linux"`. A table names a crate in its body (a
   dependency, a renamed or inherited one, a feature entry such as `paddock-secrets/keyring` or
   `paddock-secrets?/keyring`) or in its header line (`[dependencies.keyring]`,
   `[target.'cfg(...)'.dependencies.keyring]`). There are two exceptions. `crates/paddock-secrets/Cargo.toml` defines
   the `keyring` feature, and `crates/paddock-workspace-hack` is generated by `cargo hakari` and has no code (the graph
   probe covers what it mirrors).
2. **Source scan.** Every `.rs`, `.sh` and `.mjs` file outside `paddock-secrets` and C99's own code and fixtures that
   names `find-generic-password`,
   `find-internet-password` or `add-generic-password` fails, because spawning `/usr/bin/security` reaches the Keychain
   with no Rust dependency at all.
3. **Graph probe.** Per workspace and per macOS target (`aarch64-apple-darwin`, `x86_64-apple-darwin`), the check first
   runs `cargo fetch --locked --target <target>`, then `cargo tree --locked --offline --all-features -e normal,build -i
   <crate> --target <target>` for `keyring`, `keyring-core` and `apple-native-keyring-store`, and finds nothing.
   `--all-features` covers every feature a release could turn on. `security-framework` is not probed, because Tauri's
   own macOS stack pulls it in (it is in `apps/workbench-demo`, which has no `keyring`), so its API is fenced by Clippy
   (point 4). When the fetch fails, the probe never passes: on a branch it reports `not measured`, and on the release
   path (a tag or a `<app>-release.yml` run) it reports `check broken` and the release stops (ER-33).
4. **Clippy.** Clippy reads the `clippy.toml` of each workspace (it searches from the manifest folder upwards), never
   `lint/clippy.toml`, which is the preset each workspace copies. There are 7 copies today (`crates/`,
   `apps/{debrief,dyno,pitcrew,pitwall,spotter}/`, `tools/paddock-dev/`), and C13
   (`conformance/src/checks/C13-rust-lints.mjs`) compares only their `disallowed-methods` with the preset. WP-2 does
   five things:
   - It adds the entries to the preset and to all 7 copies (8 files).
   - It gives `apps/shell-demo/src-tauri` and `apps/workbench-demo/src-tauri` a `clippy.toml` (neither has one, and
     shell-demo uses `KeyringSecrets` in `src/mcp.rs`).
   - It extends C13 to compare `disallowed-types` too.
   - It adds `disallowed-types` for `keyring::Entry`, `keyring_core::Entry`,
     `security_framework::os::macos::keychain::SecKeychain`, `security_framework::item::ItemSearchOptions` and
     `security_framework::passwords_options::PasswordOptions`.
   - It adds `disallowed-methods` for every function of `security_framework::passwords` (in 3.7.0:
     `get_generic_password`, `generic_password`, `set_generic_password`, `set_generic_password_options`,
     `delete_generic_password`, `delete_generic_password_options`, `get_internet_password`, `set_internet_password`,
     `delete_internet_password`), for `find_generic_password` and `find_internet_password` in
     `security_framework::os::macos::passwords`, and for `add_item` and `update_item` in `security_framework::item`.

   Clippy takes exact paths, not `::*`, so the list names each item, with `allow-invalid = true` for workspaces that do
   not link the crate. `paddock-secrets` gets one `#[allow]` with a reason, in `src/os/native.rs` only.

Positive controls (ER-33, rule 71), all of which must fail or be found, or C99 reports `check broken`:

- Fixture manifests flagged by the scan: `features = ["keyring"]` under `[dependencies]`, a `[dependencies.keyring]`
  header table, and a direct `security-framework` entry.
- A fixture `.rs` file that spawns `security find-generic-password`, flagged by the source scan.
- Real entries the scan must find: `crates/paddock-secrets/Cargo.toml`'s optional `keyring` dependency (found, then
  exempt), and from WP-1 on, `apps/dyno/crates/dyno-platform/Cargo.toml`'s `cfg(not(target_os = "macos"))` table
  (found, then allowed).
- In the graph probe, `x86_64-pc-windows-msvc` must show `keyring` in at least one workspace, and `paddock-secrets` must
  be found for the macOS targets.
- A fixture crate that calls `get_generic_password` and names `keyring::Entry` must fail `cargo clippy -- -D warnings`
  with the family's `clippy.toml`. This proves the paths resolve, which `allow-invalid` would otherwise hide. The
  `security_framework` half runs on the macOS runner, because that crate is empty off Apple targets
  (`#![cfg(target_vendor = "apple")]`).

The check starts with a waiver for each of the six manifests that fail on `origin/main` today (no source file there
names the `security` subcommands, and no manifest but the exempt workspace hack names `security-framework`). The
waiver list is the to-do list and
empties with work packages WP-3 to WP-7. Dyno's own test stays until C99 lands, then is deleted with the app's copy of
the scan (rule 43).

Released builds that wrote Keychain items: Debrief 1.1.1, Pitcrew 1.0.1, Pitwall 1.0.3 (research note, "Per app").
There is no compatibility shim beyond the one-time re-entry above (memory note "no backward compatibility before v1").
Debrief's old Pitwall key keeps working after the update, because a Pitwall key stays valid until it is revoked
(`pitwall-server/src/auth.rs:215`, "the old ones keep working until revoked"). Re-pairing an app that already exists
adds a key beside the old ones (`decide_pairing`, `auth.rs:349`), and only `add_key` applies the cap of 8 keys per app
(`auth.rs:222`). So WP-5 revokes the old key at re-pair: when Pitwall approves a pairing for an app that already has
keys, it revokes those keys with `revoke_key` (`auth.rs:238`). If that would cut off a second machine that pairs under
the same app id, WP-5 falls back to a release note that tells the user to revoke the old key in Pitwall's app list.

adapter that could delete it. A delete through the API with interaction off measured silent (research note, "Measured"),

### 5. The trade-off, plainly

An owner-only file is readable by any program running as the same user. The realistic such program on this machine is
supply-chain code: an npm `postinstall` script or a Cargo build script that runs as the user during a build. It can
read the file silently. A Keychain item made by another program would at least raise a dialog for it. That dialog is
weak protection here, because people who type their password into it after every update learn to type it into any such
dialog (judgement; the dialog does not show which build asks, research note "Dialog text on Dyno").

The file protects against other users. At rest it is weaker than the Keychain. Keychain items are encrypted inside the
keychain file, but an owner-only file is plain text, which FileVault protects only when FileVault is on. Backup
exclusion keeps it out of Time Machine only. Other clones and copies of the home folder (Carbon Copy Cloner, `rsync`,
a migration) copy it in plain text. The fair comparison is `~/.netrc` or `~/.docker/config.json`, which hold tokens in
plain text in the same way, not `~/.ssh`, whose keys can carry a passphrase.

It matters only for real third-party tokens: Spotter's forge and registry tokens and mail password, and Pitcrew's Gitea
tokens and channel secrets. Dyno's key list holds hashes, Pitwall's key is already in a file, and Debrief's key is a
local-only `pw_` key.

For those tokens there are two options:

- **(a) Owner-only file** (`FileSecrets`, backup-excluded). Never blocks, no dialogs, exists and is tested. Same-user
  programs, supply-chain code included, can read it silently, and it is plain text at rest. About 0 extra days.
- **(b) Keychain with no-UI reads plus a visible action** ("Allow access after the update"): reads with interaction
  off, a health row "Needs permission", and a button that calls `ask()`. Keeps the same-user dialog. Costs one password
  dialog per item per update, and about 2 days per app with UI (Spotter, Pitcrew): the action, the health row and tests,
  plus a VM row that answers the dialog.

**Recommendation: (a)** for a personal family of apps that update often. It is the user's call (D2).

### 6. Release check (ER-33)

`scripts/vm-smoke` gets a row per app with secrets: install build A, create the app's secrets, install build B, open
it. Pass means the first window appears within the row's bound and no SecurityAgent window exists. Its positive control
reads an item that another build created, which must show the dialog; otherwise the row reports `check broken`. The
earlier run showed the pitfalls (research note, "VM release row"): a press on "Allow" matched the label `Allow | _NS:8`
by accident, and after one AX press the dialog's tree was empty, so the row finds the dialog in the window list, not
the accessibility tree.

## Consequences

- No Paddock app on macOS can hang on a Keychain dialog, because the adapter is not compiled in. C99 keeps it so by
  checking Paddock manifests for the Keychain crates (`keyring`, `keyring-core`, `apple-native-keyring-store`,
  `security-framework`), source files for the `security` Keychain subcommands, the macOS dependency graph for the
  Keychain crates, and the Keychain types and functions through Clippy.
- Secrets on macOS are as safe as `~/.netrc` (section 5): plain text owner-only files, readable by same-user code.
  Time Machine excludes them, while other clones, a synced or network home folder may still copy them or lose the file
  mode (Pitcrew ADR 0022 warns of this).
- Windows and Linux keep the OS store. Windows Credential Manager and the Linux Secret Service have no per-build
  binding (read in Microsoft's `CredReadW` page and the Secret Service spec, not measured), so they are unaffected.
- If Developer ID is ever bought, the Keychain becomes viable again (`teamid:` partition, read in Apple's source, not
  measured); the rule then changes with a new ADR, and `for_app` is the one place to switch.
- A Dyno change touches the release path, so rule 54 asks for an installer build before it lands.

## Decisions for the user

- **D1.** Dyno 1.1.0: land the fix before the tag (recommended, WP-1, 0.5 day), or tag and accept that users with an AI
  key meet a no-window dialog on the first update.
- **D2.** Real tokens (Spotter, Pitcrew) on macOS: (a) owner-only file (recommended), or (b) Keychain with no-UI reads
  and an "Allow access" action (about 2 days per app).

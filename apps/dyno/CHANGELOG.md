# Changelog

## [1.1.0] - 2026-11-04

Dyno 1.1.0 adds the optional administrator helper, saved views, the benchmark tool, the network lists, world map and firewall view,
power features, the per-metric menu-bar items, a free-size dashboard grid and dialogs that fit their content, and fixes the nine
problems reported on 1.0.0. Update by hand once from the releases page: 1.0.0 does not look at these releases (see the note below).
The app and the agent speak protocol 4: update both together (they ship in one installer).

### Added

- Saved views (ADR 0029): disk-map scans, the counter catalog and the software list are kept in a rebuildable `cache.db` and shown at once with their age after a restart; Rescan keeps the saved map until the new pass is done, and Settings has the limits and Forget saved maps.
- Network (ADR 0031): lists of addresses you choose to download and flag connections, a world map of the connections and a read-only firewall view; the disk-health tool (smartmontools) can be downloaded on demand. All network features are on by default with one switch each.

- Benchmarks: the `dyno-bench` runner is now part of the installers (it was started by the agent but never bundled, so every benchmark answered "missing"). It is built with the other sidecars, signed as `net.decryptology.dyno.bench`, and the release checks start it with `--version`. The 1.0 disk test (its reads came from the memory cache) is never shipped; the rebuilt one is below (ADR 0030).
- Benchmarks: processor and memory runs warm up for a second and repeat five times; the page shows the median with the spread of the repetitions ("2,380 to 2,440") and marks a metric whose repetitions vary by more than 10 % as unsteady. A change counts as better or worse only when it is larger than the noise band and the runs' spreads together. Runs measured by 1.0 are kept, marked "Measured the old way", and never compared with newer runs.
- Benchmarks: a run is a job (it shows in the Jobs view with the phase it is in, on its own scale) and Cancel works in every phase and ends the measuring program. A run that goes quiet for 30 seconds shows "Not responding" with Cancel, and one that outlasts its plan shows "Still working"; nothing ends it but Cancel. On battery the run asks first ("On battery. Results will be lower and the battery drains faster. Run anyway?") and stops if the computer switches to battery without that consent. Linux: the runner is a named systemd user unit (verified on a real systemd, `docs/linux.md`), stopped on Cancel and cleaned up by invocation id after a crash.

- Tests: `crates/dyno-core/tests/wire_roundtrip.rs` round-trips a sample of every variant of the app-agent wire enums (`Message`, `Request`, `Reply`, `ErrorCode`, `LiveDetail`, `JobSpec`, `JobOutput`, `HelperRequest`, `HelperReply`, `HelperMessage`) through postcard, fails with the type named when a type postcard cannot carry (internally tagged enum, `flatten`, `untagged`, `skip_serializing_if`) reaches the wire, and fails at compile time (an exhaustive match) or in the test (a source scan) when a new variant has no sample. It is written against the types on `main`: a branch that adds variants adds their samples when it merges.
- Benchmarks, disk (ADR 0030 WP-B3): the disk test is rebuilt to measure the drive, not memory. Per chosen drive it writes one scratch file (default 1 GiB; 256 MiB, 1 GiB or 4 GiB) with the cache bypassed (Linux `O_DIRECT`, Windows no-buffering with write-through, macOS `F_NOCACHE` and `F_FULLFSYNC`; where a file system refuses it the test runs buffered and the read labels say "cached reads possible"), and measures sequential 1 MiB with 1 and 8 threads and random 4 KiB with 1 and 32 threads, each read and write, after an uncounted ramp (at most 1/8 of the file or 1 s), three repetitions, median and spread. Sequential results are MB/s; random results are IOPS and MB/s. At most 14.5 GiB is written per drive and run (`disk_write_budget`, enforced by the runner so the figure shown is an upper bound). The file is unlinked at once on macOS and Linux and deleted on close on Windows, so a killed runner leaves nothing; the agent's scratch folder is recorded with its identity and removed at the next start only if the identity still matches. A drive that is read-only, optical, a RAM disk, disconnected, a network drive (unless ticked), or short of free space (the file plus the larger of 10 % of the volume and 2 GiB) is reported unavailable with the reason; the other drives still run. The disk method is version 2.
- Wire (protocol 4): `StartBenchmark` gained `disk_volumes` (ids of the volumes, empty means the system drive) and `allow_network_drives`; `KindResult` gained `device` (the drive's name; the disk kind has one result per drive, metric ids carry the drive: `disk-<slug>-seq1m-t1-read`); `RunPlan` and the UI type `StartBenchmark` mirror them. The sustained-write test and the picker are not in yet (WP-B7).

- Windows: a one-time notice, shown on the first start and again when a new menu-bar icon is added: "Drag Dyno's icons from ^ to the taskbar to keep them visible", with the button Open taskbar settings (`ms-settings:taskbar`, the command `open_taskbar_settings`, fixed target). Windows 11 puts a new tray icon in the overflow (a promoted icon is on the taskbar; verified in the VM, both icons appear once pinned). Remembered per webview (`dyno.trayHintSeen`).
- Every metric can be its own menu-bar / tray item: the limit of four items is now 32 (one icon each, so each can be dragged to its own place; ADR 0028).
- Each item is given a stable identity so the OS can remember where you put it: macOS names every status item (`NSStatusItem.autosaveName`) and keeps a copy of its saved position across the item being removed; Windows gives every icon a GUID (`guidItem`), recovering a GUID the shell refuses and falling back to no GUID rather than losing the icon; Linux's status-notifier id is the item id. Not yet verified on a Mac or a Windows PC. Windows builds are not signed, so a remembered place holds only while the program stays in the same folder. A new item of the same kind as a removed one takes its place.
- Changing the items only replaces the icons that changed. The log tells each icon's identity (and, on Windows, whether its GUID was accepted) or why it could not be created.

### Changed

- The menu-bar and tray items have a new look (design `docs/design/dyno-tray/README.md`): stacked label-over-value numbers with tabular figures in the system font, fixed widths per format, a dimmed dash when a value is missing, an alert that needs the level held for 3 s, and whole-pixel icons at the taskbar's own size on Windows (drawn again when the DPI or theme changes). The default set is CPU, memory, network and temperature.
- A tray item shows its alert while Dyno has an open alarm for its metric (your alarm rules and the overheating alert); a load no rule covers uses the new Settings level "Menu-bar alert level" (default 90 %). A number item can be set to one line, and Settings explains what macOS and Windows 11 do with items that do not fit once more than four are on.
- When the agent stays away for 3 s the items show a dimmed dash at their usual width instead of the static icon.
- Administrator readings (Dyno ADR 0027, WP-11): Settings has a card "Administrator readings" with the helper's state in words and an icon (Off, Not running, Needs repair, Update available, On, Not available here), what turning it on shows and what the OS will ask, and Turn on / Repair / Update / Turn off as one job with phases and Cancel (Cancel waits while the system's permission prompt is open and says so; the job has no UI deadline). A helper that is not installed, does not answer, or whose endpoint is owned by something else (never sent anything) is a state with a next step, not an error.
- Packaging of the helper (ADR 0027 WP-13): `dyno-helper` ships next to the agent on every OS (`externalBin`; on macOS with the code-signing identifier `net.decryptology.dyno.helper`); the `.deb` carries `dyno-helper.service` (generated from the spec, shipped disabled), the polkit rule that lets a local active session start only that unit, and maintainer scripts (upgrade restarts it only when it was enabled; remove stops and disables; purge removes `/var/lib/dyno-helper`; none runs without systemd); the Windows uninstaller asks for one prompt to remove the service with the bundled helper; `check-bundle` checks all of it and starts `dyno-helper --self-test` from the extracted artifact.
- Helper requests for scheduled wake (Dyno ADR 0032 D2; `HELPER_API` is now 3): `ScheduleWake { tag, at_utc }`, `CancelWake { tag }`, `ListWakes` (owner and administrators only, Dyno-tagged events only, at most 8 pending, not in the past, at most 31 days ahead; audited before they happen; macOS through `pmset schedule wake` with an owner string, Linux through a `systemd-run` timer with `WakeSystem=true`) and `WolState { ifname }` (Linux, read-only modes, any caller). Tags and interface names are parsed at the wire into types that cannot hold anything else.
- Agent protocol: `Request::HelperStatus` / `Reply::HelperStatus` and `JobSpec::Helper { action }` / `JobKind::Helper` / `JobOutput::Helper` are appended to the wire. The version number is not raised here: the one `PROTOCOL_VERSION` 4 of 1.1.0 covers this change together with the other appended variants of 1.1.0.
- Helper readers (Dyno ADR 0027 WP-5, WP-6, WP-10; the reply enum gains `Processes`, `CounterValues`, `Memory`, `SocketOwners`, `FileHolders`, `Extras`): `Processes` pages every process of every account from `sysinfo` with only allow-listed fields (no command line, environment or working directory), scoped to the caller by the connection's own account (never a request field) and with other accounts' profile paths cut to a file name; `Counters` answers per id (Linux sysfs thermal, fans and RAPL energy; macOS `powermetrics`; Windows `MSAcpi_ThermalZoneTemperature`), one missing sensor never hides the others; `MemoryModules` reuses the slot-table reader, which has no serial number field; `SocketOwners` and `FileHolders` (Linux) read `/proc/<pid>/fd` and `/proc/locks` and never open the file; `Extras` (Windows) reads `powercfg /requests` and `wbadmin get versions`, in detail for the owner and administrators and as counts for anyone else.

### Added (power, ADR 0032)

- Keep awake. The agent holds the computer awake while you ask: for 30 minutes to 7 days, until a time of day, until you stop it, while a chosen program runs, or while the computer is busy (CPU, network or disk above a limit, or a program running, and for a grace after the last busy moment). The OS holds a power assertion (macOS), power request (Windows) or logind inhibitor (Linux, and the desktop's screen saver lock for the display) named "Dyno: keeping awake ...", so `pmset -g assertions`, `powercfg /requests` and `systemd-inhibit --list` show the same truth. The hold ends with the agent; after a crash or restart it is not taken again and the page says "Keep awake ended: Dyno restarted". When the OS ends it (the computer is put to sleep), it is taken again on wake if the time has not run out. The Power page (Keep awake), a Keep awake submenu in the tray menu (Settings > Power > Show Keep awake in the tray menu), Settings > Power, and `dyno awake [on|off|status] [--for 90m] [--until 18:30] [--display]`.
- Settings: `power.keepAwake` (`enabled`, `display`, `graceSecs`, `cpuPct`, `netBytesPerS`, `diskBytesPerS`, `trayItem`), all optional with defaults; `SCHEMA_VERSION` unchanged.
- Wire: `Request::PowerState`, `PowerKeepAwake { spec }`, `PowerStopKeepAwake`; `Reply::Power(PowerView)`; `Message::PowerChanged(PowerView)`. Appended only; `PROTOCOL_VERSION` is 4 for all of 1.1.0. The golden `power.wire.json` and `power.contract.spec.ts` guard both sides. A new push event `dyno://power`.
- Helper: keep awake needs nothing from the helper (it runs with the user's rights). Scheduled wake (a later package) will need `ScheduleWake`, `CancelWake` and `ListWakes` in `HELPER_API` 3, as ADR 0032 section 7 says.

- Wake-on-LAN (ADR 0032 section 3, D6, D8). The Power page has a Wake devices tab: your computers (added only by your pick from the computers Dyno sees on the network, or by hand; rename, change, remove), Wake and Test wake per computer, and This computer's readiness. A wake sends the magic packet (the 6 x 0xFF and 16 x address payload, plus an optional SecureOn password) to the limited broadcast and the subnet broadcast of each network card, UDP port 9, three rounds one second apart; it runs as a job with phases ("Sending the wake packets", "Waiting for an answer"), Cancel and "Still working". Test wake first checks whether the computer already answers (then it sends nothing), and counts it awake when its hardware address turns reachable in the neighbour table or its last address answers one ping; it says "Awake after 23 s (answered ping)" or "No answer in 120 s: it may be off at the wall, have Wake-on-LAN off, or block ping", and saves a moved address. The SecureOn password is kept in the OS credential store under the computer's id, never in `dyno.db` or the logs. A Wake device submenu in the tray menu lists up to ten saved computers and "Manage devices...". This computer's readiness lists what Dyno can read (macOS `pmset` "Wake for network access"; Windows the kind of sleep from `powercfg /a`, Fast startup from the registry, and each physical card's wake setting from `powercfg /devicequery`; Linux each physical card's `power/wakeup`) with a plain Fine, Needs a change (with the fix) or Can't tell (with the reason) for each, and always says the BIOS/UEFI setting cannot be read. Relaying through another Dyno is not built (D8).
- The neighbour tables (ARP and NDP), which Dyno did not read before: macOS `arp -an` and `ndp -an`; Linux `ip neigh` (else `/proc/net/arp`); Windows `GetIpNetTable2`. They run through the one tool runner with a timeout, parse with parsers that never panic (bounded to 4096 entries, 1 MiB of text, 512 bytes a line), and are read only when "Add from network" is opened or a test wake looks for its answer.
- MCP (D7): Dyno's four tools for `paddock-mcp` in `app/src-tauri/src/mcp.rs`: `power_state` and `wol_devices` (read-only) and exactly two actions, `wake_device` and `keep_awake` (1 to 720 minutes), hidden and refused until the user allows each by name; no sleep, shut down, timed or scheduled tool exists. The tools ask the agent with the same requests the Power page sends. Not yet wired to the shell's `Builder::mcp` and the Settings > AI access page (see the report of this change).
- Settings: `power.wol` (`enabled`, `discovery`, `directedBroadcast`, `testTimeoutSecs`), all optional with defaults (on, on, on, 120); `SCHEMA_VERSION` unchanged. Settings > Power > Wake-on-LAN.
- Wire: `Request::WolDevices`, `WolCandidates`, `WolSave { device }`, `WolRemove { id }`, `WolWake { id, test }`, `WolReadiness`; `Reply::Wol`, `Reply::WolCandidates`, `Reply::WolReadiness`; `JobSpec::WolWake { id, test }` and `JobOutput::Wol`; `Message::WolChanged(WolView)`; a new push event `dyno://wol`; `Page::Power` for a widget or tray navigation. Appended only; `PROTOCOL_VERSION` is 4 for all of 1.1.0. The golden `wol.wire.json` and `wol.contract.spec.ts` guard both sides.

- Scheduled wake (ADR 0032 section 5, D9). The Power page's Schedule tab lists, adds, changes and cancels schedules: a local time (once, every day or on chosen weekdays) at which the computer wakes and then stays awake for 1 to 720 minutes, wakes chosen Wake-on-LAN computers and runs one job from a fixed list (check the backups, list the installed software; never a command). Off until you turn on Settings > Power > Scheduled wake. The agent arms each schedule for its next occurrence through the local zone (DST gaps and folds included) and sets the OS wake: on Windows its own waitable timer with the resume flag (it works while the agent runs, needs "Allow wake timers", and Dyno cannot tell about Modern Standby, which the tab says); on macOS and the Linux package the administrator helper's `ScheduleWake`/`CancelWake`/`ListWakes` (at most 8 pending, never in the past, at most 31 days ahead; the tab says "Needs the helper" with Turn on the helper when it is off, and "no helper in this build" for an AppImage). A wake that passed while the computer was off or the agent was not running is shown as missed and never run late (a 10 minute grace). Nothing wakes a computer that is shut down; the tab says so. Dyno's wakes that no schedule owns are cancelled at start and when the setting is turned off.
- Wire: `Request::PowerWakes`, `PowerSetWake { entry }`, `PowerCancelWake { id }`; `Reply::PowerWakes(WakesView)`; settings `power.wake.enabled` (default off). Appended only; `PROTOCOL_VERSION` is 4 for all of 1.1.0. `wake.wire.json` and `wake.contract.spec.ts` guard both sides.

### Fixed

- Windows: after a restart the helper card no longer shows Repair (and asks for UAC) until the helper has had a minute or two to start. The helper service now starts with the boot (`auto`, not `delayed-auto`; failure actions unchanged), the agent starts a stopped helper service itself with the user's own rights when it finds the pipe absent (the service's security descriptor already lets interactive users start it) and waits up to 15 s for the pipe, and Settings reads the helper again after 2, 4, 8 and then every 15 s, for about three minutes, while it is installed but not answering. A service that is stopped with an error is not started in a loop: the card says Repair and the detail names the service's exit code and reason.
- Windows: a helper that refuses to start (a data folder or file that is not protected, a damaged configuration, an endpoint that cannot be opened) now says why: the reason and a service-specific exit code (3 not protected, 4 configuration, 5 endpoint) are written to the Windows Event Log (source "Dyno helper", registered at install) and kept as the service's exit code, and the lines of the start that came before the data folder was verified go to the Event Log too (nothing is written into the unverified folder). A panic in the helper and the reason for any self-removal (an Uninstall request, or the app gone for an hour) are written to the Event Log too, and the line before a service is deleted names the code that asked.

- Menu-bar / tray items: hovering an item names its metric and reading ("CPU 34%", "Disk C: 81% (alert: above its limit)"), not "Dyno". On Windows the tip change was refused because the modify call did not name the icon by its GUID, so every icon kept the tip it was built with; it now does, and a tip is cut to the 127 units the notification area keeps. A refused tip is logged. Linux status-notifier hosts show the tip only if they support it (GNOME with the AppIndicator extension does not).
- Connections map: the five count steps of the legend (1–2 to 200+) were five near-identical magentas (CIEDE2000 1.1 to 4.5 between neighbours). They are now a lightness ramp, lighter with the count in dark and darker in light, at least 10 apart between neighbours in normal vision and under protanopia, deuteranopia and tritanopia. The legend draws each step's marker size on its fill ("Shade and dot size: connections per country"), and the tooltip names the step ("Step 4 of 5 (50–199)"). Destination markers are now the text colour with a page-colour halo (the accent sat inside the ramp), arcs run on a page-colour casing, the home marker is a ring, and the flagged hatch has page-colour gaps.

- Health: an active alarm now lowers the health score, so the dashboard and the tray pop-up no longer show "Health 100 Good" next to an active alarm. An active Warning alarm caps the score at the top of "Fair" (79), an active Critical alarm at the top of "Poor" (59); a score already below the cap is unchanged. "Active" is the alarm state Active (condition holds, not acknowledged, not shelved): acknowledged, cleared and shelved alarms do not cap, and Info alarms are listed but never cap. The engine computes it (`dyno_core::health`, bands and their top scores in `Grade::top_score`); "What holds it back" names each active alarm (title, severity, since when) ahead of the performance reasons, and the trend line says "held at Fair by an active Warning alarm (performance alone: 100)". Wire: `HealthReport` gains `performance_score` and `capped_by`, `HealthReason` gains `since` (postcard, appended; no `PROTOCOL_VERSION` bump: the app and the agent ship together).
- Disk map: one folder answering "Operation timed out" (os error 60, a File Provider or network-backed folder) no longer stops the whole scan as "the link dropped". The scan root is asked again: if it answers, only that folder is marked incomplete and the scan goes on; only when the root stops answering too is the volume lost. The log tells which (`Disk scan: one folder ... the volume still answers` or `... the volume is lost`, with the raw error text).
- macOS start-up items: login items and app-registered agents (System Settings > Login Items & Extensions) are not listed because reading them (`sfltool dumpbtm`) needs administrator rights and asks for a password; the page now says so ("Not shown: Login items ...") next to the launch agents it can read, and shows the reason instead of "No startup items" when nothing could be read. The helper in 1.1 will read them. Read failures are logged, and the read is kept between explicit refreshes. A folder that does not answer in time shows "Did not answer in time", and eight such folders in a row end the scan as a lost volume even if the root still answers.
- About: "See all releases" opens the releases page in the browser (it failed with "state not managed ... `files_open_url`" because the shell served the command without its service; fixed in `paddock-shell`).
- History: switching the range no longer leaves the chart empty until the view is reopened. The chart resized itself to 0 px while the panel's skeleton detached it between two answers and never recovered; it now ignores a container without a size and fits itself again after each draw.
- Windows: at logon only the agent started (in a console), with no tray icon and no window. Cause (reproduced in the Windows 11 VM with a restart): the agent's service entry and the app's own autostart entry were both the Run value `Dyno`, and the app's repair, five seconds after every start, replaced `Dyno = dyno-app.exe --hidden` with `Dyno = dyno-agent.exe run`. Now the app's own value is the only logon entry (it starts the agent itself, hidden); the agent's own entry, when someone installs it by hand, is `Dyno agent`; the app's start no longer repairs a Windows entry; and the first start after an update removes the stale `Dyno = dyno-agent.exe run` and, when Start at login is on, registers the app's entry again (when off, removing it is all).
- Windows: `dyno-agent` is a GUI-subsystem program, so the per-user Run entry (`dyno-agent run` at logon) no longer opens a command prompt window that stays open for as long as the agent runs (reproduced in the Windows 11 VM: a Windows Terminal window titled `dyno-agent.exe`). Run from a terminal, `dyno-agent --version` and `service install` still print (it attaches to the parent console); a prompt does not wait for a GUI program, so for `--version`, `status`, `stop`, `once` and `service ...` in a terminal use `dyno agent <command>` (the console `dyno` program runs the agent's commands and returns their exit code). The release workflow reads the built `dyno-agent.exe` (PE Subsystem 2) and `dyno.exe` (3).
- Windows: the log tells each tray icon: its static image and size, created or why not, and the first drawn image (size, or the refusal). A new icon of an app that was never pinned sits in the taskbar's overflow (the `^` at the right) on Windows 11 until the user turns it on in Settings > Personalization > Taskbar > Other system tray icons; the registry showed Dyno's icon registered there (`NotifyIconSettings`, tooltip `Dyno`).
- Windows: the tray popup no longer disappears at once after a click on the tray icon (the shell took the foreground back and the popup closed on that blur; see `paddock-window`). The log tells each tray click, the popup's show, focus and hide with the reason.
- macOS: the Network page lists every program's sockets also when Start at login is off. The agent the app starts itself was its child process, and macOS 27 shows a child of an ad-hoc signed app only its own sockets; the app now starts it as a launchd job of the user's session (`launchctl bootstrap`, label `net.decryptology.dyno.agent.ondemand`, its definition in Dyno's data folder, not in `~/Library/LaunchAgents`, so nothing starts it at login), and ends it through launchd on Quit. Linux and Windows are unchanged. The log says which way the agent was started (`Via`) and the agent logs what macOS shows it (Dyno ADR 0026).
- "Is this normal?": the learning card said "day 1 of 7" on the second day. It now counts local calendar days from the first start (the first start is recorded when the agent starts, not at the first request), is ready only after 7 local days and 7 times 24 hours, and on the last day says when it will be ready.
- Dialogs (About, What's new, Updates and the confirmations): each window fits its content, grows or shrinks when the content arrives late (Updates no longer opens with a scrollbar beside one line), keeps the size you gave it by hand, follows a change of display scale, and on Windows an Aero snap counts as your resize while a DPI change does not (ADR 0043).

### Added (notifications, tables, performance)

- Notifications: select messages (checkboxes, Shift-click for a range) and delete the selected ones, or delete all after a confirmation. Deleted messages stay gone after a restart (shared `paddock-health` commands).
- Expand all and Collapse all (icon buttons with tooltips) in the toolbars of Network (programs or remote hosts), Processes (Apps and Tree views), and the grouped lists of What changed (days) and Files (groups). Interaction state only; Network keeps its fold in the same saved list as a single fold.
- Processes: the Tree view no longer searches the whole process list for every row it draws (a map lookup), so opening a tree of thousands of processes is quick.
- macOS: the menu-bar icons no longer risk flickering: each picture is set with its template flag in one call (it was set, then set again as a template), the tooltip is sent only when it changed, and changing the items replaces only the icons that changed. The log shows every picture set at debug level. Not yet confirmed on the Mac that reported it.
- Lower CPU use (measured in a macOS VM, `docs/performance.md` 2026-11-03):
  - With no window open, the app asks the agent for the new `tray` live level instead of the summary: the menu bar icons keep the user's sampling interval, and the process table is read at the unwatched pace (every 10 s instead of every 2 s). A menu bar item that shows one app's numbers keeps the summary level; an older agent that cannot read the tray level gets the summary.
  - A menu-bar picture is not set again when only its tooltip changed.
  - Charts animate only their first draw with data. Options are replaced whole on each update, so a live chart (Counters, every 2 s) replayed its entry animation on every poll.
  - Live numbers glide in 6 steps over 300 ms instead of one step per display frame (about 18 repaints per update, every second on the dashboard).
### Changed (dashboard grid, dialogs, wire)

- Dashboard widgets sit on a grid of rectangles (shared `paddock-widgets`, ADR 0044) instead of spans; the dashboard layout is schema 2 and stored under the new settings key `dashboardGrid`. A Dyno 1.0 dashboard is upgraded on the first start (logged once in the activity list, written at once); the 1.0 value stays under the old `dashboard` key until the first dashboard edit in 1.1, so Dyno 1.0 started later still shows the person's layout.
- Wire (protocol 4): `EditWidgetLayout` has `baseRevision` and a stale one is refused with the new error code `stale` (the UI reads the view again and retries once); a layout view has `revision`, `canRedo`, `arrangements`, `moves` and `outcome`; dashboard placements are `{ id, x, y, w, h, widget }`; `Edit` has `Arrange` and `Redo`; grid gestures, sizes and steps are externally tagged enums and a placement is written field by field in postcard, so views and edits stay plain postcard (no second encoding inside a string; a round-trip test covers every edit variant on every surface). New app command `preview_widget_layout` (answered in the app, from the last view the agent sent). Undo is 20 steps for every layout.

## [1.0.0] - 2026-10-29

### Fixed

- macOS: a look that waits for the login service (`SMAppService.status`, 21 s on a loaded login) reads the discovery file and the lock again every 100 ms and returns as soon as an agent holds the lock, so the app connects when launchd's agent is up instead of when the service answers.
- The diagnostics bundle reads its logs from the folder `run` named (carried by the agent's folders), so a test harness never copies the machine's real Dyno logs; a log that does not fit is left out instead of failing the save, and the newest logs are taken per process.
- Report a problem is reachable: Help menu item and a command-palette entry (the UI never imported the shared diagnostics dialog); it shows the app log and the agent log read from disk, so both are there with the agent stopped. The Diagnostics page's saved bundle now holds the newest app and agent logs (`logs/`).
- macOS: a service recheck in the wait for the agent no longer blocks the look while the folder lock is held (the agent is up): at login under load the rechecks, each waiting on `SMAppService.status`, delayed the connect.
- macOS: a restart with Dyno running ("Reopen windows when logging back in") starts Dyno hidden in the tray, whatever Start at login says; loginwindow's restore request (`rsto`, sender checked by its executable path) counts like a login-item start (`lgit`). The log says which signal decided (`flag`, `login item`, `restored at login`).
- Settings: when a save cannot reach the agent ("The Dyno agent is not running"), the page puts the controls back to what is stored and shows Retry, which sends the edit again. Before, the switch kept the unsaved position, so the next press equalled the stored value and nothing was saved. An engine refusal still keeps the edit so it can be corrected.
- macOS: at login the app connects to the agent that launchd started as soon as its file is there, without waiting for `SMAppService.status`. That call is an xpc round trip to smd and blocked the first look for about 30 s on a busy login (sampled in the VM); the service is now asked again right after the connection, for the hand-over, and still decides a look that has no agent to connect to.
- An agent that the system or another app (App Tamer) has stopped is reported as "Paused by macOS or another app" and waited for: no Retry on the chip, and nothing ends or replaces it (ADR 0031). Before, a stopped start counted as having done nothing for 60 s and Retry ended it.

- Logs for root cause (login start and every other start): the agent now writes its own dated log (`dyno-agent.<day>.log` beside the app's `dyno.<day>.log`, with the panic hook and a crash marker) with a line per step of its start (lock, store, endpoint bound and `agent.json` written, running, stopping) and millisecond counts; its errors go there instead of standard error. The app's own lines go to the same shared file as the shell's (the separate `logs/app.log` is gone) and tell the login start step by step: the open event that started it, each decision look with the service's answer and how long `SMAppService.status` took, the discovery file and lock, every change of the link's phase with its duration, connect attempts, launches, closes and failed requests (names and codes only), and the time from connecting to the first data. Repeats are told once. Report a problem now includes both logs and the agent's own `agent.log`, and works with the agent down.
- Fixed a gap that skipping the service on the decision look opened: switching Start at login off right after the app connected, before the service had answered once, no longer leaves the service's agent connected and unsupervised (a change of the service with no earlier answer takes the agent back; a first answer that is only a baseline still does not).
- Logs: the agent's refusal says why, who holds the folder (its pid) and what started the refused agent, and `agent.log` is gone (everything is in the dated log); connect attempts carry the attempt number, the time since the link began and the attempts a success took; a connect in the app's log and the agent's lines share `AgentRun`; a flapping link is summarised once a minute; failed requests are told once per request name.
- The first look at login no longer waits for `SMAppService.status` when an agent is already there: the look was wrongly never marked as a decision look, so the service was always asked first.
- macOS: a healthy agent that launchd runs is no longer thrown away at login. The reader of `launchctl print` took the nested `state = active` lines of the coalitions for the job's state, so a running job looked stopped, and "has a launch constraint" alone counted as refused; the repair then killed the agent four times and printed "needs LWCR update" without launchd having said so. Only spawn failed, exit 78 and "needs LWCR update" mark a refused job, a running job is never replaced because the app has not connected yet, and the failure message prints the state launchd reported. `launchctl` output is read while it runs (a listing over 64 KiB blocked it until the 5-second timeout on every look).
- macOS: the reader of `launchctl`, the "is this job refused" decision and `launchctl bootout` now come from the shared `paddock-service` crate (no copy in Dyno); a pending or running job is never called stale, and `launchctl` output is read while the tool runs.
- The agent's `settings.json` is no longer moved aside as `settings.json.corrupt` at every app start (the shell used the same file name; see the shared changelog), so Start at login and the other settings survive a restart.
- macOS: the Network page, a program's connections and open files, and "what is locking this file" no longer ask the kernel about other programs' sockets, pipes and kqueues one descriptor at a time (`proc_pidfdinfo`, `lsof`), which could rarely make macOS fail another app's waiting reads and writes on a socket with EBADF. Sockets now come from the kernel's own TCP and UDP lists (the owner is the process the socket works for), files and libraries from `libproc` file descriptors only (Dyno ADR 0026). The agent and the `dyno` command carry a dotted code-signing identifier (`net.decryptology.dyno.agent`, `.cli`) from an embedded Info.plist, which macOS 27 needs to show the whole list; without it the Network page says why instead of listing only Dyno's own sockets.
- macOS: turning on Launch at login adds Dyno's own two entries to Login Items, the app and its agent (the app registers itself with `SMAppService.mainApp`; no extra "dyno-app, unidentified developer" row, nothing under `~/Library/LaunchAgents`), it is refused with a message when Dyno runs from the disk image or a quarantined download, and a login start still opens in the tray. `dyno-agent service` refuses inside the app on macOS. The "First launch" notes describe the macOS 26 steps.

### Added

- Widget layouts are shared with the other apps (family ADR 0035, `paddock-widgets`): the tray popup, the dashboard and the menu-bar items each have a closed catalogue (`dyno_core::widgets`), live in the agent (`settings.json` `popover`, `dashboard`, `menuBar`) and change only through `EditWidgetLayout`, which validates the whole result, saves it and tells every window. The popup shows the widgets you choose (default: active alarms, disk space, CPU and memory; up to 8), each with its own loading, empty, error and working state, and says "Agent stopped" once, with Restart agent, when the agent is away. Values are built in one pure module (`widgets::popover_values`) from what the agent already keeps and the live push, and are sent to the popup only while it is visible. `PROTOCOL_VERSION` is 3. Pinned counters are not in the live push: while the popup is visible the app asks the agent for them every 5 seconds (from the counters' kept readings, never a fresh OS read); the backup widget carries `lastBackup` and the UI draws its age. The old `tray` and `trayItems` settings keys are gone (Dyno 1.0 is unreleased: nothing is migrated). The default popup fits the family's 520 px popup cap without scrolling, also while the agent is stopped: one alarm row and two volume rows are shown before "+N more" (`tray-fit.spec.ts` checks the default and the taller states).
- The widget UI is on the shared components (family ADR 0035): the tray popup draws the engine's layout with `pd-widget-area` and one template per widget kind (the calm alarms row, the agent notice, the ⋯ footer menu with Customize widgets…, Settings… and Quit Dyno; a shortcut is shown only if the popover window binds it, as Ctrl on Windows and Linux); Settings > Menu bar has the popup widgets chooser with a live preview and the menu-bar items editor, and the dashboard's edit mode is the same chooser with presets (edits apply at once and have Undo; there is no Save dashboard). The TypeScript copy of the layout model (`widget-model.ts`) and Dyno's hand-written `Settings`, `DashboardLayout` and `TrayItems` types are gone: only the generated types are used. The dashboard no longer colours a widget by threshold until the engine supplies dashboard values.
- The link to the agent is now a state machine with one owner (ADR 0025): a request made before the first connection waits for the connection or for a shown stall with Retry instead of failing after 8 seconds, a connection that drops right after it was made backs off, and a start, a hand-over and a quit can no longer interleave into two agents or a wrong "stopped" note.
- Dyno measures your PC and explains why it is slow; it only looks and changes nothing on your computer. On Windows, macOS and Linux, with your own rights: no privileged helper and no administrator prompt (the helper is planned for 1.1), and a figure the OS keeps from you says *Unavailable* with the reason.
- A per-user background agent samples the machine and keeps its history while the window is closed; the app and the `dyno` command line talk to it over one local IPC. Only one agent runs per user: it holds a lock on its data folder, a second one exits at once (code 3) without touching the history, and the app waits for a slow-starting agent instead of starting another one (a cold, slow disk can take a minute), then stops exactly the agent it started when you quit. Turning Launch at login on hands the agent over to the system's login service (macOS, Linux) instead of running two; turning it off brings back the app's own. A start that takes long is never given up on, but the status bar says why (still starting, waiting for the login service, another agent holds the data folder) with a Retry; if the login service starts no agent, Dyno starts its own and says so. Its own cost is shown ("Dyno: x % CPU, y MB") and it stretches its sampling when it is over budget.
- Live dashboard: CPU, memory, disk and network, plus GPU, battery, temperatures and fans where the OS reports them (otherwise the reason, never a zero), with sparklines, a health score and customisable widgets.
- History in SQLite that survives closing the window: raw points for a day, then 1-minute, 15-minute and hourly rollups with min, average and max, so a short spike stays visible; retention is configurable and a damaged database is set aside and recreated (one another process is writing is not damaged and stays).
- Processes grouped by application, with details (command line, modules, connections, signer; macOS and Linux first), "what is locking this file", open location, snapshots and diffs, network traffic per program where the OS allows it, and the **Other users** row.
- Why is it slow: a diagnosis with causes, confidence, evidence and suggestions, anomalies, a disk-full forecast, throttling detection, SSD and battery life ranges and learned "is this normal" baselines.
- Alarms with an ISA-18.2 style lifecycle (low disk, overheating, crash loops, throttling, stale backups), acknowledged, muted and annotated in Dyno's own data; issues from the OS logs (crashes, hangs, unexpected shutdowns) with a stability score and export for Debrief; new and unusual programs against a learned baseline; and a weekly report for any of the last 52 weeks, exported as Markdown or a web page.
- Disk map: a ring chart of a volume or folder where a click drills in, with a live scan job (phases, Cancel, bounded in depth, entries and time), Retry for folders the OS refused, Reveal and Copy path, and a hint while Full Disk Access is missing on macOS. It deletes, moves and renames nothing.
- Health and startup items with reasons only, a performance-counter browser with charts, named sets and dashboard graph widgets, extras (what changed, sleep, boot, per-app network and energy, GPU per process, large and duplicate files, inventory with memory-slot drawings and export, maintenance windows), backup health (Time Machine, Windows Backup and File History, restic, Borg), benchmarks on click, a flight recorder and the diagnostics bundle.
- Web and VirusTotal search from right-click menus only open your browser, with private details removed first; the file hash is computed on your computer and nothing is uploaded.
- The `dyno` command line (`status`, `why-slow`, `top`, `alarms`, `snapshot`, `counters`; text or `--json`), shipped in the installers.
- Out-of-process Rust sensor plugins with timeouts, a memory cap and quarantine, listed in Settings.
- Runs on the Paddock app shell: one frame, notifications and service health, jobs with Cancel, settings, About, updates and What's New, the tray with a live metric and compact dropdown, and light and dark themes with a colour-vision-checked palette. Closing the window keeps Dyno measuring.
- Every dialog is on the shared dialog API: the alert rule, the lookups and the lockers list are dialog windows with their contracts declared in Rust, deleting an alert rule asks with the shared confirmation, and the buttons follow each system's order.
- About shows the build's commit and date.
- Updates are opt-in and signed with the Paddock family key: one HTTPS GET of the `dyno-latest` release, every update verified before it installs, and a build without the key never checks. The installers are an NSIS setup (Windows, per user), an ad-hoc signed `.dmg` (macOS) and a `.deb` and AppImage (Linux), each with the `dyno-agent` and `dyno` sidecars.
- Settings > Parallelism and cost: how many threads read folders (Auto or 1 to 16, for the disk map and the file finder; Auto follows the kind of volume), how many jobs run at once (Auto or 1 to 8, read at start) and the file finder's limits (files looked at, folder depth, content compared), all validated by the engine. The finder skips a file over the comparison budget and carries on, counts the folders it could not read, and counts the threads of a cancelled search on a dead share together with the disk map's per host (restarting Dyno clears it). Child processes of the log read are the shared `paddock-proc`: their own process group ended as a whole, lower priority without `nice(1)`.
- Finding large and duplicate files, reading the system logs, checking the backups, hashing a program's file and the sleep, boot, app-usage and software reads are jobs on the shared `paddock-jobs`: starting one answers at once, the agent pushes every status to the shell (`paddock://jobs`), so the Jobs view, the status item and the pages show it with the phase's own count (a growing count while it walks or streams, then the comparison, then the bytes read), "Still working" at the shell's threshold, and Cancel in every phase. A cancelled or failed job changes nothing, and no timeout of the UI ever abandons a running one (the UI has no timer at all; a shared check over the app's sources keeps it so). Cancelling a system-log read kills the `log show` process at once; a log read or backup check asked for while the scheduled one runs waits for it. The file finder is bounded in files (500,000), folder depth (48 levels) and bytes compared (64 GiB) and says which limit stopped it and what to do. The agent protocol is version 2 (`StartJob`, `Jobs`, `CancelJob`, `JobResult` replace `FindFiles`, `RescanIssues`, `RefreshBackup`, `FileHash`, `SleepBlockers`, `BootAnalysis`, `AppUsage` and `SoftwareInventory`; `Message::Job` pushes a status).
- A command palette: Mod+P goes to any page, Mod+Shift+P runs a command (the pages' own buttons, such as Read the system logs now, Check now, Run again, Save bundle, Add rule; each shows its page first and is off while the page's button is).

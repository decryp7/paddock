# 16. The privileged helper: a registered system daemon, installed on a click, spoken to over the one IPC

- Status: accepted (2026-10-23); the closed action list is reduced to read-only actions plus Install and Uninstall by ADR 0021 (2026-10-28); Dyno 1.0 ships without the helper (ADR 0021 point 4); the install flow, IPC and audit log are revised for 1.1 by ADR 0022; for 1.1.0, ADR 0027 (Accepted 2026-11-03) replaces the single authorised user, the token and `dyno-ipc` with `paddock-ipc`, kernel peer facts and per-account scope, and keeps install on a click
- Related: ADR 0001, 0002, 0006 (this record fills in its points 3 to 5), 0010, `crates/dyno-helper`,
  `dyno_core::helper` and `dyno_core::helper_wire`, `dyno_platform::{elevate, tuning_admin}`,
  `dyno_agent::helper_link`, docs/roadmap.md (WP-01)

## Context

ADR 0006 decided that system changes needing administrator rights go through a separate minimal executable with a
closed set of `HelperAction`s, installed on first use. It did not say how the helper is registered on each OS, who may
talk to it, what it records, or what happens when it crashes or is uninstalled. The items waiting for it are the
administrator items of Tuning (hibernation, macOS sleep timer and Low Power Mode, battery charge limit, Defender
exclusions), the all-users startup entries, and per-program traffic on Windows (the per-connection TCP statistics can be
switched on only when elevated).

Constraints: the app and agent never run elevated; Dyno changes the system only on the user's click; the Mac the
project is built on is the user's real machine, so nothing in the tests installs anything; the macOS bundle is ad-hoc
signed (no Developer ID), which rules out checks that need a team identifier.

## Decision

### 1. One executable, two roles, one elevation primitive

`dyno-helper` is a small Rust binary shipped next to `dyno-agent` (a second `externalBin`). It has three commands:
`serve` (the daemon), `install` and `uninstall`. The only thing the agent ever runs elevated is
`dyno-helper install --user <id> --agent-exe <path>`; the install command (running as root/LocalSystem-capable admin)
does all the OS-specific work itself from a typed, pure **install plan** (create directories, copy itself to a
system-owned place, write the configuration and the registration, start the daemon). The agent asks the OS to elevate
that one command:

| OS | Elevation (the OS's own prompt) | Registration of the daemon | Where it lives |
| --- | --- | --- | --- |
| macOS | `osascript` `do shell script ... with administrator privileges` (the standard password dialog) | a LaunchDaemon `net.decryptology.dyno.helper` (`RunAtLoad`, `KeepAlive` on failure) bootstrapped with `launchctl` | `/Library/PrivilegedHelperTools/`, data in `/Library/Application Support/Dyno/Helper/` |
| Linux | `pkexec` (polkit) | a systemd system unit `dyno-helper.service` (`Restart=on-failure`, `NoNewPrivileges`, `ProtectHome`) | `/usr/local/libexec/dyno-helper`, data in `/var/lib/dyno-helper/`, socket in `/run/dyno-helper/` |
| Windows | `ShellExecuteExW` verb `runas` (UAC) | a service `DynoHelper` as LocalSystem, auto start, restart on failure, created with `sc.exe` | `%ProgramFiles%\Dyno\Helper\`, data in `%ProgramData%\Dyno\Helper\` |

`SMAppService` daemons need a signed bundle with an approval step in System Settings and do not work with an ad-hoc
seal; the `osascript` prompt works today. When a Developer ID exists the macOS registration can move to
`SMAppService` without changing anything else (the install plan is the seam). Windows uses a service rather than a
per-click elevated process because per-program traffic needs a long-lived elevated reader and because a service is the
one thing UAC lets a standard user talk to without a prompt per request. The Windows session-0 argument of ADR 0010
does not apply: the helper never touches a desktop.

The binary is **copied to a system-owned folder** at install and the daemon runs from there. A SYSTEM/root process must
never run an executable that the user can overwrite (the app may be installed per user).

The helper stays **resident and idle** (a few MB, no polling). ADR 0006 said "exits when idle"; on-demand activation
(launchd `Sockets`, a systemd socket unit, a demand-start service) needs per-OS activation code that cannot be
verified without installing on the developer's machine, so it is a later hardening. Residence is the only deviation
from ADR 0006.

### 2. The wire: the existing IPC, with a fixed endpoint

Frames, handshake and `Peer` are `dyno-ipc` unchanged. The body type is `dyno_core::helper_wire::HelperMessage`
(`Request(HelperRequest)` or `Reply(HelperReply)`; postcard). Additions to `dyno-ipc`, all additive:
`Host::listen_at(Endpoint, Token, FrameLimit)` for a fixed, system-wide endpoint (a Unix socket path with a mode, a
named pipe name with an SDDL), and `Connection::peer_uid()` (the kernel's answer for the peer's user on Unix). The
**token** is generated by `install`, kept in a file owned by the authorised user (mode 0600 / ACL for that SID) and a
root-owned copy is read by the daemon; it defends against a confused or hostile local user who is not the authorised
one. The agent keeps no copy of its own.

### 3. Who may call (authentication)

The daemon serves **one authorised user**, the one who clicked install; installing again as another user takes over
(the OS prompt guards it). A connection is accepted only if all of these hold:

1. **Endpoint access**: the socket is mode 0666 in a root-owned directory (the path must be reachable) but the next
   check refuses other users; the Windows pipe's DACL grants only `SYSTEM` and the authorised SID (and rejects remote
   clients), so other users cannot even open it.
2. **Peer user (Unix)**: `SO_PEERCRED` (Linux) / `LOCAL_PEERCRED` (macOS) uid equals the authorised uid.
3. **Token** in the handshake (constant time), and the protocol version.
4. **Peer program**: the image path of the peer's process (`/proc/<pid>/exe`, `proc_pidpath`,
   `QueryFullProcessImageNameW`) equals the `dyno-agent` path recorded at install. If the OS cannot tell, the
   connection is refused (fail closed). The recorded path is the agent installed with the app, normally in a folder an
   ordinary user cannot write (`/Applications`, `Program Files`); this is what keeps same-user malware that merely
   copies the token from asking for a Defender exclusion. A signature check (macOS designated requirement, Windows
   Authenticode) needs a real certificate and is a later hardening; the path check is the strongest gate that works
   with an ad-hoc seal. Residual risk: a same-user process that can write into the agent's folder or inject into the
   agent. The pid is checked once per connection (a pid could in theory be recycled in that window; the connection is
   short-lived and the token has to match too).

The install step itself runs the helper program that ships with the app, elevated. When the app is installed per user (the
Windows installer is), that folder is writable by the user, so a program already running as that user could replace the file
before the user approves the prompt. The same program could equally replace the app and wait for any other elevation, so this
does not widen what per-user malware can do, but it is the reason the daemon never runs from there and the prompt names the
program being elevated.

### 4. What it will do: a closed list, validated twice

- The daemon accepts only `HelperRequest::{Info, Apply, Read, Traffic, Audit, Uninstall}`. `Apply` and `Read` carry a
  typed `HelperAction`. **Only actions that need administrator rights on this host**
  (`needs_admin_on(host)`) are accepted; everything else is refused ("not a helper action"), so the privileged surface
  is the smallest that does the job. There is no string-to-command path: every action becomes a fixed program with
  validated arguments or a small file operation (`dyno_platform::tuning_admin`). Free text reaches a program only as an
  environment variable (Defender folder paths) or as a single argument after validation, never through a shell.
- `HelperAction::validate` runs again in the daemon after postcard decoding (**parse, don't validate**: decoding
  yields the typed value; an out-of-range or unknown variant is a decode failure). Folder paths are canonicalised,
  must exist, be directories, not links, and not be system roots. Startup entry names are restricted per location
  (a launch-agent label is `[A-Za-z0-9._-]`); a launch agent is changed only inside `/Library/LaunchAgents`.
- Every call has a timeout (tools: 15 s; the client waits 60 s) and the frame limit of the IPC bounds the input.
  Changes are serialised by one lock. After applying, the daemon **reads the setting back**; if it does not read as
  the action says it answers `Failed` (the agent, which holds the inverse action, then puts the previous setting back).
- The app/agent stays the owner of the *undo history* (the activity log carries `apply` and `revert` actions). The
  helper additionally records the previous value of every setting it changes in its own audit log.

### 5. Audit log, undo, crash and uninstall

- **Audit log**: `audit.jsonl` in the helper's data folder (root-owned, world-readable, no secrets, no file contents):
  one JSON line per mutating call or refusal, with time, peer pid, a one-line summary (the action's preview), the
  value before and after, and the verdict (`applied`, `refused`, `failed`, `interrupted`). It is size-capped (rotated
  once to `audit.1.jsonl`). A line `started` is written before an action runs and an `interrupted` verdict is recorded at
  the next start for any `started` without an end, so a crash mid-action is visible. The last entries are shown in
  Settings.
- **Undo**: Dyno records every helper action in the activity log with its inverse (`UndoRecord::Tuning`), exactly like
  an unprivileged tuning change; undo goes through the helper again. Before a revert Dyno re-reads the setting and
  refuses if something else changed it.
- **Crash**: the OS restarts the daemon (launchd, systemd, SCM recovery). A crash never leaves the Dyno agent without
  a working fallback: when the helper is unreachable the item says so and what to do ("restart the helper in Settings,
  or reinstall it"); observe mode is unaffected.
- **Uninstall**: from Settings, on a click. The authenticated daemon removes its own registration and files (the plan in
  reverse); no second prompt is needed because the caller is already authenticated and removing the helper only reduces
  power. `dyno-helper uninstall`, run elevated, does the same when the daemon is not reachable. Changes made through the
  helper stay in force (they are the user's settings) and stay undoable in the activity log only while the helper is
  installed; Settings says so before uninstalling.
- **Update**: the agent compares `Info.version` with its own; a different version shows "Update the helper" (one OS
  prompt, install again).

### 6. When the helper is asked for

Nothing starts it automatically. The UI shows an item that needs the helper with its preview; if the helper is not
installed the same click opens a dialog that explains the one-time install and the OS prompt, and only after the user
confirms does the agent run the elevated install and then the action. Declining (or a dismissed OS prompt) leaves Dyno
fully working: the item stays listed with the reason and "Install the helper" as the next step. On Windows the traffic
page asks the helper for counters only if it is installed; otherwise it shows the existing "needs administrator
rights" reason with the install step.

## Consequences

- The privileged code is one crate with a typed request set, a pure install plan and a fake backend; every part except
  the three elevation calls and the OS service managers is unit-testable, and none of it installs anything on the
  developer's machine. The elevation and registration themselves are verified by generating and asserting the exact
  files and command lines (plist, unit, `sc.exe` arguments, AppleScript quoting) and, for the real thing, by the manual
  checklist in docs/testing-manual.md on each OS.
- Windows-only code type-checks on the developer's Mac (`cargo check --target x86_64-pc-windows-msvc`) and runs on the
  Windows CI runner; the macOS and Linux daemon registration is verified only by the generated-config tests until a
  person runs the checklist on a spare machine.
- A resident idle root process exists once the user installs the helper; Settings shows its state and removes it.
- Residual risks are listed in section 3; the biggest is the lack of a signature check, accepted until a certificate
  exists.

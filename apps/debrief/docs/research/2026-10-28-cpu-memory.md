# CPU and memory: a measured baseline and the 1.2 performance workstream

Research note, 2026-10-28. Goal from the user: "improve Debrief performance by reducing CPU usage and memory usage",
plus three follow-ups the same day: llama-server at about 8 GB during "Learning human names", that job being too slow,
and a Windows PC turning sluggish while it runs. Scope: Debrief (`apps/debrief`) and the shared crates it uses. The work
packages are slotted into the 1.2 plan ([`docs/plans/debrief-1-2.md`](../../../../docs/plans/debrief-1-2.md), section
"Performance packages"). Inputs: the plugin research (`docs/research/2026-10-plugins-memory-and-manager.md`), the
DuckDB 2.0 and large-data research (`docs/research/2026-10-duckdb-2-and-large-data.md`), the poller survey
(`docs/research/2026-10-poller-pool.md`) and family ADRs 0018 and 0020.

What is **measured** here is marked with the command that produced it. What is **read from the code** cites the file and
line. What is **estimated** (no measurement possible without a model or real Event Viewer data) says so.

## 0. Method and reproduction

- **Machine:** Mac mini, Apple M4 Pro, 14 cores, 64 GB, APFS SSD, macOS (Darwin 27.2). Shared with other agents: load
  averages 3 to 25 during the runs (recorded per run in `*.uptime`), so wall times are ±30 %; CPU seconds, footprints and
  wake-ups are the steadier figures. Every heavy step went through `heavy.sh` with the machine-wide slots, one at a time,
  `CARGO_BUILD_JOBS=2`.
- **Commit:** `origin/main` at `9b14d621e` (Debrief on libduckdb 1.5.6, release profile).
- **Data: synthetic only** (ER-14). `scripts/perf/gen_large.py` (deterministic seeds; from the DuckDB research) writes
  log4net-pattern text with stack traces, CLEF, many small Serilog-text files and gzip text in the shapes of `/samples`.
  Scale 1.0 = 8.07 GB uncompressed (7.2 GB on disk, 56.2 M events, 618 sources; "7.6 GB" below); scale 0.072 = 581 MB
  (4.04 M events, 61 sources; "550 MB" below). Event-log (`.evtx`) data is generated by the plugin research's generator
  (`crates/debrief-plugins/tests/it/evtx_memory.rs`); its numbers are quoted, not re-measured.
- **Memory measure: physical footprint** (rule 26: `ri_phys_footprint` from `proc_pid_rusage(RUSAGE_INFO_V4)`), with RSS
  next to it only to show how far apart they are. `scripts/perf/procsample.py` samples a process and its children every
  250 ms (footprint, lifetime peak footprint, RSS, user+system CPU time, idle and interrupt wake-ups);
  `scripts/perf/perfsum.py` summarises per process and per phase.
- **Harnesses** (committed on this branch, do nothing without their environment variable):
  - Import: `scripts/perf/perf-import.sh LABEL CORPUS STORE` runs the release `debrief import ... --json` (the headless
    CLI, ADR 0044) with the release `debrief-store-worker`, exactly the process split of the app.
  - After the import: `crates/debrief-store-duck/tests/perf_idle.rs` (`DEBRIEF_PERF_STORE=<store>`) reopens the store and
    runs, one after the other, the catalogue build (the full-text index builds concurrently), 60 s idle, 60 s of the name
    watcher's calls, and the name-table rebuild step by step; `scripts/perf/perf-post.sh` samples it.
  - Names: `crates/debrief-core/tests/it/names_perf.rs` `merge_scaling` (ignored; `--ignored --nocapture`).
  - Plugins: `crates/debrief-plugins/tests/it/perf_plugins.rs` (`DEBRIEF_PERF_PLUGINS=1`) warms the 12 built-ins up as
    the app does and idles 60 s; this process stands in for the app (it runs the host's memory watchers); `sample(1)`
    attributed its CPU.
- Not measured: the app process with a window (no GUI in agent runs), llama-server (no model on the machine; read from
  the code), Windows (read from the code; Windows numbers need the CI runner).

Commands, in order (raw results in `/Volumes/d7sst7/dev-targets/research-data/results/perf-2026-10-28/`):

```sh
python3 -I scripts/perf/gen_large.py <data>/mid550 0.072          # 18 s, 581 MB
cargo build --release -p debrief-cli -p debrief-store-worker       # through heavy.sh
scripts/perf/perf-import.sh mid550 <data>/mid550 <data>/stores/mid550
scripts/perf/perf-import.sh large  <data>/large  <data>/stores/large
scripts/perf/perf-post.sh   mid550 <data>/stores/mid550 60
scripts/perf/perf-post.sh   large  <data>/stores/large  60         # then large2 with 30 s (see 1.3)
<release it binary of debrief-core> names_perf:: --ignored --nocapture --test-threads 1
DEBRIEF_PERF_PLUGINS=1 <release it binary of debrief-plugins> perf_plugins:: --nocapture   # + sample <pid> 5
```

## 3. "Learning human names": options and estimates

Assumptions (estimates, flagged): a 550 MB Event Viewer import gives **about 600 groups** with at least 5 events (process
images, services, providers, DLLs; not measurable here, the `.evtx` generator repeats one chunk's four events); decode
speed of an 8 B Q4 model about 40 tokens/s on Apple silicon (Metal) and about 8 tokens/s on an 8-core CPU-only PC
(typical llama.cpp figures, not measured here). Token counts are measured on a synthetic batch of 16 Windows program
names (chars/4): today's prompt ~200 tokens per batch, today's reply up to **~39 tokens per name** (name + 6 aliases in
`{"id","name","aliases"}` objects); a compact reply (name + 2 aliases, positional arrays) **~13 tokens per name**.

Today: 600 × 39 ≈ 23,400 decode tokens: **~10 min on Metal, ~50 min on a CPU-only PC**, holding the 7-8 GB model the
whole time; plus up to 10 min waiting whenever the assistant is busy.

| # | Option | Time for 600 groups (Metal / CPU) | Memory effect | WP (failing test or bench first) |
|---|---|---|---|---|
| 6 | **Quadratic merge fix first** (H5) | Removes up to 15-29 min of one core before the job can start on large name sets; nothing at 600 groups | none | N1 |
| 1 | **Names pack** (TOML, rule 21; built-in + user `packs/`, hot-reloaded through `paddock-packs`): human names and aliases of common Windows, macOS and Linux programs, libraries and services (svchost "Service Host", conhost, lsass, explorer, MsMpEng "Defender antivirus", launchd, systemd...) | Coverage estimate for Event Viewer data: **40-60 % of groups** (Windows' own binaries and providers dominate System/Security logs); → ~5 / ~25 min | none; the pack is a few hundred kB | N4 |
| 2 | **Cross-workspace cache** keyed by scope + normalised key (+ model version), in the config folder next to the global name book | Second and later imports on the same machine: only new names, typically 10-20 % → ~1 / ~5 min | ~1 MB on disk; none in RAM beyond the book | N4 |
| 4 | **Compact reply**: one human name + up to 2-3 aliases, positional JSON under the grammar, `max_tokens` = 16 × 16 per batch | 13 instead of 39 tokens per name: **−67 % decode** → ~3.3 / ~17 min alone | none | N3 |
| 5 | **Bigger batches and 2-4 slots**: batches of 32, `--parallel` 2-4 with `-c` split per slot (bounded by ER-20: slots ≤ physical cores/4 on CPU, 4 on GPU), the 250 ms pause dropped (it waits anyway when the assistant is busy) | Metal: decode is memory-bandwidth-bound, so 4 sequences raise total tokens/s by about 2-2.5× (estimate); CPU: ~1.3×; the pause is 38 × 0.25 = 10 s | KV cache split, not added, if `-c` stays; prompt cache per slot | N5 |
| 3 | **On-demand priority**: groups hit by a search or the assistant go first (a priority queue the job reads before each batch), the rest at background priority | The name the user typed is answered in **one batch: ~5 s Metal, ~25 s CPU** instead of "somewhere in the next 10-50 min" | none | N6 |

Combined (pack 50 %, compact, 4 slots on Metal): 300 × 13 = 3,900 tokens → **~40 s on Metal, ~8 min on a CPU-only PC**;
names the user asks about within seconds; a second workspace in seconds. Order: **N1 (merge) → N3 (compact) → N4 (pack +
cache) → N6 (priority) → N5 (slots)**, with N2 (priority and pause, H10) before any of them on Windows, because a slow job
that leaves the PC usable is acceptable and a fast one that does not is not.

## 4. Budgets and how each is enforced

Two kinds of gate (ER-12, non-flaky): **PR tests that count work** (statements, process-table reads, model calls,
wake-ups on a fake clock): deterministic, no wall clock; and **nightly budgets** in `debrief-bench.yml` through
`paddock-bench` (`budgets.toml` with tolerance and a regression limit against the stored previous result, so one noisy
night is reported and two in a row fail).

| Budget | Value | Measured today | Gate |
|---|---|---|---|
| Idle CPU, every Debrief process, no job running | **≤ 0.5 % of one core and ≤ 1 wake-up/s per process** (target ≈ 0) | app 116 %; store 5.8-11.7 %, 4.4 wake-ups/s; plugins 0 % but 5 wake-ups/s each | PR: catalogue and full-text loops execute 0 statements across N idle turns on a `ManualExecutor`/fake clock; the child watcher reads only the watched pids (a counting `ProcessProbe`: 0 `snapshot()` calls); the name watcher makes 0 `catalogue(all)` calls while `built` is false. Nightly: 60 s idle of the store harness and the plugin harness, CPU-s and wake-ups/s from `proc_pid_rusage` (Linux `/proc/<pid>/stat`), budget 0.3 CPU-s per 60 s per process |
| Peak footprint, store worker, import | **≤ 768 MB** at 550 MB and at 7.6 GB (ADR 0014) | 805 / 1,268 MB | Nightly: plan 4.3's corpus run, footprint (rule 26) |
| Peak footprint, store worker, catalogue phase | **≤ 512 MB** | 390 / 911 MB | Nightly (same run, phase-tagged) |

## 6. Pattern-level issues (ADR candidates, rule 40 / ER-21)

1. **Background work outside the jobs system.** The catalogue build (5 min, 652 CPU-s), the name-table rebuild (inside
   request handlers), the name watcher thread and the alias job's progress all bypass jobs: no progress, no Cancel, no
   priority, invisible in the Jobs pane. Rule: every activity longer than ~100 ms that the user did not start in the
   foreground is a job (ADR 0008) or an executor task with an owner (ADR 0020); a request handler never does it inline.
2. **Polling loops without wake-ups.** Name watcher (500 ms, full catalogue), catalogue and full-text loops (500 ms
   fallbacks with table scans), child memory watchers (200 ms each). ADR 0020 decided the mechanism; the check (its
   WP-12 lint) is what is missing, and it should flag a sleep loop that calls a store or the OS each turn.
3. **A helper that does global work per call.** `process_memory(pid)` builds the whole machine's process table; ADR 0020
   WP-4's `ProcTable` must make the per-pid path the only cheap one, with a counting test over every caller.
4. **Every job kind has an idempotency key.** Duplicate Summarize today; the same shape will recur for imports, exports,
   downloads and every AI request.
5. **Background work runs at background priority, including child processes.** ADR 0020 sets two OS tiers for threads
   (`priority::apply_current`), but child processes started for background work (llama-server, future workers) are not
   covered: the AI worker uses below-normal for everything and every core. ER-20 asks for background priority; this
   is **missing family-wide for child processes**. Rule: a child that serves background work runs in the OS background
   class with a thread bound from ER-20; the launch API takes the class, and a test over every launch site checks it.
6. **Bounded queries bound memory, not only rows** (ADR 0018 amendment). `catalogue(all)` has a 50,000-row limit and
   still runs out of memory at 7.6 GB; ADR 0018's bounded test helper should run each bounded method on a large
   synthetic store under the worker's memory limit.
7. **Memory caps per process with streaming.** Already decided for plugins (plan 2.6, PH4) and imports (4.3, 3.5); the
   same applies to the store's post-import phases (911 MB peak in the catalogue phase).

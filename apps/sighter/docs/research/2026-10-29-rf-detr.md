# Sighter's object detector: RF-DETR, checked again (2026-10-29)

Question (backlog 2026-10-27, "Sighter: use RF-DETR / UI-DETR-1 as detector?"): which detector does Sighter's trained
layer use, under which licence, how does it run from Rust on macOS (Apple Silicon) and Windows, where do its models come
from, and does it run in Pitwall or in Sighter? This note re-checks the family note
[2026-10-sighter-detector](../../../../docs/research/2026-10-sighter-detector.md) (2026-10-27) against the official
sources as they stand today, corrects two of its facts, adds one indicative measurement on this Mac, and feeds
[ADR 0001](../adr/0001-object-detector.md).

How to read it: **verified** means read today in the official repository, package or documentation (URL and date in
the sources), or measured here; **read** means taken from an official page without a way to check it; **(verify)** means
a secondary source or an open point. No Sighter code exists yet; nothing here was measured on UI data.

## Answer in short

- **Use RF-DETR, the Apache-2.0 sizes only (Nano, Small, Medium, Large)**, as the architecture of the per-app detector.
  Train it with the `rfdetr` package (Apache-2.0) in Sighter's managed Python training runtime, export ONNX, and run it
  with `ort` (ONNX Runtime 1.31, statically linked) in Sighter's own inference sidecar, behind the `Detector` port.
- **Default preset Small; Nano for CPU-only runners; Medium or Large as "Accurate".** On this Mac (indicative, see
  section 5) a 640 px tile of RF-DETR-S takes about 30 to 35 ms on the CoreML EP and about 0.2 s on 4 CPU threads; the
  first CoreML compile of a model takes 23 to 49 s, so compiled models must be cached.
- **Never XL, 2XL, Atto, Femto or Pico**: their weights are under Roboflow's PML 1.0 and need `rfdetr[plus]` and a
  Roboflow account. Sighter refuses them by name and by metadata.
- **Fallback: D-FINE** (Apache-2.0 code and weights, CNN backbone), same ONNX adapter. **RT-DETRv4** (Apache-2.0 code,
  ECCV 2026) is a new candidate, but its training distils from DINOv3, whose licence is not permissive: excluded until a
  lawyer-grade reading says the trained weights are free of it.
- **Two corrections to the 2026-10-27 note**: (1) N/S/M/L use patch size 16 and two windows, so input sides must be
  multiples of **32**, not 14; Sighter's 640/960 tiles work as they are. (2) **DEIMv2 is now non-commercial** (its own
  licence, not only the DINOv3 question), so it is excluded, not "pending".
- **Runs in Sighter, not in Pitwall.** Pitwall hosts LLMs and VLMs through llama.cpp; a detector must work without
  Pitwall, per frame, in tens of milliseconds, deterministically. Pitwall stays the VLM layer for bounded, user-started
  requests (rule 46).
- **Models are mostly made, not downloaded.** The runtime detector is always the user's own fine-tuned model. Only the
  COCO start weights (for training) and an optional UI-DETR-1 labeller are downloaded, from a pinned catalogue checked by
  SHA-256 (upstream publishes MD5 only).

### What changed since the 2026-10-27 note

- **Input sides are multiples of 32 for N/S/M/L** (verified in `config.py`: `patch_size = 16`, `num_windows = 2`; the
  check in `detr.py` rejects a resolution not divisible by `patch_size * num_windows`). The "divisible by 14" rule applies
  to the old Base model (patch 14). Our 640 px export of Nano and Small worked (section 5). The design review's tiling
  (1:1 window crops, overlapping tiles) keeps 640 and 960.
- **The package now exports many formats**: ONNX (opset 17 default, optional INT8 quantisation, dynamic batch), CoreML
  `.mlpackage`, a "Core AI" path, OpenVINO, TensorRT, TFLite/LiteRT, ExecuTorch (`src/rfdetr/export/`). Only ONNX is
  needed for `ort`; the CoreML exporter matters only if the CoreML EP route disappoints (section 3).
- **Unreleased (main branch)**: exported ONNX files will carry versioned inference metadata (class layout, preprocessing)
  and other formats a `.rfdetr.json` sidecar with an artifact digest (CHANGELOG "Unreleased"). In 1.11.2 the ONNX file has
  no metadata (checked), so Sighter writes its own `model.json` (proposal section 11) either way and treats upstream
  metadata as a cross-check once released.
- The ONNX graph is small and plain (checked on the Nano and Small exports): 1,424 and 1,539 nodes, opset 17, one input
  `input` `[1,3,H,W]` float32, outputs `dets` `[1,300,4]` (normalised boxes) and `labels` `[1,300,91]` (class logits). No
  NMS: decode is sigmoid plus top-k, pure Rust. Op types are ordinary (MatMul, LayerNormalization, Softmax, Erf, Conv,
  TopK) plus **GridSample** (2 in Nano, 3 in Small) from the deformable-attention decoder.

### Fine-tuning

Unchanged from the family note and verified in the package: COCO-format datasets (which Sighter's studio exports),
augmentation, EMA, early stopping and COCO evaluation, Python ≥ 3.10, PyTorch Lightning based. The Kornia GPU augmentation
backend changed behaviour in the unreleased version (CHANGELOG): pin the package version in the training runtime and
record it in each model card. Training belongs to the managed Python runtime the user accepted on 2026-10-24 (proposal
section 6); inference stays Rust.

## 3. Running it from Rust

### `ort` and ONNX Runtime (verified 2026-10-29)

- `ort` 2.0.0-rc.15 (crates.io, 2026-10-19, MIT OR Apache-2.0) binds **ONNX Runtime 1.31** (MIT). Its build script
  downloads pyke's prebuilt static libraries, listed with SHA-256 in `build/download/dist.tsv`: `aarch64-apple-darwin+coreml`,
  `x86_64-pc-windows-msvc+directml` (also `+webgpu`, `+openvino`, `+cuda13,tensorrt,nvrtx,directml`), `aarch64-pc-windows-msvc+directml`,
  Linux x64/arm64 (CPU, CUDA, OpenVINO, WebGPU, MIGraphX). **No `x86_64-apple-darwin`**: fine, Intel Macs were dropped
  (user, 2026-10-27).
- Static linking keeps rule 23 safe on macOS: Pacenotes ADR 0001 built it on this machine and found no vendor dylib in
  `otool -L` (`load-dynamic` and `copy-dylibs` must stay off). The static build links the CoreML and Foundation frameworks
  (`build/static_link/mod.rs`), which are system frameworks.
- **Windows**: pyke's Windows libraries are always built with DirectML, so the binary links `DXGI`, `D3D12` and
  `DirectML` (`build/static_link/mod.rs` line 49). DirectML 1.15.2 is what ONNX Runtime's DirectML EP uses; whether the
  `DirectML.dll` in System32 (Windows 10 1903 and later) is new enough or the redistributable must ship next to the
  sidecar is **not stated** on ONNX Runtime's page (verify on the Windows runner; this is the one Windows packaging risk).
- **EP behaviour** (ort docs): registered EPs are tried in order, unsupported nodes fall to the next one and finally the
  CPU; if every EP fails to register, `ort` silently runs on the CPU unless `.error_on_failure()` is set. Sighter sets it
  for the EP the user chose and reports the EP actually used in every response (the design review's determinism P2).
- **CoreML EP** (ONNX Runtime docs): `ModelFormat=MLProgram` is needed for this graph: GridSample (4-D, linear or zeros),
  LayerNormalization and Gelu are listed only for MLProgram. `Attention` is not listed, but the RF-DETR export has no
  fused Attention node (checked). `ModelCacheDirectory` caches compiled models but never evicts them; Sighter must key and
  clean that cache itself. `MLComputeUnits` picks CPU-only, CPU+GPU, CPU+ANE or all; the ANE is never guaranteed.
- **DirectML EP** (ONNX Runtime docs): opset ≤ 20 (our export is 17), **sustained engineering** (no new features; new
  work goes to Windows ML), memory patterns off, sequential execution, and **one `Run` at a time per session**: the
  sidecar keeps one session per worker thread or serialises calls. 5-D GridSample is unsupported; ours is 4-D.

## 4. Where it runs: Sighter's sidecar, not Pitwall

The family's port pattern says the core depends on a port and an adapter does the work; it does not say the adapter must
live in Pitwall. Weighed against Sighter's needs:

| Need | In Pitwall | In Sighter's `sighter-infer` sidecar |
|---|---|---|
| Works without Pitwall (Sighter AGENTS.md: "Pitwall is always optional") | No: locate and unattended CI runs would need Pitwall | **Yes** |
| Per-frame latency (locate p50 ≤ 80 ms GPU, p95 ≤ 600 ms CPU) | HTTP hop plus image encoding per tile on loopback | In-process tensors over `paddock-ipc`, frames by shared buffer or file |
| Determinism (record EP, runtime version, model hash) | Pitwall's model management would also have to own Sighter's ONNX models | Sighter owns model, EP choice and the record |
| New runtime in the host | Pitwall would need ONNX Runtime next to llama.cpp, for one client | Sighter needs ONNX Runtime anyway for PaddleOCR (proposal section 8) |
| Fault containment | A C++ abort would take down the family's AI host | Ends one request; the server restarts the sidecar (`paddock-proc` `Supervised`, memory cap, rule 26) |
| Rule 46 (no LLM for large jobs) | n/a | The detector is exactly the deterministic bulk path; the VLM stays for bounded, user-started requests |

So: `sighter-core` owns the `Detector` port; `sighter-infer` is the `ort` adapter in its own sidecar (started through
`paddock-ipc` `launch`, supervised by `paddock-proc`, answering `--self-test` per rule 23), shared by the detector and
OCR. Rule 42: no second Paddock app runs ONNX Runtime today (Pacenotes rejected it in ADR 0001), so this stays in Sighter;
if a second app needs it, the `ort` session handling moves to a shared crate, still not into Pitwall.

Jobs (ER-17 to ER-20, rules 10 to 14, ADR 0024): locating is a request, not a job. Everything long is a `paddock-jobs`
job with phases on their own scales and Cancel: model download (`download`, `verify`, `self-test`), detector pre-labelling
of a recording (a growing frame count, at background priority, one session per EP and batched tiles, bounded by memory,
not cores), evaluation, and training (in the Python worker, epochs and steps). CoreML's first compile of a model took
23 to 49 s here (section 5): it is a labelled phase ("Preparing the model for this Mac"), and the compiled cache makes it once per
model version.

## 5. Indicative measurement on this Mac

One short run of exported RF-DETR Nano and Small (COCO weights, `rfdetr` 1.11.2, ONNX opset 17, fp32) through ONNX
Runtime 1.31.1 (Python wheel; same runtime version as `ort` rc.15) on the CPU EP (4 intra-op threads) and the CoreML EP
(MLProgram), on a synthetic random tensor, at `nice 19` on a shared machine. **Indicative only**: other agents' CI was
running, the input is random noise (DETR cost does not depend on content), and the Python wheel is not the static `ort`
build. Results block: [performance.md, 2026-10-29 RF-DETR ONNX latency](../performance.md#2026-10-29-rf-detr-onnx-latency-indicative-docssighter-rfdetr).

Batch 1, 5 warm-up runs, 30 timed runs per row, one process per row; Mac mini M4 Pro, 14 cores, 64 GB, macOS 27.2;
1-minute load 17.9 to 24.4 during the timed runs.

| Model, input | CPU EP p50 / p95 | CoreML ALL p50 / p95 | CoreML CPU+GPU p50 / p95 | CoreML session creation |
|---|---|---|---|---|
| Nano, 384 | 72 / 132 ms | 23 / 31 ms | 17 / 19 ms | 44 s (ALL), 23 s (CPU+GPU) |
| Nano, 640 | 142 / 170 ms | 35 / 45 ms | 30 / 32 ms | 40 s, 26 s |
| Small, 512 | 99 / 131 ms | 19 / 22 ms | not run (load guard) | 42 s |
| Small, 640 | 179 / 276 ms | 35 / 44 ms | 30 / 32 ms | 49 s, 23 s |

What it says, within its limits:

- **CoreML takes almost the whole graph**: 2 partitions, 802 of 808 nodes (Nano) and 871 of 877 (Small) after ONNX
  Runtime's own fusions. On a GPU-class path a 640 tile is about 30 ms, inside the proposal's "< 50 ms on a GPU at 640 px".
- **CPU**: one 640 tile of Small is about 0.2 s at 4 threads under load. A 1080p frame tiled at 640 is about six tiles,
  so a whole-frame locate on the CPU would be over the 600 ms p95 budget; locating within the target window or a region
  (the design review's 1:1 window crops) or Nano is what makes the CPU path fit. To be measured on the runner class.
- **CoreML session creation took 23 to 49 s** (model compilation, no cache configured), against the 1.5 s cold-load
  budget. The `ModelCacheDirectory` option (keyed by model hash) is therefore required, and the first preparation of each
  model version is a job phase, not part of a request. The CPU EP created sessions in 0.2 to 0.3 s.
- Physical footprint after the runs: 181 to 440 MB per process (one model, one EP), well inside the 1.5 GB server budget
  for three models, though the CPU EP at 640 px is the largest (413 to 440 MB).

Sizes on disk (files, not timings): the COCO checkpoints the package downloads are 366 MB (Nano) and 386 MB (Small) as
`.pth`; the exported ONNX files are 108 MB (Nano, 384 px), 109 MB (Nano, 640 px), 114 MB (Small, 512 px) and 115 MB
(Small, 640 px) in fp32. Parameter counts barely change from N to L (30.5 to 33.9 M), so every Apache size is about
110–130 MB in fp32 (estimate for M/L); fp16 or INT8 roughly halves or quarters that (not measured).

## 6. Where models come from and how they are distributed

| Model | Needed for | Source | Size | Distribution |
|---|---|---|---|---|
| The user's trained detector (ONNX + `model.json`) | Locating, pre-labelling | Made locally by the training runtime | ~110–130 MB fp32 | Lives in the project's model registry, content-hashed, immutable (proposal "Versions"); never downloaded |
| RF-DETR N/S/M/L COCO checkpoints (`.pth`) | Start weights for training | `repo.roboflow.com/rfdetr/...` | 366–386 MB (N, S measured) | Downloaded on request by the training runtime, from a catalogue pinned in Sighter |
| UI-DETR-1 (optional) | Day-one box proposals, spike start weights | Hugging Face `racineai/UI-DETR-1` | ~130 MB (verify) | Opt-in download, hash-pinned, licence shown before download |
| Self-test model | Sidecar `--self-test` (rule 23) | Generated in CI: a tiny ONNX with the same input/output contract | KBs | Bundled |

Verification: upstream pins **MD5** for each checkpoint (`model_weights.py`), which catches corruption, not tampering.
Sighter's catalogue (the `paddock-runtime` catalogue pattern: one TOML entry per file with URL, size and **SHA-256**,
parsed once, anything wrong refuses the whole catalogue) pins its own SHA-256, computed when the entry is added, and
`paddock-download` hashes while writing (rule 15). The training runtime gets the file path, never the URL. Whether to
mirror the Apache checkpoints on our own Gitea release (Apache-2.0 allows redistribution with the licence and notice) is
an open question: it removes the dependency on Roboflow's URLs, which already moved once (`rf-detr-large.pth` to
`rf-detr-large-2026.pth`).

Nothing ships in the installer except the self-test model: the base checkpoints are only needed by users who train, and
the training runtime is itself a download.

## 7. Risks

- **CPU on Windows runners** without a GPU: not measured. If Small at 640 px misses p95 ≤ 600 ms per locate on the
  8-core runner, Nano or the D-FINE fallback is the CPU preset.
- **DirectML's future**: sustained engineering. Plan Windows ML (ONNX Runtime with automatic EP selection) as the later
  route; DirectML is fine for v1. The `DirectML.dll` question is open.
- **CoreML compile time and partitions**: 2 partitions and 23 to 49 s to create a session here (section 5). A stale or
  missing compiled cache turns into a long "preparing" phase; the cache needs keys and cleanup. The CPU EP is the
  reference path and the determinism baseline.
- **Upstream churn**: `rfdetr` releases often (1.10.0 to 1.11.2 in a month; breaking changes queued). Pin the version in
  the training runtime, re-validate export on each bump, and store the version in each model card.
- **Licence drift**: Roboflow moved five sizes to PML 1.0 and Intellindust moved DEIMv2 to a non-commercial licence. The
  model card records the licence per checkpoint at the time of download, and the catalogue refuses anything not on its
  Apache allow-list.

## 8. Spike checklist (when Sighter code starts)

1. Export N/S/M/L (and D-FINE-S) to ONNX with the pinned `rfdetr`; load in static `ort` on macOS arm64, Windows x64 and
   Linux x64; run the sidecar `--self-test`.
2. Time a 640 tile and a 1080p frame tiled 1:1, batch 1 and batch 8, on CPU (cores−1 and 4 threads), CoreML (ALL and
   CPU+GPU) and DirectML; record CoreML partition counts and first-compile time; record footprint (rule 26). Results blocks
   in performance.md.
3. Fine-tune Small on one synthetic legacy-style app (1k frames) from COCO and from UI-DETR-1; compare mAP@0.5:0.95 per
   class and wrong-click rate.
4. Load the same ONNX in `tract`; works or names the missing op.
5. Windows: does the system `DirectML.dll` suffice, or must the redistributable ship (and does that keep the installer
   signing story intact)?

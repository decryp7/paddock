# Sighter's object detector: RF-DETR, checked again (2026-10-29)

Question (backlog 2026-10-27, "Sighter: use RF-DETR / UI-DETR-1 as detector?"): which detector does Sighter's trained
layer use, under which licence, how does it run from Rust on macOS (Apple Silicon) and Windows, where do its models come
from, and does it run in Pitwall or in Sighter? This note re-checks the family note
[2026-10-sighter-detector](../../../../docs/research/2026-10-sighter-detector.md) (2026-10-27) against the official
sources as they stand today, corrects two of its facts, adds one indicative measurement on this Mac, and feeds
[ADR 0001](../adr/0001-object-detector.md).

How to read it: **verified** means read today in the official repository, package or documentation (URL and date in
the sources), or measured here; **read** means taken from an official page without a way to check it; **(verify)** means
a secondary source or an open point. No Sighter code exists yet; nothing here was measured on UI data.

## Answer in short

**User decisions, 2026-10-29** (recorded in [ADR 0001](../adr/0001-object-detector.md)): RF-DETR Small is the default
detector, Nano the CPU preset, Medium or Large "Accurate", D-FINE the fallback behind the same ONNX adapter; the Apache
COCO checkpoints are mirrored on our Gitea and pinned to our own SHA-256s; UI-DETR-1 is not in v1; whole recordings are
pre-labelled by the user's own detector, and Pitwall's VLM only labels small user-chosen selections or runs after a
confirmation that states the frame count (rule 46); RT-DETRv4 gets a licence review and stays pending (section 9);
Sighter ships Microsoft's DirectML redistributable, approved as a named licence exception for that file only (section
11), on condition that the spike's egress test shows it makes no outbound connection; ONNX Runtime is self-built with
`--no_telemetry` (section 12); RF-DETR's checkpoints are accepted on Roboflow's Apache-2.0 label despite their
Objects365 lineage, because Sighter is personal and non-commercial (section 10); an opt-in CUDA training runtime is an
approved licence exception (section 11); the proposal 9.1 amendment is approved and applied. Nothing is open. Screens up to 5K and HiDPI: ADR 0001,
"Screen resolutions and HiDPI" (section 13 here). The bullets below are the research's recommendation as written before those decisions; where a decision differs, it wins.

- **Use RF-DETR, the Apache-2.0 sizes only (Nano, Small, Medium, Large)**, as the architecture of the per-app detector.
  Train it with the `rfdetr` package (Apache-2.0) in Sighter's managed Python training runtime, export ONNX, and run it
  with `ort` (ONNX Runtime 1.31, statically linked; self-built without telemetry, decided) in Sighter's own inference
  sidecar, behind the `Detector` port.
- **Default preset Small; Nano for CPU-only runners; Medium or Large as "Accurate"** (decided). On this Mac (indicative, see
  section 5) a 640 px tile of RF-DETR-S takes about 30 to 35 ms on the CoreML EP and about 0.2 s on 4 CPU threads; the
  first CoreML compile of a model takes 23 to 49 s, so compiled models must be cached.
- **Never XL, 2XL, Atto, Femto or Pico**: their weights are under Roboflow's PML 1.0 and need `rfdetr[plus]` and a
  Roboflow account. Sighter refuses them by name and by metadata.
- **Fallback: D-FINE, COCO-only checkpoints** (Apache-2.0 code and weights, CNN backbone), same ONNX adapter (decided).
  **RT-DETRv4** (Apache-2.0 code, ECCV 2026) is a new candidate, but its training distils from DINOv3, whose licence is
  not permissive, and its checkpoints state no licence: pending its licence review (section 9).
- **Two corrections to the 2026-10-27 note**: (1) N/S/M/L use patch size 16 and two windows, so input sides must be
  multiples of **32**, not 14; Sighter's 640/960 tiles work as they are. (2) **DEIMv2 is now non-commercial** (its own
  licence, not only the DINOv3 question), so it is excluded, not "pending".
- **Runs in Sighter, not in Pitwall.** Pitwall hosts LLMs and VLMs through llama.cpp; a detector must work without
  Pitwall, per frame, in tens of milliseconds, deterministically. Pitwall stays the VLM layer for bounded, user-started
  requests (rule 46). Whole recordings are pre-labelled by the user's own detector (decided).
- **Models are mostly made, not downloaded.** The runtime detector is always the user's own fine-tuned model. Only the
  COCO start weights (for training) are downloaded, from our Gitea mirror through a catalogue pinned to our own SHA-256s
  (decided; upstream publishes MD5 only). UI-DETR-1 is not in v1 (decided).

### What changed since the 2026-10-27 note

- **Input sides are multiples of 32 for N/S/M/L** (verified in `config.py`: `patch_size = 16`, `num_windows = 2`; the
  check in `detr.py` rejects a resolution not divisible by `patch_size * num_windows`). The "divisible by 14" rule applies
  to the old Base model (patch 14). Our 640 px export of Nano and Small worked (section 5). The design review's tiling
  (1:1 window crops, overlapping tiles) keeps 640 and 960.
- **The package now exports many formats**: ONNX (opset 17 default, optional INT8 quantisation, dynamic batch), CoreML
  `.mlpackage`, a "Core AI" path, OpenVINO, TensorRT, TFLite/LiteRT, ExecuTorch (`src/rfdetr/export/`). Only ONNX is
  needed for `ort`; the CoreML exporter matters only if the CoreML EP route disappoints (section 3).
- **Unreleased (main branch)**: exported ONNX files will carry versioned inference metadata (class layout, preprocessing)
  and other formats a `.rfdetr.json` sidecar with an artifact digest (CHANGELOG "Unreleased"). In 1.11.2 the ONNX file has
  no metadata (checked), so Sighter writes its own `model.json` (proposal section 11) either way and treats upstream
  metadata as a cross-check once released.
- The ONNX graph is small and plain (checked on the Nano and Small exports): 1,424 and 1,539 nodes, opset 17, one input
  `input` `[1,3,H,W]` float32, outputs `dets` `[1,300,4]` (normalised boxes) and `labels` `[1,300,91]` (class logits). No
  NMS: decode is sigmoid plus top-k, pure Rust. Op types are ordinary (MatMul, LayerNormalization, Softmax, Erf, Conv,
  TopK) plus **GridSample** (2 in Nano, 3 in Small) from the deformable-attention decoder.

### Fine-tuning

Unchanged from the family note and verified in the package: COCO-format datasets (which Sighter's studio exports),
augmentation, EMA, early stopping and COCO evaluation, Python ≥ 3.10, PyTorch Lightning based. The Kornia GPU augmentation
backend changed behaviour in the unreleased version (CHANGELOG): pin the package version in the training runtime and
record it in each model card. Training belongs to the managed Python runtime the user accepted on 2026-10-24 (proposal
section 6, family note; ADR 0001 closes proposal section 15 question 1); inference stays Rust. The worker runs with no
network: `rfdetr`'s DINOv2 backbone code calls Hugging Face `from_pretrained` (`models/backbone/dinov2.py`), so the
worker sets `HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1` and the sandbox denies outbound connections; whatever it
needs locally (configs) comes with the runtime (spike item).

## 3. Running it from Rust

### `ort` and ONNX Runtime (verified 2026-10-29)

- `ort` 2.0.0-rc.15 (crates.io, 2026-10-19, MIT OR Apache-2.0) binds **ONNX Runtime 1.31** (MIT; pyke's archives are
  1.31.0). **Sighter does not use pyke's archives** (decided: self-built with `--no_telemetry`, section 12), but they are
  the reference for what a build contains. The build script by default downloads pyke's prebuilt static libraries, listed with SHA-256 in `build/download/dist.tsv`: `aarch64-apple-darwin+coreml`,
  `x86_64-pc-windows-msvc+directml` (also `+webgpu`, `+openvino`, `+cuda13,tensorrt,nvrtx,directml`), `aarch64-pc-windows-msvc+directml`,
  Linux x64 (CPU, CUDA, OpenVINO, WebGPU, MIGraphX) and Linux arm64 (CPU and CUDA only). **No `x86_64-apple-darwin`**: fine, Intel Macs were dropped
  (user, 2026-10-27).
- Static linking keeps rule 23 safe on macOS: Pacenotes ADR 0001 built it on this machine and found no vendor dylib in
  `otool -L` (`load-dynamic` and `copy-dylibs` must stay off). The static build links the CoreML and Foundation frameworks
  (`build/static_link/mod.rs`), which are system frameworks.
- **Windows**: pyke's Windows libraries are always built with DirectML, so the binary links `dxguid`, `DXCORE`, `DXGI`,
  `D3D12` and `DirectML` as imports (`build/static_link/mod.rs` lines 47–55); nothing in `ort-sys` delay-loads them, so a
  missing or too old `DirectML.dll` can stop even a CPU-only start (spike item). pyke's Windows archive ships
  `DirectML.dll` itself (checked: 18,527,776 bytes, file version 1.15.4) next to `onnxruntime.lib`. ONNX Runtime's
  DirectML page says the EP uses DirectML 1.15.2 and does not say whether System32's copy suffices. Decided: Sighter
  ships the redistributable `DirectML.dll` next to the sidecar, as a named licence exception (section 11).
- **EP behaviour** (ort docs): registered EPs are tried in order, unsupported nodes fall to the next one and finally the
  CPU; if every EP fails to register, `ort` silently runs on the CPU unless `.error_on_failure()` is set. Sighter sets it
  for the EP the user chose and reports the EP actually used in every response (the design review's determinism P2).
- **CoreML EP** (ONNX Runtime docs): `ModelFormat=MLProgram` is needed for this graph: GridSample (4-D, linear or zeros),
  LayerNormalization and Gelu are listed only for MLProgram. `Attention` is not listed, but the RF-DETR export has no
  fused Attention node (checked). `ModelCacheDirectory` caches compiled models but never evicts them; Sighter must key and
  clean that cache itself. `MLComputeUnits` picks CPU-only, CPU+GPU, CPU+ANE or all; the ANE is never guaranteed.
- **DirectML EP** (ONNX Runtime docs): opset ≤ 20 (our export is 17), **sustained engineering** (no new features; new
  work goes to Windows ML), memory patterns off, sequential execution, and **one `Run` at a time per session**: the
  sidecar keeps one session per worker thread or serialises calls. 5-D GridSample is unsupported; ours is 4-D.

## 4. Where it runs: Sighter's sidecar, not Pitwall

The family's port pattern says the core depends on a port and an adapter does the work; it does not say the adapter must
live in Pitwall. Weighed against Sighter's needs:

| Need | In Pitwall | In Sighter's `sighter-infer` sidecar |
|---|---|---|
| Works without Pitwall (Sighter AGENTS.md: "Pitwall is always optional") | No: locate and unattended CI runs would need Pitwall | **Yes** |
| Per-frame latency (locate p50 ≤ 80 ms GPU, p95 ≤ 600 ms CPU) | HTTP hop plus image encoding per tile on loopback | In-process tensors over `paddock-ipc`, frames by shared buffer or file |
| Determinism (record EP, runtime version, model hash) | Pitwall's model management would also have to own Sighter's ONNX models | Sighter owns model, EP choice and the record |
| New runtime in the host | Pitwall would need ONNX Runtime next to llama.cpp, for one client | Sighter needs ONNX Runtime anyway for PaddleOCR (proposal section 8) |
| Fault containment | A C++ abort would take down the family's AI host | Ends one request; the server restarts the sidecar (`paddock-proc` `Supervised`, memory cap, rule 26) |
| Rule 46 (no LLM for large jobs) | n/a | The detector is exactly the deterministic bulk path; the VLM stays for bounded, user-started requests |

So: `sighter-core` owns the `Detector` port; `sighter-infer` is the `ort` adapter in its own sidecar (started through
`paddock-ipc` `launch`, supervised by `paddock-proc`, answering `--self-test` per rule 23), shared by the detector and
OCR. Rule 42: no second Paddock app runs ONNX Runtime today (Pacenotes rejected it in ADR 0001), so this stays in Sighter;
if a second app needs it, the `ort` session handling moves to a shared crate, still not into Pitwall.

Jobs (ER-17 to ER-20, rules 10 to 14, ADR 0024): locating is a request, not a job. Everything long is a `paddock-jobs`
job with phases on their own scales and Cancel: model download (`download`, `verify`, `self-test`), detector pre-labelling
of a recording (a growing frame count, at background priority, one session per EP and batched tiles, bounded by memory,
not cores), evaluation, and training (in the Python worker, epochs and steps). CoreML's first compile of a model took
23 to 49 s here (section 5): it is a labelled phase ("Preparing the model for this Mac"), and the compiled cache makes it once per
model version.

## 5. Indicative measurement on this Mac

One short run of exported RF-DETR Nano and Small (COCO weights, `rfdetr` 1.11.2, ONNX opset 17, fp32) through ONNX
Runtime 1.31.1 (the official Python wheel; `ort` rc.15's archives are 1.31.0) on the CPU EP (4 intra-op threads) and the CoreML EP
(MLProgram), on a synthetic random tensor, at `nice 19` on a shared machine. **Indicative only**: other agents' CI was
running, the input is random noise (DETR cost does not depend on content), and the Python wheel is not the static `ort`
build. Telemetry was **not** disabled in that run: the official wheel is a build with telemetry on by default (section
12). The CoreML results were not checked for correctness against the CPU EP (the ANE computes in fp16, and RF-DETR's own
docs report class logits collapsing in fp16 on OpenVINO, section 11): a spike item. The scripts are in
[scripts/](scripts/). Results block: [performance.md, 2026-10-29 RF-DETR ONNX latency](../performance.md#2026-10-29-rf-detr-onnx-latency-indicative-docssighter-rfdetr).

Batch 1, 5 warm-up runs, 30 timed runs per row, one process per row; Mac mini M4 Pro, 14 cores, 64 GB, macOS 27.2;
1-minute load 17.9 to 24.4 during the timed runs.

| Model, input | CPU EP p50 / p95 | CoreML ALL p50 / p95 | CoreML CPU+GPU p50 / p95 | CoreML session creation |
|---|---|---|---|---|
| Nano, 384 | 72 / 132 ms | 23 / 31 ms | 17 / 19 ms | 44 s (ALL), 23 s (CPU+GPU) |
| Nano, 640 | 142 / 170 ms | 35 / 45 ms | 30 / 32 ms | 40 s, 26 s |
| Small, 512 | 99 / 131 ms | 19 / 22 ms | not run (load guard) | 42 s |
| Small, 640 | 179 / 276 ms | 35 / 44 ms | 30 / 32 ms | 49 s, 23 s |

What it says, within its limits:

- **CoreML takes almost the whole graph**: 2 partitions, 802 of 808 nodes (Nano) and 871 of 877 (Small) after ONNX
  Runtime's own fusions. On a GPU-class path a 640 tile is about 30 ms, inside the proposal's "< 50 ms on a GPU at 640 px".
- **CPU**: one 640 tile of Small is about 0.2 s at 4 threads under load. A 1080p frame tiled at 640 is about six tiles,
  so a whole-frame locate on the CPU would be over the 600 ms p95 budget; locating within the target window or a region
  (the design review's 1:1 window crops) or Nano is what makes the CPU path fit. To be measured on the runner class.
- **CoreML session creation took 23 to 49 s** (model compilation, no cache configured), against the 1.5 s cold-load
  budget. The `ModelCacheDirectory` option (keyed by model hash) is therefore required, and the first preparation of each
  model version is a job phase, not part of a request. The CPU EP created sessions in 0.2 to 0.3 s.
- Physical footprint after the runs: 181 to 440 MB per process (one model, one EP), well inside the 1.5 GB server budget
  for three models, though the CPU EP at 640 px is the largest (413 to 440 MB).

Sizes on disk (files, not timings): the COCO checkpoints the package downloads are 366 MB (Nano) and 386 MB (Small) as
`.pth`; the exported ONNX files are 108 MB (Nano, 384 px), 109 MB (Nano, 640 px), 114 MB (Small, 512 px) and 115 MB
(Small, 640 px) in fp32. Parameter counts barely change from N to L (30.5 to 33.9 M), so every Apache size is about
110–130 MB in fp32 (estimate for M/L); fp16 or INT8 roughly halves or quarters that (not measured).

## 6. Where models come from and how they are distributed

| Model | Needed for | Source | Size | Distribution |
|---|---|---|---|---|
| The user's trained detector (ONNX + `model.json`) | Locating, pre-labelling | Made locally by the training runtime | ~110–130 MB fp32 | Lives in the project's model registry, content-hashed, immutable (proposal "Versions"); never downloaded |
| RF-DETR N/S/M/L COCO checkpoints (`.pth`) | Start weights for training | Mirrored from `repo.roboflow.com/rfdetr/...` to our Gitea (decided) | 366–386 MB (N, S measured) | Downloaded on request by the training runtime, from a catalogue pinned in Sighter |
| UI-DETR-1 | (Day-one box proposals) | Hugging Face `racineai/UI-DETR-1` | 535 MB (`model.pth`, checked) | **Not in v1** (decided) |
| Self-test model | Sidecar `--self-test` (rule 23) | Generated in CI: a tiny ONNX with the same input/output contract | KBs | Bundled |

Verification: upstream pins **MD5** for each checkpoint (`model_weights.py`), which catches corruption, not tampering.
Sighter's catalogue (the `paddock-runtime` catalogue pattern: one TOML entry per file with URL, size and **SHA-256**,
parsed once, anything wrong refuses the whole catalogue) pins its own SHA-256, computed when the entry is added, and
`paddock-download` hashes while writing (rule 15), behind `paddock-net`'s `Egress` (host allow-list: our Gitea). Share
first (rule 42): Pacenotes' Model2Vec `potion-code` download and, most likely, Pitwall's model downloads (verify) are the
same need, so this is the third case and the catalogue becomes a shared single-file asset kind in `paddock-runtime` (ADR 0001 plan item P3). The
Python training runtime is itself a `paddock-runtime` entry. The training runtime gets the file path, never the URL. **Decided
(user, 2026-10-29): the Apache checkpoints are mirrored on our Gitea (dev.decryptology.net)**, with the licence and a
notice (Apache-2.0 allows redistribution), and pinned to our own SHA-256s; upstream's MD5s are checked once, when the
mirror is made. This removes the dependency on Roboflow's URLs, which already moved once (`rf-detr-large.pth` to
`rf-detr-large-2026.pth`). The upload (about 1.5 GB) is ADR 0001's plan item P1 and needs the user's OK when it happens.

Nothing ships in the installer except the self-test model: the base checkpoints are only needed by users who train, and
the training runtime is itself a download.

## 7. Risks

- **CPU on Windows runners** without a GPU: not measured. If Small at 640 px misses p95 ≤ 600 ms per locate on the
  8-core runner, Nano or the D-FINE fallback is the CPU preset.
- **DirectML's future**: sustained engineering. Plan Windows ML (ONNX Runtime with automatic EP selection) as the later
  route; DirectML is fine for v1. `DirectML.dll` ships with the sidecar under a named licence exception (section 11);
  its terms allow Microsoft data collection, which the egress test must also watch on Windows.
- **Telemetry**: ONNX Runtime 1.31 builds telemetry in by default (section 12). Decided: self-build with
  `--no_telemetry`, plus the runtime opt-out and an egress test.
- **Objects365 lineage** of RF-DETR's checkpoints (section 10): accepted by the user for personal, non-commercial
  use; revisit before any commercial use.
- **fp16**: RF-DETR's docs report class logits collapsing in fp16 (OpenVINO on an M4 Max). CoreML on the ANE and any NPU
  compute in fp16: check results, not only speed.
- **CoreML compile time and partitions**: 2 partitions and 23 to 49 s to create a session here (section 5). A stale or
  missing compiled cache turns into a long "preparing" phase; the cache needs keys and cleanup. The CPU EP is the
  reference path and the determinism baseline.
- **Upstream churn**: `rfdetr` releases often (1.10.0 to 1.11.2 in a month; breaking changes queued). Pin the version in
  the training runtime, re-validate export on each bump, and store the version in each model card.
- **Licence drift**: Roboflow moved five sizes to PML 1.0 and Intellindust moved DEIMv2 to a non-commercial licence. The
  model card records the licence per checkpoint at the time of download, and the catalogue refuses anything not on its
  Apache allow-list.

## 9. Licence review: weights distilled from DINOv3 (RT-DETRv4)

The user's question (2026-10-29): when a model is trained by distillation from DINOv3, does it inherit DINOv3's licence?
What the official texts say, read 2026-10-29. This is a reading of the documents, not legal advice.

**What RT-DETRv4 is.** The repository (`AIMIA-EAI/RT-DETRv4`, `LICENSE`: Apache-2.0) trains an HGNetv2 CNN detector and
uses "a pre-trained Vision Foundation Model (VFM) as the teacher. We use the ViT-B/16-LVD-1689M model from DINOv3",
downloaded by the user from Meta's DINOv3 page and configured as `teacher_model: DINOv3TeacherModel`. At inference the
student runs alone. The released checkpoints are Google Drive links in the README; **no licence is stated for them**
(the badge and `LICENSE` cover the repository), and whether a checkpoint file also holds teacher parameters is not
stated (inspect its keys).

**What the DINOv3 licence says** (DINOv3 License, last updated 2025-08-19):

- "DINO Materials" are what Meta distributes: "the models, software and algorithms, including machine-learning model
  code, trained model weights, inference-enabling code, training-enabling code, fine-tuning enabling code".
- Grant: use, reproduce, distribute, copy, "create derivative works of, and make modifications to the DINO Materials",
  royalty-free, worldwide. **There is no non-commercial clause.**
- Pass-through: "Distribution of DINO Materials, and any derivative works thereof, are subject to the terms of this
  Agreement", with a copy of the Agreement.
- Restrictions: comply with trade controls; no ITAR uses or end uses "related to military or warfare purposes, nuclear
  industries or applications, espionage"; no reverse engineering of the DINO Materials; acknowledge DINO in publications.
- Ownership: "with respect to any derivative works and modifications of the DINO Materials that are made by you ... you
  are and will be the owner of such derivative works".
- Meta "may modify this Agreement from time to time"; changes are "effective immediately"; continued use is acceptance.
- **"Derivative works" is not defined.** "Output and results" appear only in the warranty disclaimer and the litigation
  clause; the licence places **no restriction on outputs** and says nothing about models trained on outputs or features.

**What follows:**

- A distilled student holds none of DINOv3's parameters (assuming the checkpoint has no teacher keys) and a different
  architecture; it learned from DINOv3's **outputs** (features). The licence restricts the Materials and their
  derivative works, not outputs. On that reading the student is not a derivative work and the DINOv3 terms do not pass
  to it.
- The other reading treats a model trained to imitate DINOv3's features as a derivative work. Then the DINOv3 terms pass
  through: non-OSI, field-of-use restrictions, terms Meta can change at will. That is incompatible with Sighter's
  permissive-only rule. No official source found settles which reading holds; the law on training from another model's
  outputs is unsettled.
- Independently of that, **the checkpoints have no licence** at all, so there is no explicit grant to use or redistribute
  them even on the first reading.
- If Sighter ever trained RT-DETRv4 with its distillation recipe, Sighter's training runtime would itself download and
  use DINOv3, and would be bound by the DINOv3 licence directly. Fine-tuning a released student without the teacher
  avoids that.

**To clear it (ADR 0001 plan item P4):** (1) ask the authors to state a licence for the checkpoints and whether they hold
teacher weights; (2) inspect one checkpoint's keys; (3) get a reading on DINOv3-distilled weights (or a statement from
Meta). **Status: pending; not in the catalogue.**

## 10. Objects365 lineage

- **RF-DETR**: the paper says "we pseudo-label Objects-365 ... with SAM2 ... to allow us to pre-train the segmentation and
  detection heads on the same data", and the ablations note models "pretrained with 60 epochs of Objects-365" (arXiv
  2511.09554, appendix A and section 3; read 2026-10-29). `model_weights.py` also lists an Objects365 LW-DETR checkpoint
  (`lwdetr_dinov2_small_o365_checkpoint.pth`). Roboflow labels the N/S/M/L COCO checkpoints Apache-2.0.
- **D-FINE**: its README marks the `*_obj365` and `*_obj2coco` checkpoints: they "may be subject to the Objects365 dataset
  terms and should not be assumed to be commercially cleared under the D-FINE license". Its COCO-only checkpoints have no
  such note (the RF-DETR paper also says D-FINE nano "was not pretrained on Objects-365").
- **Objects365**: its website (objects365.org, read 2026-10-29) asks for a citation and states **no licence or terms**.
- So RF-DETR's Apache-2.0 checkpoints have the same Objects365 lineage that D-FINE's authors flag. Whether that matters
  is a licence-risk decision. **Decided (user, 2026-10-29):** accept RF-DETR's checkpoints on Roboflow's Apache-2.0
  label, because Sighter is for personal, non-commercial use; every model card records the lineage (ADR 0001
  decision 1).

**Recommendation.**

- **Inference, v1: CPU, CoreML and DirectML only.** DirectML already runs on NVIDIA laptop GPUs and Intel integrated
  GPUs, with one 18.5 MB file and no extra licence beyond the approved exception.
- **OpenVINO (inference): candidate opt-in after the spike**, if it beats DirectML on Intel integrated GPUs by a clear
  margin at f32 with correct results. It is permissive (Apache-2.0/MIT), but adds a ~100 MB runtime and its own build
  target. **Not on the NPU for RF-DETR** until fp16 results are shown to be correct.
- **CUDA/TensorRT (inference): not planned.** DirectML already uses the NVIDIA GPU; CUDA/TensorRT add 0.5–1 GB of
  proprietary libraries and an ADR licence exception for a speed-up nobody has measured on a laptop. Revisit only if the
  spike shows DirectML too slow on NVIDIA.
- **Training, NVIDIA: CUDA as an opt-in training runtime.** PyTorch training has no DirectML path; CUDA is the only
  practical accelerator on NVIDIA. The PyTorch CUDA wheels bring NVIDIA's proprietary libraries, so this needs a recorded
  licence exception. **Approved (user, 2026-10-29)**: training only, downloaded on request (ADR 0001, "Licence
  exceptions").
- **Training, Intel GPUs**: not in v1 (OpenVINO is inference-only; PyTorch's Intel GPU support was not checked).
  Apple Silicon trains on MPS, everything else on the CPU.

## 12. ONNX Runtime telemetry

- **ONNX Runtime 1.31.0** (release notes, published 9 October; the page shows no year): "Supported native builds now default to 1DS telemetry. Windows
  TraceLogging remains selectable with --use_windows_telemetry ... telemetry can be disabled with --no_telemetry."
- **ONNX Runtime's `docs/Privacy.md`**: telemetry is "ON by default in the official builds"; Windows apps and components
  use TraceLogging (ETW; "based on user consent, this data may be periodically sent to Microsoft servers"); other builds
  use the 1DS SDK (`cpp_client_telemetry`) "to send the same trace events to Microsoft's telemetry backend over HTTPS".
  Ways to disable: `--no_telemetry` at build time; `ORT_DISABLE_TELEMETRY=1` before ONNX Runtime initialises (all 1DS
  builds; "The legacy Windows TraceLogging backend does not use this environment variable"); the API that suppresses
  non-essential events, after which "ONNX Runtime may already have emitted a minimal initialization event".
- **`ort-sys` rc.15** links the 1DS libraries (`mat`, curl, mbedTLS) when a build contains them
  (`build/static_link/mod.rs` lines 312–321) and links `shell32` because "ONNX Runtime's Windows telemetry uses
  CommandLineToArgvW ... since 1.30" (line 43).
- **pyke's 1.31.0 archives, inspected 2026-10-29** (downloaded from `cdn.pyke.io`, SHA-256 matching `dist.tsv`):
  - `aarch64-apple-darwin+coreml`: one `libonnxruntime.a`; it contains ONNX Runtime's generic `telemetry.cc` (session
    telemetry hooks) but **no 1DS SDK symbols** (`nm`: no `Microsoft::Applications::Events`, no `curl_easy_*`) and no
    Microsoft collector host names in its strings. Indicative (a string and symbol search, not a build audit).
  - `x86_64-pc-windows-msvc+directml`: `onnxruntime.lib` (360 MB) and `DirectML.dll` 1.15.4. The library **contains the
    TraceLogging provider** (`Microsoft.ML.ONNXRuntime`, `ONNXRuntimeTraceLoggingProvider`, `_TraceLoggingMetadata`)
    and `EnableTelemetryEvents`/`DisableTelemetryEvents`; no 1DS or curl strings were found.
- **Consequence (decided, user, 2026-10-29):** Sighter self-builds ONNX Runtime with `--no_telemetry`, keeps
  `ORT_DISABLE_TELEMETRY=1` plus `DisableTelemetryEvents` as a second line, and runs an egress test on `--self-test`
  (ADR 0001 decision 4, plan item P5).
- The indicative measurement (section 5) used the official 1.31.1 wheel with telemetry **not** disabled.

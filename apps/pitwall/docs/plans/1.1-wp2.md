## Where Pitwall stands (measured on the branch base)

- **Tokens.** `src/styles.scss` defines its own scale (about 90 custom properties per scheme: `--bg-*`, `--sp-*`, `--fs-*`, `--r-*`,
  `--text-*`, `--accent*`, `--ok/warn/bad/info*`, `--viz-*`, shadows) and its own Material theme over them; components use
  about 1,600 `var(--…)` references to it and none to `--pd-*`. `angular.json` loads none of paddock-ui's CSS.
- **Material.** Icons, tooltips, slide toggles and one progress bar are Material; buttons (`.btn`), fields, the select
  (`pw-select`), tabs, menus (`pw-row-menu`, `pw-context-menu`), the confirm (`pw-confirm-dialog`) and the toast host are
  Pitwall's own.
- **Shell.** The Rust app crate (`src-tauri`) has its own start, window, tray, app menu, native feel, quit and updater
  (`shell.rs`, `window.rs`, `tray.rs`, `app_menu.rs`, `native_feel.rs`, `quit.rs`, `updater.rs`; about 1,400 lines) on
  `tauri::Builder`, not on `paddock-shell`. The UI has its own sidebar and routes.
- **Dialogs.** Five in-page CDK dialogs: `pw-confirm-dialog` (11 call sites), `pw-create-app-dialog`, `pw-key-secret-dialog`,
  `pw-quit-dialog`, `pw-service-consent`. The slots panel is an anchored popover and stays one (ADR 0026 §7).
- **Layout.** `e2e/layout.e2e.ts` measures 22 states at 900, 1024 and 1280 px; its baseline holds 90 known problems
  (52 at 900, 25 at 1024, 13 at 1280), each a test that fails until the line is gone. `e2e/a11y.baseline.json` holds 4 axe
  routes.
- **No About, no notices.** There is no About window and no `THIRD_PARTY_NOTICES.md`.

## Shared-code changes Pitwall needs

Packages 2.1 to 2.6 need one shared fix (the menu's Quit with no window open, item 1); the others are settled:

1. **A Quit the app may ask about first: one shared fix needed (code review 2026-10-30).** Pitwall asks "Quit, keep
   serving / Quit and stop serving" before it quits (setting "When you quit Pitwall": keep serving, stop serving, ask).
   The real paths today:
   - **Tray menu** (Quit, Quit and stop serving): Pitwall's own tray actions (`tray.rs` `act`) call `quit::request` in Rust,
     with or without a window open.
   - **macOS app menu** (`pd.app.quit`, Mod+Q, and "Quit Pitwall and stop serving"): Pitwall contributes them in the UI
     (`shell/contributions.ts`, `QuitFlow`); paddock-menu routes a native menu click to the focused window's UI. With the
     main window open this works. **With no window open, paddock-menu's `route()` finds no target and drops the click**,
     so Quit does nothing (the 1.0 `app_menu.rs` handled it in Rust). The shared fix is a "no target window" handler with
     a builder hook (branch `fix/menu-quit-without-window`, another agent); Pitwall then registers `quit::request(None)`
     for `pd.app.quit` and `quit::request(Some(StopServing))` for `pw.quit-stop`. Until it lands, the mock-runtime test
     `quit_from_the_menu_with_no_window_open_still_quits_or_asks` (`tests/shell.rs`, ignored with that reason) shows it
     failing.
   - Every path goes through `quit::request`: it decides from the setting, asks with `pw.quit` when asked to (it always
     sets `PendingAsk` and emits `pitwall://quit-ask`; the UI takes the pending ask before asking, so a leftover never pops
     up later), applies the choice and only then calls `paddock_window::tauri::quit`. A cancelled question never reaches
     the window layer.
   - An OS-level quit (Dock, log out) reaches the shell's `exit_requested` directly and keeps serving, as 1.0 does.
   - **When `fix/menu-quit-without-window` is on `main`** (with Dyno 1.0; do not merge the branch before): the shell
     frames add `pd.app.quit` with Mod+Q by default, so delete Pitwall's own `pd.app.quit` command, keybinding and menu item
     (`shell/contributions.ts`), provide the ask flow as `APP_QUIT` instead, and register `quit::request` with
     `Builder::menu_quit_without_window` on the Rust side; then un-ignore the test above.
2. **Translucent main window: decided, no shared change.** Pitwall's main window used Mica / vibrancy (`html.translucent`);
   the shared window layer has a material for the tray popover only. **User decision 2026-10-30: the main window is opaque,
   like every family window; no shared translucency option is added.** Done on the branch: the `transparent` and
   `windowEffects` settings, the `translucent` class and the `--pw-*` window, sidebar and content backgrounds are gone, and a
   Rust test checks that no window configuration is transparent. `macos-private-api` stays for the shared tray popover.

3. **Found in WP-2.4: the shared updater has no offline gate.** Pitwall 1.1 refuses an app-update check while offline mode is
   on and fails closed (`updater::OfflineKnown`, WP-1). `paddock_updater::tauri::UpdatesBuilder` has no such predicate: once
   Pitwall registers it with its feed (About's Updates and the background check), a check would go online in offline mode.
   Until that is settled Pitwall keeps its own update flow (`updater.rs`, the WP-3 `start_app_update` job) and does not
   register the shell's updater. **Decision needed:** (a) a shared change, an offline predicate on `UpdatesBuilder` that
   the background and manual checks honour (about 0.5 agent-day, failing test first, after the freeze), then Pitwall moves
   to the shared updater with its service hooks; or (b) Pitwall keeps its own updater in 1.1 and About is registered
   without a channel (About shows the legal documents; Updates says this build updates itself elsewhere). WP-2.7 needs the
   answer because About and the notices come from `UpdatesBuilder::legal`.
   **Decided 2026-10-30: (a).** Done on the branch: `UpdatesBuilder::offline_mode` / `Updater::with_offline_mode`
   (`paddock-updater`, commit 0ee1a55ff; it lands on `main` when shared code unfreezes after the Dyno and Spotter tags),
   and Pitwall on the shared updater with `OfflineKnown::blocks_updates` and its service hooks (branch
   `pitwall/1.1-wp2-shell-ui`, with the UI half of WP-2.5).
   **Code review 2026-10-30, done:** the predicate is three-valued (`OfflineState::{Off, On, Unknown}`); unknown blocks
   with its own kind and words (`offlineUnknown`: "could not be confirmed off") instead of claiming Offline mode is on.
   Pitwall keeps the last confirmed value in `offline-known.json` in its data folder, so a restart with the server not
   answering still knows it; a first run is unknown. Offline mode turned on during a download: **Pitwall cancels the
   update job** when `OfflineKnown` flips to on (`stop_update_transfer`; a verified download is kept), rather than a
   per-chunk check in the shared downloader. The server pushes a `server` frame when the settings are saved, so the flip
   is heard at once. `tests/shell.rs` proves the wiring.
   **Other apps (checked 2026-10-30, not changed):** Dyno uses the shared updater and has no Offline mode of its own, so
   its update checks are a network path no Offline switch reaches; Spotter on `main` has its own updater and no Offline
   mode either. Neither app uses `paddock-net`'s `Egress::set_offline`; the shared updater downloads through
   `paddock-download`, which that switch does not reach. Dyno passes `DYNO_COMMIT`/`DYNO_BUILT` to `build_info`, but the
   family's `build-env` action sets `PADDOCK_BUILD_COMMIT`/`PADDOCK_BUILD_DATE` (Pitwall uses those).

Everything else Pitwall needs is on `main`: `paddock_shell::Builder` with `tray`, `launch`, `add_to`, `windows`, `updater`
(About, What's new, Updates and the legal documents), `dialogs`; `paddock_dialogs::dialogs!`; `pd.confirm`; the pages frame;
`paddock_shell::testing::start` for the start test; `scripts/notices.sh` for the notices.

### WP-2.1 Tokens: `--pd-*` everywhere (no shared change)

- `angular.json` loads `paddock.css`, `controls.css` and `material.css` from `ui/dist/paddock-ui/css` (as Dyno does);
  `<html data-accent="pitwall">`; Pitwall's own Material theme and its own token scale are deleted from `styles.scss`.
- Every component style and template uses `--pd-*` directly; there is no bridge of the old names. Values between steps move
  to the scale (`--sp-5` 20 px → 16 or 24 by context, `--r-xl` → `--pd-radius-dialog`); the few Pitwall-only layout values
  that have no family token (title-bar inset) are `--pw-*` locals defined once.
- The chart colours come from the shared palette (`--pd-chart-*`); `shared/theme-tokens.ts` mirrors `--pd-*` values for
  ECharts and `scripts/ci/tokens.test.mjs` checks that every mirrored value equals the shared token.
- **Colour-vision check (accepted 2026-10-30, ER-22).** The palette's colour-vision separation is measured once, by
  paddock-ui's token test (`ui/test/tokens`: adjacent series ΔE ≥ 20 CIE76 and the first five pairwise ≥ 14, under
  protanopia, deuteranopia and tritanopia). Pitwall's own copy of that check, on its OKLab metric and threshold (adjacent
  ΔE ≥ 8, which the family palette misses at 7.80 light and 7.87 dark), is deleted; Pitwall's spec keeps only what its
  charts rely on (eight slots in order, every mark 3:1 against the card).
- Acceptance:
  - a unit test fails on any `var(--x)` in `src/**/*.{ts,scss}` that is not `--pd-*`, `--pw-*`, `--mat-*`/`--mdc-*` or a
    component-local property declared in the same file;
  - `styles.scss` declares no colour literal;
  - the app follows `data-theme`, `data-accent`, `data-density` (spec: the root variables change with each);
  - layout and axe baselines: no new line; unit tests, lint and build green; screenshots of every route in both themes.
